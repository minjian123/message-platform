## 1. 任务级边界与输入基线 <a id="scope"></a>

**做什么**：在 06-3-1 的指标面之上，交付 Prometheus 告警规则、P0~P3 分级、抑制与恢复、Grafana 看板，并完成 bms 可观测性栈的声明式接入。

**不做什么**：

- 不新增业务指标（只引用 06-3-1 已登记指标名）；
- 不改 Alertmanager 通知通道实现（邮件 / webhook / 短信）；
- 不做真实容量模型（阈值占位，8B_12 回填）；
- 不部署 msg 服务本身（服务器当前无 msg 进程，真机触发登记部署窗口）。

## 3. 规则文件结构 <a id="rules"></a>

```text
msg/deploy/observability/
├── rules/
│   └── msg.yml                 # Prometheus 规则（本任务主交付）
├── tests/
│   └── msg-rules.test.yml      # promtool test rules 输入序列
└── grafana/dashboards/
    └── msg.json                # 概览看板（部署聚合到 bms 栈）
```

`msg.yml` 头部固定注明：

```yaml
# msg 消息平台告警规则（06-3-2；指标清单见 bms_msg/metrics/names.py）。
# 加载：bms prometheus.yml 的 rule_files（/etc/prometheus/rules/products/*.yml）。
# 校验：promtool check rules /etc/prometheus/rules/products/msg.yml
#       promtool test rules /etc/prometheus/rules/products/msg-rules.test.yml
# 分级：P0/P1 → severity=critical；P2/P3 → severity=warning；priority 保留 P0~P3。
# 阈值：带 `# TODO(8B_12)` 的为占位值，容量模型回填后只改数字，不改表达式结构。
groups:
  - name: msg-availability
  - name: msg-lag
  - name: msg-errors
  - name: msg-dlq
  - name: msg-storage
  - name: msg-replay
```

**分组原则**：按「故障面」分组，不按级别分组；一组内同级规则共享 `for` 与标签模板，便于整组启停。

## 4. 分级与规则清单 <a id="alerts"></a>

| 级别 | 告警 | 表达式（要点） | for | 标签 | 说明 |
| --- | --- | --- | --- | --- | --- |
| P0 | `MsgMetricsDown` | `up{job="msg"} == 0` | 1m | `severity=critical, priority=P0, service=msg` | 抓取失败 = 进程挂 / 网络不可达 / `/metrics` 失守 |
| P0 | `MsgNotReady` | `probe_success{job="bms-probe", instance=~".*/msg:8000/readyz"} == 0` | 2m | 同上 + `probe=readyz` | 就绪失败（存储 / 数据库 / 摘流中） |
| P1 | `MsgConsumerLagHigh` | `sum by (tenant, topic) (msg_consumer_lag) > 10000` | 10m | `severity=critical, priority=P1, service=msg` | 单主题总积压超阈值 |
| P1 | `MsgConsumerLagGrowing` | `sum by (tenant,topic)(msg_consumer_lag) - sum by (tenant,topic)(msg_consumer_lag offset 20m) > 5000` | 10m | 同上 | 积压持续增长（区别于一次性堆积） |
| P1 | `MsgPublishErrorRate` | `sum(rate(msg_publish_errors_total[5m])) / clamp_min(sum(rate(msg_messages_in_total[5m])), 0.001) > 0.05` | 5m | 同上 | 发布错误率 > 5% |
| P2 | `MsgDlqGrowing` | `sum by (tenant,topic) (rate(msg_dlq_growth_total[5m])) > 1` | 10m | `severity=warning, priority=P2, service=msg` | 死信快速增长 |
| P2 | `MsgDelayDeliverFailed` | `sum(rate(msg_delay_deliver_failed_total[5m])) > 0.1` | 10m | 同上 | 到期转投失败 |
| P2 | `MsgIsrShrinking` | `sum(rate(msg_isr_shrink_total[15m])) > 0` | 15m | 同上 | 02-5 交付前恒 0，规则先就位 |
| P2 | `MsgReplayFailed` | `sum(increase(msg_replay_failed_total[10m])) > 0` | 0m | 同上 | 重放任务失败 |
| P3 | `MsgDiskHigh` | `msg_disk_used_ratio > 0.85` | 15m | `severity=warning, priority=P3, service=msg` | 磁盘高水位 |
| P3 | `MsgStorageRejected` | `sum(rate(msg_storage_rejected_total[5m])) > 0` | 10m | 同上 | 存储拒绝（盘满 / 采样失败） |
| P3 | `MsgInflightStall` | `sum by (tenant,topic) (rate(msg_window_stall_total[5m])) > 1` | 10m | 同上 + `tenant,topic` | 传输层持续暂停 |
| P3 | `MsgLongPollWaitersHigh` | `msg_long_poll_waiters > 1000` | 10m | 同上 | 等待器接近上限 |
| P3 | `MsgRateLimitRejected` | `sum(rate(msg_rate_limit_rejected_total[5m])) > 5` | 10m | 同上 | 持续限流 |

**注解模板**（每条告警必须齐全）：

```yaml
annotations:
  summary: "主题 {{ $labels.topic }} 积压 {{ $value | humanize }} 条"
  description: "租户 {{ $labels.tenant }} / 主题 {{ $labels.topic }} 积压持续 10 分钟超阈值 10000；检查消费者数量与处理耗时，或上游突增。"
  runbook_url: "msg文档/项目/08B_消息平台/任务/06_管理与运维/06_管理与运维_03_指标与告警/06_管理与运维_03_指标与告警_02_告警规则与分级抑制恢复.md#runbook"
  dashboard_url: "/d/msg-overview?var-tenant={{ $labels.tenant }}&var-topic={{ $labels.topic }}"
```

- `runbook_url` 为仓库文档路径，文档站部署后由网关替换为可点击 URL（口径写入文件头）。
- `dashboard_url` 用 Grafana 相对路径，避免写死主机 / IP（红线）。
- `description` 必须写「看哪里、做什么」，不写「指标异常」这类不可行动文案。

## 5. 抑制与恢复 <a id="inhibit"></a>

### 5.1 抑制（落 bms `alertmanager.yml.tmpl`）

在现有「critical 抑制同名 warning」之外新增两条：

| # | source | target | equal | 目的 |
| --- | --- | --- | --- | --- |
| 1 | `severity="critical"`（P0/P1） | `severity="warning"`（P2/P3） | `service` | 同实例 P0/P1 在途时抑制 P2/P3 |
| 2 | `priority="P1"` | `priority="P3"` | `service`, `topic` | 同主题 P1 积压抑制 P3 噪音 |

**保留现有规则**：critical 抑制同名 warning（`equal: alertname, service`）不动，避免改变 BMS 既有告警行为。

**注意**：`equal` 中的标签在 source 与 target 必须同时存在；P3 的全局规则（如 `MsgDiskHigh`）没有 `topic`，不会被第 2 条匹配（符合预期）。

### 5.2 恢复

- receiver 的渠道块由渲染脚本生成，`send_resolved: true` 已写入 `email_configs` / `webhook_configs`（无凭据时 no-op receiver，不建渠道）。
- 恢复条件与触发条件**对称**：同一表达式 + `for` 结束即恢复；积压类用同一阈值，不引入双阈值（避免阈值之间来回抖动）。
- 抖动控制：所有告警带 `for`；`MsgReplayFailed` 用 `increase(10m) > 0`，事件型不设 `for`，但 10 分钟窗口内只报一次。

### 5.3 静默

维护窗口 / 计划重放由 Alertmanager 静默（silence）处理，不在规则里写死时间窗；操作入口与权限归运维流程。

- **不把未实测数字写成最终结论**（任务书要求）；测试记录登记「占位」状态。

## 7. Grafana 看板 <a id="dashboard"></a>

- 文件：`deploy/observability/grafana/dashboards/msg.json`；UID `msg-overview`；标题「消息平台概览」。
- 数据源：`uid=prometheus`（bms provisioning 已固定）。
- 变量：`tenant`（`label_values(msg_consumer_lag, tenant)`）、`topic`（联动 tenant）。
- 面板：
  1. 吞吐：`sum(rate(msg_messages_in_total[5m]))` / `sum(rate(msg_messages_out_total[5m]))`
  2. 积压：`sum by (tenant,topic)(msg_consumer_lag)`（Top 10 + 趋势）
  3. 死信：`sum(msg_dlq_total)` + `sum(rate(msg_dlq_growth_total[5m]))`
  4. 磁盘：`msg_disk_used_ratio`
  5. 延迟：`histogram_quantile(0.95/0.99, sum by (le)(rate(msg_publish_latency_ms_bucket[5m])))` 与 consume 同口径
  6. 错误：`sum by (reason)(rate(msg_publish_errors_total[5m]))`
  7. 饱和度：`sum by (tenant,topic)(msg_inflight_bytes)`、`msg_long_poll_waiters`
  8. 重放：`msg_replay_tasks` / `msg_replay_replayed_total`
- 06-1 概览页跳转用 `/d/msg-overview`，不内嵌 Grafana iframe（避免 X-Frame 与鉴权耦合）。

## 8. bms 接入（跨仓） <a id="integration"></a>

### 8.1 `prometheus.yml`

```yaml
# 抓取目标追加（与 bms-services 并列；msg 独立部署，需与 observability 同网络）
  - job_name: msg
    static_configs:
      - targets: ["msg:8000"]

# 规则目录追加（保留原 bms 路径）
rule_files:
  - /etc/prometheus/rules/*.yml
  - /etc/prometheus/rules/products/*.yml
```

- `msg` 主机名依赖部署网络别名；msg 未部署时该 target 为 `up=0`，会触发 `MsgMetricsDown`——**上线顺序**：先部署 msg，再把该 target 加入生产 `prometheus.yml`（登记部署窗口步骤）。
- 探针目标追加 `http://msg:8000/healthz` / `http://msg:8000/readyz`，与 `bms-probe` 同口径。

### 8.2 `compose/observability.yml`

```yaml
  prometheus:
    volumes:
      - ../observability/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ../observability/rules:/etc/prometheus/rules:ro
      - ../observability/products:/etc/prometheus/rules/products:ro
```

Grafana 已挂载整个 `dashboards` 目录，产品看板放 `dashboards/products/msg/` 即可被 file provider 递归发现，无需改 Grafana 配置。

### 8.3 `alertmanager.yml.tmpl`

- 两个 receiver 显式 `send_resolved: true`；
- `inhibit_rules` 增加 §5.1 两条；
- 渲染脚本与凭据外部化口径不变。

## 9. 部署聚合 <a id="deployment"></a>

服务器部署目录是 `~/deploy`（bms `deploy/` 的副本），没有 msg 仓。因此产品可观测资产采用「**msg 仓自持源文件 + 部署时聚合**」：

```text
msg 仓                                  部署机（bms 部署目录）
deploy/observability/rules/msg.yml  →   observability/rules/products/msg.yml
deploy/observability/tests/*.yml    →   （仅校验用，可不部署）
deploy/observability/grafana/
  dashboards/msg.json               →   observability/grafana/dashboards/products/msg/msg.json
```

- 聚合步骤登记到 bms《部署窗口待办》与 msg 任务测试记录（本次服务器无 msg 服务，不做真机触发）。
- 后续若产品增多，聚合脚本化（登记为平台运维能力项，不在本任务扩张）。
