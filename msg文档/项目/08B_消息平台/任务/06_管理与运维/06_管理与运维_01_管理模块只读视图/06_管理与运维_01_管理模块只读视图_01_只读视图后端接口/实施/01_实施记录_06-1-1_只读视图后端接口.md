## 3. 关键命令 <a id="commands"></a>

```text
# 静态（单文件 / 单节点）
cd backend
.venv/Scripts/ruff.exe check <改动文件>
.venv/Scripts/ruff.exe format <改动文件>
uv run pyright <改动文件>

# 契约与前端类型（应用装配冒烟也走这两条）
.venv/Scripts/python.exe -m ops.contract_snapshot export
.venv/Scripts/python.exe -m ops.contract_snapshot check
cd ../frontend && node packages/api-types/scripts/generate.mjs --check

# 门禁与覆盖率
cd .. && .venv/Scripts/python.exe scripts/tools/preflight/提交前预检.py
```

Windows 与 Linux 的差别：解释器与 `ruff` 在 Linux 换 `backend/.venv/bin/`；`uv run pyright` 必须带 venv 环境，直接调 `pyright.exe` 会因找不到 `bms_core` 而报大量假错。

## 4. 问题与处置 <a id="issues"></a>

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 端口方法拟名 `locate_by_log_id` 会覆盖 `FileMessageStore` 既有同名方法 | 后者返回 `FileSlice`（磁盘坐标），端口要返回头视图，同名会打断 02-7 恢复期去重链 | 端口改名 `find_by_log_id()`，先回写详细设计 §6.1 再实施 |
| 2 | 前置契约写 `DelayStore.list_all()` 同源 | `/admin/delayed` 实际用 `list_for_tenant()`；`list_all()` 跨租户 | 汇总改用当前租户快照，回写任务文档 §5 与设计 §3 |
| 3 | 概览四端点无法逐主题做 describe 判定 | 概览无 `namespace` / `topic` 参数，06-3 快照键不带命名空间 | 停下逐项确认，结论为「租户级汇总不输出主题分项、不逐主题判定」，回写设计 §10 与「对齐记录」第 10 项 |
| 4 | `DELAY_STUCK_TTL_MS` 是七天，拿它当堆积提示会让 `hint` 恒为 `normal` | 该常量是 02-7 恢复台账兜底判据，不是视图语义 | `stale_count` 只按「已到期未转投」计数，回写设计 §8.2 |
| 5 | `min_remaining_ms` 恒为 0 | `minimums` 初始化成 0，使「更新更小剩余时间」分支永不可达 | 去掉初始化，无记录时由 `get(key, 0)` 兜底；补同档三条记录用例闭合分支 |
| 6 | `_payload` 改普通 dict 后被裸集合护栏拦 | 函数返回签名属新增裸集合声明 | 按框架边界加 `# bare-collections:allow` 并写明 pydantic 序列化理由；`MessageItem.headers` 同口径 |
| 7 | 生成器零漂移用例在 `pytest -n auto` 下偶发 `first != second` | 多个用例并发改写 / 删除同一份生成物 | 合并为单用例串行执行 + `finally` 恢复现场 |
| 8 | 单文件 `pyright.exe` 报 232 个假错 | 未带 venv 环境，`bms_core` 解析不到 | 统一改用 `uv run pyright <文件>` |
