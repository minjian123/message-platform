## 2. 任务内容 <a id="content"></a>

1. **表设计先行**：在 `msg文档/设计/数据库设计/数据表设计/` 新增 `msg_dead_letter` 表文件，写归属 / 字段 / 索引 / 分片归档 / 变更记录，并在《[数据库设计总览](../../../../../../设计/数据库设计/01_数据库设计_总览.md)》「已设计数据表登记」登记；**表文件先于模型与建表**。
2. **字段**：至少含 `id`（雪花）、`tenant_id`、`namespace`、`topic_id`、`topic`、`partition_no`、`offset`、`message_id`、`log_id`、`reason`、`attempts`、`detail`（JSON）、`status`、`disposition_reason`、`disposed_by`、`disposed_at`、`replay_task_id`、审计字段与 `version`；`status` 五态与需求一致。
3. **索引**：`(tenant_id, status, created_at)` 支撑列表；`(topic_id, partition_no, offset)` 定位；`replay_task_id` 关联重放任务；不建物理外键。
4. **端口替换**：新增持久化 `DeadLetterQueue` 实现，保持 `add` / `list_all` / `contains` / `purge_topics` 签名；`add` 同三元组幂等；`list_all` 保持插入序语义（按 `created_at` / `id` 稳定排序）；内存实现保留为测试替身。
5. **服务与仓储**：新增死信仓储与状态迁移服务；状态迁移只允许需求定义的五态路径；`replaying` 关联 `replay_task_id`；终态写 `disposed_by` / `disposed_at` / `disposition_reason`。
6. **启动恢复**：服务启动时从表加载活跃死信到运行态（或按需查询，不强制全量驻留）；与 01-2 投递侧 `contains` 判定同源，避免重启后重复投递或漏判。
7. **清理**：主题删除（06-2）时按 `topic_id` 清理死信；租户生命周期清理复用 `purge_topics` 语义；清理幂等。
8. **边界**：不删除原始日志记录；不把死信表当消息存储；不做冷归档存储；不改 `nack` 上报契约。
9. **测试**：表文件 ↔ 总览 ↔ 目录一致性；五种状态迁移与非法迁移拒绝；同三元组幂等；重启恢复；主题删除清理；`list_all` 排序稳定；变更模块行 + 分支覆盖率 100%。

## 3. 完成标准 <a id="accept"></a>

- `msg_dead_letter` 表文件已建并在总览登记，模型、仓储、建表落地一致；
- 死信记录含原因、重试次数、原 offset、`message_id` / `log_id`、状态与处置信息；
- 五态迁移矩阵可验证，非法迁移拒绝；
- 持久化实现替换内存实现且端口签名不变，重启不丢；
- 主题删除 / 租户清理可幂等清理死信；
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
