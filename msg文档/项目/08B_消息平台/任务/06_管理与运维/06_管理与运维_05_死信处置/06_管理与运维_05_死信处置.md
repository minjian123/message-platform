## 3. 任务内容 <a id="content"></a>

1. **死信来源**：重试超过上限的消息进入死信，记录原因（`delivery_exhausted` / `schema_invalid` / `processing_failed`）、重试次数、原 offset、`message_id` / `log_id`、主题 / 分区、失败详情。
2. **状态机**：`pending`（待处置）→ `replaying`（重放中）→ `resolved`（已解决）/ `pending`（再次失败）；`pending` → `ignored`（已忽略，必须填原因）；`pending` / `ignored` → `archived`（已归档）。状态迁移必须可审计、可回放。
3. **持久化**：新建 `msg_dead_letter` 表落平台库，替换现有 `InMemoryDeadLetterQueue`；先改数据库表文件并登记总览，再改模型、仓储与服务；启动时从表恢复，重启不丢死信。
4. **处置动作**：重放复用 01-6 已交付的任务化重放（可限速、可暂停 / 取消、进度可见；06-6 后续补影响可见与页面）；忽略必须填原因；归档只改状态并从活跃列表隐藏，原始消息仍在日志保留期内可查。
5. **权限与审计**：查询 `msg:query`，重放 / 忽略 / 归档 `msg:manage`；全部处置写基座审计链，记录操作人、原因、时间、`record_ref`（死信记录 ID 与 `log_id`）。
6. **告警**：死信增长接 06-3 指标与 P2 告警；处置失败、重放再次失败有指标 / 日志，不静默。
7. **页面**：死信与重放页的“死信”页签提供列表、筛选、详情、处置入口；重放交互与 06-6-2 共用。
8. **边界**：不删除原始日志记录；不把死信当业务错误日志；不绕过消费端幂等；归档不承诺长期冷存储（后续归档阶段另议）。
9. **测试**：三种原因入死信；五态迁移矩阵；重启恢复；重放 / 忽略 / 归档；忽略缺原因拒绝；审计与 `record_ref`；死信增长指标；变更模块行 + 分支覆盖率 100%。

## 4. 完成标准 <a id="accept"></a>

- 毒消息进入死信后不阻塞主链路，原因 / 重试次数 / 原 offset 可查；
- 死信五态可迁移，重启不丢，处置结果可追溯；
- 重放复用任务化能力，忽略必须填原因，归档后从活跃列表隐藏；
- 全部处置有 `msg:manage` 与审计，`record_ref` 可定位；
- 死信增长可触发 P2 告警，处置失败可见；
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
