## 2. 实施过程 <a id="process"></a>

| 序 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 值对象 | 新增 `core/trace.py`：`TraceContext`（四字段 frozen）+ 三条不变量（不可变 / 各自可空 / 空即单例）、`TRACE_FIELD_MAX_LENGTH = 128`、`trace_of()` 唯一换算入口、`TraceCarrier` 协议（请求模型 / 记录头 / 存储记录 / 延迟记录共用，不用 union） |
| 2 | 记录层 | `broker/record.py`：`RecordHeader.trace_id` 字段改为 `trace: TraceContext` + `trace_id` 只读属性；`_pack_header` 恒写顶层 `trace_id`、仅在 `trace.has_span` 时写 `trace` 子 map；`_decode_trace` 合成（子 map 非 map / 值非字符串一律退化 `None`，不判损坏）；**不升 `RECORD_FORMAT_VERSION`** |
| 3 | 端口 | `broker/log.py`：`MessageStore.append` / `InMemoryMessageStore.append` 收 `trace`；`StoredMessage`、`MessageHeaderView` 落 `trace` + `trace_id` 只读属性；`message_header_view()` 同步 |
| 4 | 文件存储 | `broker/file_store.py`：`_PartitionLog.append` 与 `FileMessageStore.append` 收 `trace`，`_to_stored` 取 `header.trace` |
| 5 | 延迟链路 | `broker/delay.py`：`DelayRecord` 落 `trace` + `trace_id` 属性，发布走 `trace_of(request)`；`broker/scheduler.py` 到期转投 `trace=record.trace`（原样带入、不重新生成）；`broker/delay_file.py` 记录头编解码（`_put_header` / `_clear_header` / `_to_record`）同步 |
| 6 | 投递与重放 | `broker/delivery.py` 发布入口 `trace_of(request)`（死信仍只落 `trace_id` 列）；`broker/replay.py` 重放 `trace=message.trace`（`log_id` 新分配、`message_id` 与四项不变）；`broker/waiter.py` 端口转发同签名 |
| 7 | 契约 | `schemas/message.py`：`PublishRequest` additive 增 `span_id` / `parent_span_id` / `trace_flags`（默认 `null`，复用 `max_length=128`），`MessageItem` 四字段全部必填回显；`schemas/admin_view.py::MessageItem` additive 增四项，`api/admin/messages.py` 抽 `_admin_item()` 映射助手（检索响应与用例共用一处） |
| 8 | 三出口 | `api/data/messages.py::message_item()` 逐条填四项；`api/frame/responses.py::_message_meta()` 追加三项（`consume` 头与 `message` 帧共用，字段名与 JSON 一致） |
| 9 | 日志关联 | `api/data/messages.py` 新增 `_log_published()`：发布成功（立即 / 延迟两分支）写一条带四项的结构化日志；**空值不写 key**（日志器对上下文字段用 `setdefault`，显式 `None` 会顶掉自动注入的 `trace_id`）；消费侧不逐条打（批内多 trace） |
| 10 | 帧契约 | `protocol/contract.py`：`endpoint_fields.publish.optional`、`stream.message_header_fields` 追加三项；新增 `tracing` 段（四字段、上限、谁做决策、采样、批量、additive 六条口径） |
| 11 | 契约产物 | `python -m ops.contract_snapshot export` 重导快照；`node packages/api-types/scripts/generate.mjs` 重生成前端类型 |
| 12 | 用例 | 新增 `tests/broker/test_tracing.py`（12 例）、`tests/api/test_tracing_exports.py`（8 例）；`tests/broker/test_readonly_ports.py` 补 1 例（覆盖 `drop_topic` 的「目录未落盘」分支）；存量 28 个测试文件按新签名/新字段同步 |

## 3. 遇到的问题与处置 <a id="issues"></a>

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 批量改写把 `from bms_msg.core.config import (` 整行拆坏，3 个模块语法错 | 用字符串锚点插入 import，锚点匹配到了多行 import 语句的第一行 | 按 isort 顺序在 `core.message_id` 之后插 `core.trace`；被破坏处逐一还原 |
| 2 | `record.py` 出现 `def _split(...):    """文档串"""` 同行 | 编辑时误把换行并入上一行（同一次失误在 `_partition` 上重复出现） | `ruff check` 的 `invalid-syntax` 直接拦下，按行修回 |
| 3 | 40+ 处测试构造 `append(trace_id=…)` / `DelayRecord(trace_id=…)` 全部失效 | 端口从「一个字符串」改成「一个对象」，属**刻意**的破坏性变更（漏传即类型错） | 按「所属调用名」逐个分类改写：记录类载体改 `trace=TraceContext(trace_id=…)`；**死信 / 审计 / RPC 的同名参数保持不动**（那是请求上下文链路，不是消息链路） |
| 4 | `DelayRecord` 缺 `trace_id` 只读属性 | 只给了 `StoredMessage` / `RecordHeader` / `MessageHeaderView` 加属性，漏了延迟记录 | 用例 `AttributeError` 抓到，按同一口径补属性 |
| 5 | 首轮模块级覆盖率差 1 个分支（`file_store.py` 1745→1747） | `drop_topic` 的「目录不存在则不 `rmtree`」分支此前无覆盖，属既有缺口，落在本次变更模块范围 | 补 1 例：登记主题但目录从未落盘（另一实例先删），断言返回 0 且目录登记被清理；**不用 `pragma: no cover`** |
| 6 | `pyright` 对两个新用例文件报私有入口与 msgpack 类型 | 用例刻意直测编解码私有入口；`msgpack` 无类型存根 | 文件级 `# pyright: reportPrivateUsage=false`（附理由）+ 与 `broker/record.py` 同法的 `cast("Callable[..., bytes]", msgpack.packb)` 收窄 |
| 7 | 帧路径新增字段「是否需要另改白名单」 | `build_frame_gate` 的 `allowed` 由 `request_model.model_fields` 派生 | 无需改动：字段加进 `PublishRequest` 即自动放行，`_model_input` 按键取白名单 |
| 8 | `engkit base bare-collections` 拒不通过（新增 2 处） | 新加的 `_pack_trace` / `_decode_trace` 签名带 `dict[str, Any]`（护栏对函数签名与带注解局部一视同仁） | 内联 `_pack_trace`（直接写进 `raw` map）；`_decode_trace` 入参改 `object` + 内部 `cast`，与既有 `_decode_delay` 同法 |
| 9 | 提交环 diff-coverage 报 `record.py:453` 未被执行 | 该行是 `_decode_trace` 的「入参非 map → 空链路」防御分支（调用点已保证是 map） | 补两条直接断言（`_decode_trace(None)` / `_decode_trace("oops")`），**不用 `pragma: no cover`**；复跑后 16 模块 100% |
