## 3. 关键实现决策 <a id="decisions"></a>

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | 验收用例落 msg 仓单份 | 只有 msg 仓能同时 import `bms_core` 与 `bms_msg`；bms 仓 CI 不 clone msg，放两仓会导致判据漂移 |
| 2 | 自建临时 SQLite 三表 | bms 测试夹具不是可跨仓 import 的包；用例内建表避免复制协议实现，也不触碰共享库 |
| 3 | `AuditEventEmitter` 真实发射 + 测试隔离返回 `SqlOutboxStore()` | 保留真实写入 / 事务 / 失败分档路径；msg 仓 CI 不保证有 bms 事件契约快照，故用 `contract_mode=off`，只验可靠性不验签发契约 |
| 4 | `ProcessedEventStore` 作效果一次载体 | 复用 bms 已交付的 `(consumer, event_id)` 消费幂等；不新增第二套去重台账 |
| 5 | outbox `replay()` 作「重放」口径 | 与 01-8-1 §4.2 的既有 `replay()` 一致，不跨到 01-6 消息重放 |
| 6 | 重启重建 `EngineRegistry` / `SessionFactory` / dispatcher | 真正丢掉进程级状态，同时保持同一 SQLite 文件，稳定且不带外部依赖 |
| 7 | 失败注入用真 `MsgEventPublisher` + 缺主题 404 / 连接失败传输 | 失败信号与生产同一实现；不用替身恒抛、不手动断网 |
| 8 | V4 / V5b 的失败轮改用连接失败 | msg 测试应用会话为单例，404 路径未提交事务，随后建主题会撞「事务已开始」；404 已由 V5a 覆盖，判据不降 |
| 9 | 验收 V1 暴露缺陷后就地修复 | 用户拍板就地修复（限本任务链路）；`encode_event()` 的 `json.dumps(default=str)` 会把嵌套 `ConcurrentStableDict` 降级为字符串，审计 `record_ref` 因此丢失 |
| 10 | 修复用 `stable_json_dumps()` | 复用基座既有「递归规整集合 + 键排序 + 非 ASCII 直出」实现，不另写序列化器；标量载荷输出逐字节不变 |

## 5. 问题与处置 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | V1 首跑：消费端 `record_ref` 为字符串，记录级定位丢失 | 根因 `encode_event()` 的 `json.dumps(default=str)` 不识别嵌套 `ConcurrentStableDict`；按拍板改 `stable_json_dumps()`，补 bms 单测；`5dc11652e`；V1 复跑通过 |
| 2 | V4 / V5b 首跑：建主题报 `A transaction is already begun on this Session` | 404 路径未提交测试应用单例会话的事务；失败轮改用连接失败传输，404 由 V5a 覆盖；不修改测试应用 |
| 3 | 首跑所有用例报「连接串模板需要服务标识」 | `Settings` 读了 msg dev 配置的 `url_template`；夹具设 `BMS_ENV=test`，让 `[database.platform].url_template` 为空、由 `BMS_DATABASE__PLATFORM__URL` 指向临时库 |
| 4 | bms 仓 venv 无 `bms_msg` | msg 仓用例改用 `msg/backend/.venv`（3.14.4），bms 仓用例用 `bms/backend/.venv`；不用 PATH 上的 `python` |
| 5 | 本机定向 pytest 不合并覆盖率数据 | 不手工采集；模块级覆盖率交推送环与 CI 的 engkit 采集插件判定，测试记录如实注明 |
