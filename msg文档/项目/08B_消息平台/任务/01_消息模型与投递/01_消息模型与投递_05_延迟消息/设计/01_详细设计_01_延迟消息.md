## 1. 概述 <a id="overview"></a>

### 1.1 目标

把「延迟一段时间再投递」做成**发布的一个维度**：`/msg/publish` 带 `delay_level` 即延迟发布，消息先进该分区的延迟区，
到期由后台推进器 `append` 进分区日志——**此刻才分配 offset**，其后与普通消息完全一致。

三条不可动摇的边界：

1. **不占 offset**：延迟期间 `LEO` / 位点 / 积压都不变。若占位，一条 60m 的消息会堵死队头——01-3 的严格停等会整个分区停等一小时，
   而绕过它推进位点又违反「位点只按连续前缀推进」，等于推翻顺序性不变量。
2. **不产生免成员的投递通道**：到期消息仍须经 `consume`，成员制（01-4）与停等（01-3）原样生效。
3. **延迟是出问题时的兜底**：因此它自己不能成为新故障点——转投失败只拒绝进、不静默清；时钟回拨不提前投；延迟区满明确拒绝（`350015`）。

### 1.2 两段交付

| 段 | 内容 | 归口 |
| --- | --- | --- |
| **A 语义与接口（本任务）** | 档位契约、延迟区端口 + 内存实现、到期推进、转投、健壮性（除重启）、只读视图 | 01-5 |
| **B 持久化与到期恢复** | `.delay` 段落盘与 CRC、启动重建时间轮、恢复期按 `log_id` 去重、TTL 与段损坏隔离、优雅关闭刷盘 | 8B_02（需求 02-7） |

A 段的「重启不丢」由 B 段承接，本任务只保证**端口形态正确、语义可验、失败可见**，不提前钉死落盘格式。

## 2. 现状与差距 <a id="gap"></a>

| 现状（01-1 ~ 01-4） | 差距 | 本任务处置 |
| --- | --- | --- |
| `MessageStore.append` 是 offset 的唯一分配方 | 延迟消息不能在到期前进入日志 | 延迟区**不调 `append`**；到期才调 |
| `StoredMessage` 无记录身份 | 转投与重放都会产生「同 `message_id` 多条」 | `append` 增 `log_id`（发布时分配、转投沿用） |
| `publish` 同步落日志并返回 offset | 延迟发布此刻还没有 offset | `PublishResult.offset` 改为可空；延迟返回 `deliver_at` |

| `/admin/groups` 已有只读投影范式 | 延迟中消息不可见 | `DelayInspector` + `GET /msg/admin/delayed` |

## 4. 延迟模型 <a id="model"></a>

### 4.1 档位 <a id="levels"></a>

| 档位名 | 1s | 5s | 10s | 30s | 1m | 5m | 10m | 30m | 60m |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 毫秒 | 1000 | 5000 | 10000 | 30000 | 60000 | 300000 | 600000 | 1800000 | 3600000 |

- 表落 `core/config.py`（`DELAY_LEVEL_MS`，只读映射），**只增不删**：删档位会让存量延迟记录失去映射。
- 契约层为 `StrEnum`（`DelayLevel`），非法值由 pydantic 直接拒（`10001`），服务层再做一次防御性校验。
- 不加任意精度：档位是**容量与可测性**的边界（任意毫秒会让时间轮与用例同时失控）。

### 4.2 延迟记录 <a id="record"></a>

| 字段 | 说明 |
| --- | --- |
| `log_id` | **记录身份**（发布时分配，转投沿用）；延迟区内唯一键，也是 B 段恢复期去重判据 |
| `message_id` | 消息身份（重投 / 转投 / 重放都不变） |
| `tenant_id` / `topic_id` | 归属（计数按租户、转投按分区） |
| `namespace` / `topic` | 展示名（视图不必回查主题表即可展示，主题删除后仍可排障） |
| `partition_no` | **发布时锁定的目标分区**（扩分区后同 key 不漂移） |
| `delay_level` | 档位名（视图按档位分布统计） |
| `payload` / `headers` / `trace_id` / `key` / `published_at` | 与普通消息同义，到期原样 `append` |
| `deliver_at` | 到期时刻（UTC；判定 `deliver_at <= now` 才转投） |
| `attempts` | 转投失败次数（只计数与告警，**不作为丢弃依据**） |

**为什么记录里存 `namespace` / `topic` 展示名**：延迟区不保证主题一直存在（可被删）；转投时若主题已删，仍要能报出「哪条延迟消息没能投出去」，
而不是只剩两个雪花主键。

### 4.3 分区锁定 <a id="partition"></a>

发布时 `TopicRouter.route(topic, key)` 算出分区号并写进记录，到期直接投该分区：

- 与 01-1「同 key 恒同分区」一致；若到期再算，扩分区期间同 key 会落到另一分区，重放与顺序承诺同时破。
- 分区被删除（主题分区数不可减少，故不会发生）或主题停用时，转投按 §6.2 失败处置。

### 4.4 与 offset / 停等 / 积压的关系 <a id="offset"></a>

| 维度 | 延迟期间 | 到期 `append` 后 |
| --- | --- | --- |
| `LEO` | **不变** | +1 |
| 位点 | **不变** | 按普通消息推进 |
| 积压 `lag = LEO - committed` | **不计入** | 计入 |
| 停等 | **不参与**（不在日志里，`_collect` 看不到） | 参与（可能成为队头） |
| 死信 | 不适用 | 复用（重投超限即死信） |
| 保留期 | 不计时（延迟区另有 TTL，B 段） | 从 `append` 起算 |

这张表是本设计最需要守住的东西：**延迟消息在到期前对日志完全不存在**，所以 01-2 / 01-3 / 01-4 的全部不变量一行都不用改。

### 4.5 容量与配额 <a id="quota"></a>

- 软上限 **每租户 100 000 条**（`DELAY_QUOTA_PER_TENANT`），超限返回 `350015`（HTTP 429）。
- 为什么按租户而不按分区：延迟积压的成因是**业务重试潮**，按租户才拦得住「一个业务把整个延迟区吃满」；按分区会让分区少的主题先被拒。
- 为什么是软上限：它是**可配置的保护阈值**，不是硬配额；到顶时明确拒绝（比 OOM 好），并配套指标告警（06 域）。
- 与 `350005`（背压）的分工：`350005` 是全局背压（写入太快），`350015` 是延迟区容量到顶——排障时能一眼分清是「整体过载」还是「延迟堆住了」。

## 5. 到期驱动 <a id="driver"></a>

### 5.1 三层分桶 <a id="wheel"></a>

| 层 | 单元 | 桶数 | 覆盖 | 装填条件 |
| --- | --- | --- | --- | --- |
| L0 | 1s | 60 | 1 分钟内 | `delay < 60s` |
| L1 | 60s | 60 | 1 分钟 ~ 1 小时 | `60s <= delay < 3600s` |
| L2 | 3600s | 24 | 1 ~ 24 小时 | `delay >= 3600s` |

桶位按**绝对时间**取模（`slot = (deliver_at // unit) % span`），不是「相对当前指针偏移」——这样同一时刻多处装填不会算错，
时钟微抖也不会整体错位。首期最长档位 60m，L2 恒空但保留（扩档位不改结构）。

**超过 86400s 的延迟直接拒**（端口层 `10001`）：延迟区不是定时任务系统，超长跨度应由业务用「短延迟 + 状态机」表达。

### 5.2 装填 <a id="place"></a>

`enqueue` 记录 → `wheel.place(record)` 按 §5.1 选层入桶。装填是纯内存操作（O(1)），不做扫描。

### 5.3 推进与候选集 <a id="advance"></a>

`take_due(now)` 按「上次扫描时刻 → now」的秒窗口逐秒推进，每个秒位取三件事：

1. L0 该秒桶全部记录；
2. 若跨分钟边界，取 L1 该分钟桶全部记录；
3. 若跨小时边界，取 L2 该小时桶全部记录。

取出后**逐条判 `deliver_at <= now`**：

- 满足 → 交转投（§6）；
- 不满足 → **重新装填**（此时剩余时间必然变小，通常落进更细的层）。这就是「不级联也能正确」的原因：正确性由 `deliver_at` 判定兜底，
  分桶只用于缩小候选集；桶放错了顶多多扫几条，不会漏投、不会早投。

### 5.4 限速与批处理 <a id="throttle"></a>

| 参数 | 值 | 作用 |
| --- | --- | --- |
| 推进周期 | 1s | 与 L0 同粒度；1s 档位偏差 0~1s 且**只晚不早** |
| 单次追赶窗口 | 60s | 进程长停摆 / 时钟前跳后，单轮最多推进 60 秒，剩余留到下一轮（防「一次性扫完全部桶」的风暴） |
| 单轮转投上限 | 500 条 | 一批投不完就下一轮继续（防单轮卡死事件循环） |

### 5.5 时钟跳变 <a id="clock"></a>

| 场景 | 处置 | 结果 |
| --- | --- | --- |
| **回拨**（`now <= last_scan`） | 本轮直接返回空，**指针不后退** | 不提前投；记录留在桶里，时钟追上后照常到期 |
| **前跳**（`now - last_scan > 60s`） | 只推进 60s，其余留给后续轮次 | 不丢、不早投，只是补投变慢（可接受，且避免风暴） |

## 6. 到期转投 <a id="transfer"></a>

### 6.1 偏序：先写后清 <a id="order"></a>

```text
① 取到期记录 → ② MessageStore.append（沿用 log_id，分配 offset）
→ ③ 成功后才 DelayStore.remove(log_id)
```

反向（先清后写）会把崩溃变成**丢消息**；本序保证最坏结果是「重复转投」而不是丢失。B 段落盘后，重复由恢复期按 `log_id` 比对消掉（§6.3）。

### 6.2 失败处置 <a id="failure"></a>

`append` 抛异常（主题停用 / 租户停用 / 存储故障）时：

1. **不删延迟记录**（`attempts += 1`），下一轮重试；
2. 记录 `msg_delay_deliver_failed_total` 指标并打日志（`delay_deliver_failed`，带 `log_id` / `topic` / `attempts`）；
3. **不做丢弃**：延迟是兜底通道，丢一条就等于让业务的重试彻底失联；上限交给运维处置（06 域告警 + 人工）。

### 6.3 去重 <a id="dedupe"></a>

| 阶段 | 判据 | 说明 |
| --- | --- | --- |
| 运行期（本任务） | 单进程串行推进 + 转投成功即清 | 同一条不会被同进程投两次 |
| 恢复期（B 段） | 扫 `.log` 尾部建 `log_id` 集合，命中即清 | 用 `log_id` 而非 `message_id`：重放会以原 `message_id` 追加新记录，用它判重会误杀 |

### 6.4 与停等 / 死信 / 保留的关系 <a id="reuse"></a>

- **停等**：到期 `append` 只是往分区尾部加一条；若队头有未 ack 消息，它自然排在后面——不需要任何特殊处理，这是「不占 offset」换来的最大好处。
- **死信**：到期后就是普通消息，重投超限照常进死信。
- **保留期**：从 `append` 的 `published_at`（保留原发布时刻）还是从到期时刻起算？**取 `append` 时刻写入记录的时间戳语义不变**——即保留期以**到期时刻**为准（架构 04 §2.4 已定），避免「发布即长延迟 + 短保留期」导致消息未到期就被清。

### 6.5 结算与关闭 <a id="shutdown"></a>

- 首期无落盘，`stop()` 只需取消推进任务；B 段在 `stop()` 里补刷盘。
- 推进任务**惰性启动**：首个延迟发布（或首个到期查询）触发 `ensure_started()`，无请求则不起任务——基座 `service_lifespan` 未提供产品启动钩子，显式注册启动任务归 8B_01（§12 风险 3）。

## 7. 接口与契约 <a id="api"></a>

### 7.1 发布（延迟维度） <a id="publish"></a>

`POST /api/v1/msg/publish`，请求新增一个可选字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `delay_level` | `DelayLevel \| null` | 缺省 `null` = 普通发布；给值即延迟发布 |

### 7.2 发布响应 <a id="publish-result"></a>

| 形态 | 字段 |
| --- | --- |
| 普通发布 | `{message_id, log_id, topic, partition, offset, deliver_at: null}` |
| 延迟发布 | `{message_id, log_id, topic, partition, offset: null, deliver_at}` |

`offset` 放宽为可空是本次唯一的**契约破坏性变更**（字段从必填变可空）。影响面：只在「读 offset 做后续操作」的客户端；
延迟发布本就没有 offset，普通发布行为与字段完全不变。

### 7.3 待投视图 <a id="admin"></a>

`GET /api/v1/msg/admin/delayed`，权限 `msg:query`：

| 参数 | 说明 |
| --- | --- |
| `namespace` / `topic` / `partition` / `level` | 过滤（给定时同样走合法性校验，非法 `350010`） |
| `page` / `size` | 分页（`size <= 100`，与 `/admin/topics`、`/admin/groups` 同构） |

响应：`items[]`（`log_id`、`message_id`、`namespace`、`topic`、`partition`、`level`、`deliver_at`、`remaining_ms`）+ `total` + `page` + `size`。
排序：`deliver_at` 升序（最急的在前）。**只读**：不做改期 / 取消 / 删除。

### 7.4 错误码 <a id="errors"></a>

## 8. 代码设计 <a id="code"></a>

### 8.1 模块职责 <a id="modules"></a>

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `broker/delay.py` | 延迟记录模型、`DelayStore` 端口 + 内存实现、发布侧 `DelayService`、只读 `DelayInspector` | `router` / `log` |
| `broker/scheduler.py` | `DelayWheel`（分层分桶）、`DelayScheduler`（推进 / 转投 / 生命周期） | `delay` / `log` |
| `api/data/messages.py` | `publish` 分派（延迟走 `DelayService`）、惰性启动推进器 | 两个新模块 |
| `api/admin/delayed.py` | 只读待投列表 | `delay` |

> 概要设计把延迟归 `broker/delay.py` 一个模块；本设计拆出 `scheduler.py`，理由是**推进器有独立生命周期**（任务启停、时钟、限速），
> 与「模型 + 端口 + 服务」混在一起会让单文件过 500 行且难以单测。已在概要设计模块表回写（§13）。

### 8.2 `DelayStore` 端口 <a id="port"></a>

```python
class DelayStore(ABC):
    async def enqueue(self, record: DelayRecord) -> None: ...
    async def count_for_tenant(self, *, tenant_id: int) -> int: ...
    async def list_for_tenant(self, *, tenant_id: int) -> ConcurrentStableList[DelayRecord]: ...
    async def list_all(self) -> ConcurrentStableList[DelayRecord]: ...   # B 段重建索引入口
    async def remove(self, *, log_id: str) -> None: ...
```

端口只有「存 / 数 / 列 / 删」四类语义，**不含时间轮**：轮是索引实现细节，8B_02 换文件实现时用 `list_all()` 重建，端口签名不变。

### 8.3 `DelayService`（发布侧） <a id="service"></a>

```python
async def publish(self, *, tenant: CurrentTenant, request: PublishRequest) -> DelayedOrder
```

顺序：`ensure_namespace` → 主题解析（`350001`）→ 分区锁定（`route`）→ 档位映射 → **配额检查**（`350015`）→ 生成 `message_id` / `log_id`
→ `enqueue` → `wheel.place` → 返回 `(message_id, log_id, partition_no, deliver_at)`。

配额检查放在「解析主题之后、生成 ID 之前」：先做无效请求的全部拒绝，再谈容量，避免「档位非法」被容量错误盖住。

### 8.4 `DelayScheduler`（推进侧） <a id="scheduler"></a>

```python
class DelayScheduler:
    def __init__(self, *, store, messages, wheel, now=_utcnow, interval_ms=DELAY_TICK_MS) -> None
    async def run_once(self) -> int          # 单步：取候选 → 转投 → 清记录；返回本轮转投条数
    def ensure_started(self) -> None         # 幂等；无运行中任务则创建
    async def stop(self) -> None             # 幂等；取消任务并等待退出
```

`run_once` 是**纯步进**（不 sleep、不读真实时钟以外的东西），因此用例可用 `ManualClock` 精确驱动；
`ensure_started` 里的 `asyncio.sleep(interval)` 是唯一真实等待点，用例用 10ms 周期验证生命周期。

### 8.5 `DelayInspector` <a id="inspector"></a>

`list_delayed(tenant, namespace, topic, partition, level, page, size) -> (items, total)`：从 `DelayStore.list_for_tenant` 取全量 → 过滤 → 按
`deliver_at` 升序 → 分页。剩余时间 `remaining_ms = max(0, deliver_at - now)`。只读，不触发转投。

### 8.6 `MessageStore` 端口扩展 <a id="logid"></a>

`StoredMessage.log_id: str`、`append(..., log_id: str)`。调用方三处：普通发布（新生成）、延迟转投（沿用）、重放（新生成，01-6）。
**端口扩展的论证在架构 04 §2.2**：不用 `message_id` 做记录级去重，因为重放会合法产生同 `message_id` 的多条记录。

### 8.7 装配与登记 <a id="assembly"></a>

`configure_service()` 注入 `app.state.delay_store` / `app.state.delay_scheduler`（进程级单例，与消息 / 位点 / 死信 / 组同构）；
`api/deps.py` 增 `DelayStoreDep` / `DelaySchedulerDep`；`api/router.py` 登记 `admin/delayed.router`。

### 9.2 覆盖与门禁 <a id="coverage"></a>

- 变更模块行 + 分支覆盖率 **100%**（`bms_msg` / `services.module_registry` / `services.table_registry`）。
- 覆盖难点与对策：**前跳/回拨/批上限/失败重试**四个分支各有一条专门用例（#11~#15），不靠"跑主路径碰运气"；
  L2 桶与跨度上限分支由端口级直接入队触发（#6 / #7），不依赖档位表（档位最长 60m，正常链路走不到 L2）。
- 不可达分支一律删除，不用 `pragma: no cover`。

## 12. 风险与开放项 <a id="risk"></a>

| # | 风险 / 开放项 | 处置 |
| --- | --- | --- |
| 1 | 延迟区不落盘，重启即空（与消息 / 位点 / 组同状） | 已标注归 8B_02（需求 02-7）；本任务不承诺 |
| 2 | 惰性启动意味着「从未发布过延迟消息的进程不起推进任务」 | 无延迟消息即无需推进；首个延迟发布必触发，不构成功能缺口 |
| 3 | 基座 `service_lifespan` 无产品启动钩子 | 惰性启动兜底；显式注册归 8B_01（进程级任务生命周期） |
| 4 | 单进程推进，多副本会各自转投同一分区 | 首期 `workers = 1`；多副本由 8B_05 单写者 / fencing 收敛 |
| 5 | 配额按租户计数需一次全量扫描（内存实现） | 全量在进程内、条数有上限（10 万），可接受；8B_02 换索引计数 |
| 6 | 转投无上限重试，可能长期卡在失败主题 | 指标 + 告警（06 域）；不做丢弃（延迟是兜底通道） |

## 13. 对齐记录 <a id="align"></a>

| 项 | 原表述 | 本设计 | 理由 |
| --- | --- | --- | --- |
| 延迟标识 | 需求 / 架构写 `delay_id` | 统一为 **`log_id`** | 延迟记录与到期后的日志记录是同一条记录身份，第三个 ID 只会让去重与排障多一次映射；需求 / 架构 / 任务文档已同步改写 |
| `PublishResult.offset` | 必填 `int` | 可空 `int \| None` | 延迟发布尚未进入 offset 空间；放宽可空对普通发布零影响 |
| 模块拆分 | 概要设计只列 `broker/delay.py` | 拆出 `broker/scheduler.py` | 推进器有独立生命周期（启停 / 时钟 / 限速），混写会让单文件过 500 行且难单测；概要模块表已回写 |
| 单轮批上限 | 架构未定 | 500 条 / 轮 | 防单轮卡死事件循环；重启风暴时形态可控 |
| 跨度上限 | 架构未定 | 86400s（超出 `10001`） | 延迟区不是定时任务系统；超长跨度应由业务用状态机表达 |
