## 1. 概述 <a id="overview"></a>

### 1.1 目标

- 消除「头注释逐条枚举码名」这一**必然漂移**的维护点：码表已由 `deploy/registry/msg.toml` 唯一声明、由 `tests/test_error_codes.py` 与枚举逐条对账；
- 消除 `350022` 的**可重试语义矛盾**：一处说「退避无用」、一处说 `retryable=true`。

### 1.2 现状核对

| # | 现状 | 处置 |
| --- | --- | --- |
| 1 | 头注释枚举 28 个码名，枚举实际 34 个（缺 `350027/350029/350030/350031/350034`） | 删除逐条枚举，改为「码表以 registry 为唯一声明 + 用例对账」；保留段位口径、判定顺序、启用来源三段 |
| 2 | `MsgStorageWatermarkError` docstring：「必须停止发布并介入清理，退避重试无用」 + 同段「`retryable=true`」 | 统一为「清理 / 扩容完成前退避不会成功；`retryable=true` 只表示恢复后可重试，客户端应停止高频发布并告警」 |
| 3 | `api/frame/responses.py::_RETRYABLE_SYSTEM` 注释：「（清理 / 扩容后即可恢复）」 | 与上条同口径（措辞统一） |
| 4 | `deploy/registry/msg.toml` 的 `350022` description | 同步为同一口径 |

## 4. 口径定稿（`350022`） <a id="watermark"></a>

| 维度 | 结论 |
| --- | --- |
| 语义 | 存储水位拒绝（卷使用率超拒绝阈值 / 数据卷不可用），HTTP **507** |
| 分层 | `system`（基础设施容量问题，不是请求本身的错） |
| `retryable` | **true**：清理 / 扩容完成后可恢复，客户端可退避重试 |
| **但** | 清理 / 扩容完成前退避重试**不会成功**——客户端应停止高频发布并告警，而不是无脑重试 |
| 与相邻码分工 | `350005` 生产限流（退避可解）、`350015` 延迟区满（档位问题）、`350032` ISR 不足（等副本） |
