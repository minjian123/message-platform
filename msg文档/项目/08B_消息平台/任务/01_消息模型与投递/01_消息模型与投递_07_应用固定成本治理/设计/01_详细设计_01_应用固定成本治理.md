# 应用固定成本治理详细设计

> 主题元数据缓存（进程内快照 + 写时精确失效）× 保留清理时间节流（每窗口每分区一次）× 语义零变更

## 1. 概述 <a id="overview"></a>

### 1.1 目标

把每条数据面请求都要付的**固定成本**（与载荷大小无关的那部分）压下来，让传输与序列化的优化重新可被度量：

1. **主题元数据缓存**：主题解析结果（分区数 / 保留配置 / 状态 / 租户归属）放进进程内缓存，`publish` / `consume` / `ack` / `nack` / `subscribe` 共用同一份；主题增删改经**同一处失效**。
2. **保留清理时间节流**：`apply_retention()` 由「每请求一次」改为「每窗口每（主题, 分区）最多一次」；触发点仍是请求驱动。
3. **语义绝对不变**：保留判定、位点推进、顺序停等、错误码、审计留痕一行不改；缓存冷热两态响应**逐字段一致**。

三条不可动摇的边界：

1. **会话口径不动**（任务 §2 第 3 条）：每请求一次短会话保留，不得顺手改连接复用或池参数。固定成本里「开一次会话」这一项本任务不碰——它是连接池治理，与元数据查询不是同一件事。
2. **不提前实现后台清理**（8B_02 的 02-1 / 02-2）：本任务只交请求驱动的节流窗口，且该窗口日后可被后台清理复用为采样窗口。
3. **单实例语义**（跨实例归 8B_05）：缓存失效是**进程内**的，多副本 / 多实例一致性不在本任务裁定范围。

### 1.2 判据来源（为什么只做「相对判据」）

03-1 的分层测量证明该基准装置在 16 并发下已经跑满（`吞吐 × 延迟 ≈ 并发数`，即 `p50 ≈ 并发数 × 单请求服务时间`）：publish 档 p50 280.3ms、`/msg/connection` 档 p50 52.4ms，差值 227.9ms ÷ 16 ≈ **14.2ms**，与另一条路径测得的「固定成本 ≈17ms/请求」同量级。

于是本任务的验收判据只能是**两档差值**，且必须写明并发——因为：

| 并发 | p50 的含义 | 「差值 ≤5ms」要求什么 |
| --- | --- | --- |
| 16（03-1 原参数） | ≈16 × 单请求服务时间 | 单请求固定成本降到 **0.3ms**（做不到，且与设计本意不符） |
| 1 | 就是单请求服务时间 | 固定成本差从 ≈14ms 降到 ≤5ms（有实际含义、可归因） |

**定稿**：`concurrency=1` 为主判据，`concurrency=16` 作参考值（同参数复跑，只记录不裁定）。判据只说明「固定成本已降到与载荷处理同量级」，**不作容量结论**（容量归 8B_12）。

### 1.3 现状与差距 <a id="gap"></a>

一条请求里主题解析不是一次，而是 2~3 次（同一会话、每次一条 `SELECT ... WHERE tenant_id = ? AND namespace = ? AND name = ?`）：

| 端点 | 解析次数 | 位置 |
| --- | --- | --- |
| `/msg/publish` | 2 | `apply_retention` → `DeliveryService.publish` |
| `/msg/consume` | 3 | `apply_retention` → `GroupCoordinator.ensure_owner`（成员制）→ `DeliveryService.consume` |
| `/msg/ack`、`/msg/nack` | 2 | `ensure_member` → `DeliveryService.ack/nack` |
| `/msg/join` | 1 | `GroupCoordinator.join` |
| `/msg/subscribe` | 预检 2 + 每轮 2~3 | `_preflight`（清理 + 成员制）；每轮 `_pull`（成员制 + 拉取） |

保留清理则是**每请求一次**扫描（`RetentionService.apply` 读段元数据 + 起点 + LEO 并按分区判定），`subscribe` 在预检时扫一次。

差距不在「某一次查询慢」，而在「同一条请求把同一份元数据反复问了三遍、把同一次清理反复算了两遍」。

## 3. 主题元数据缓存 <a id="cache"></a>

### 3.1 缓存的是「值快照」，不是 ORM 实例 <a id="snapshot"></a>

`TopicRouter.resolve()` 现返回 ORM 实例 `MsgTopic`。缓存**不能**存它：

- 请求结束会话关闭后读属性会触发懒加载 → `MissingGreenlet`（本仓已踩过同类）；
- 同一 ORM 实例被并发请求的多个会话共享，会话边界与身份映射都会打架。

因此新增不可变值对象，字段与 `MsgTopic` 对齐（**只取判定需要用到的列**，不留关系字段）：

```python
@dataclass(frozen=True)
class TopicSnapshot(BaseValueObject):
    id: int
    tenant_id: int
    namespace: str
    name: str
    partition_count: int
    retention_ms: int
    retention_bytes: int
    cleanup_policy: str
    status: str
    loaded_at_ms: int          # 载入时刻（epoch ms）：日志与 8B_05 的跨实例失效协议预留

    @classmethod
    def from_topic(cls, topic: MsgTopic, *, loaded_at_ms: int) -> "TopicSnapshot": ...
```

`resolve()` 命中与未命中**返回同一类型**，因此「冷热两态逐字段一致」不是靠用例碰运气，而是结构上只有一条路径能产出返回值。`partition()` / `route()` 只读 `partition_count`，改注解即可。

### 3.2 载体与键 <a id="carrier"></a>

| 项 | 定稿 | 理由 |
| --- | --- | --- |
| 载体 | 进程内 `dict`（`TopicCache`，`app.state.topic_cache` 单例） | 单实例语义最干净；跨实例失效在 8B_05 加协议层，不动本层接口 |
| 键 | `(tenant_id, namespace, name)` | 与唯一键同构；平台库共库多租户，键不带租户即越权 |
| 值 | `TopicSnapshot` | 见 §3.1 |
| 失效 | 按键**精确删除**（不做全清） | 命中零比较成本；不存在「全清后重建风暴」 |
| 负结果 | **不缓存** | 新建 / 恢复启用后第一请求即可用；无需 TTL 机制 |
| TTL | **不加** | 加了就是「最迟 TTL 才生效」，与任务 §3「下一次请求即生效」冲突 |
| 并发 | 不加锁 | `get` / `put` / `invalidate` 全程无 `await`，在单事件循环内原子；多 worker 各持一份（见 §3.5） |

### 3.3 失效点：`TopicService` 写方法内收口 <a id="invalidate"></a>

| 写入口 | 现状 | 本任务 |
| --- | --- | --- |
| `create_topic` | 建主题 + N 条分区（同事务） | 提交后 `invalidate(tenant_id, namespace, name)` |
| `expand_partitions` | 追加分区 + 改 `partition_count`（同事务） | 提交后 `invalidate(...)`（用返回值里的 `namespace` / `name`） |
| 保留配置变更 / 停用 / 删除 | **端点尚无**（归 06 域 06-2） | 不补端点；写成硬约束 |

三条硬约束：

1. **失效必须在提交成功之后**——事务回滚时缓存里的旧值与库一致，不该被清；提交成功才让下一次请求重新载入。
2. **06 域将来的 update / disable / delete 必须经 `TopicService` 写方法**（01-1「主题增删改唯一入口」的延伸）。端点层不得直接 `repo.update(...)` 后自己失效——那正是「改了配置仍按旧值投递」的来源。
3. **禁止绕过服务层直改库**（运维脚本 / 手工 SQL / 用例改 `status`）：本任务不加 TTL，直改库不会触发失效。这条登记为遗留，与跨实例一致性一并归 8B_05。

### 3.4 停用 / 删除的生效时序 <a id="status"></a>

`resolve()` 的判定语句一行不改，只是数据来源可能来自缓存：

```
resolve() → 查缓存（命中即用快照 / 未命中查库并回填）→ status != active → 350001
```

因此停用后：写入口失效 → **下一次请求** `resolve` 未命中 → 查库拿到 `disabled` → `350001`。错误码、抛出位置（仍在 `apply_retention` 的第一步、清理之前）与现状一致；不存在「窗口内旧值仍可收发」的区间。

### 3.5 多实例 / 多副本边界 <a id="multi"></a>

本任务只保证**单实例**语义，且这一条是可验证的：多 worker 时每个进程各持一份缓存，A 进程的写不会失效 B 进程的副本。

- 量化边界：失效滞后有一个上界——「B 进程下一次请求」即读到旧值，直到 B 自己的某个写入口触发失效或进程重启；**没有 TTL 兜底**。
- 归口：8B_05（跨实例一致性）。届时在快照上已有的 `loaded_at_ms` 之外加 generation/广播，`TopicCache` 接口（`get` / `put` / `invalidate`）不变。
- 现有部署 `workers = 1`（与 01-6 重放执行器同口径），故本阶段不构成实际问题。

## 4. 保留清理节流 <a id="throttle"></a>

### 4.1 窗口形态与取值 <a id="window"></a>

| 项 | 定稿 | 理由 |
| --- | --- | --- |
| 形态 | 固定时间片：`window = now_ms // W`，每键只存当前窗口序号 | 判定是一次整数比较，无「上次时刻」表；跨片边界可紧邻两次扫描（999ms 与 1001ms），保留期以天计，这点偏差无意义 |
| 取值 | `RETENTION_SCAN_WINDOW_MS = 1000`（1s） | 清理频率降低三个数量级已足够；取 5s / 30s 只会同比拉长「位点早于起点 → `350003`」与清理生效的时延，时序语义偏移更大 |
| 落点 | `core/config.py`（与 `RETENTION_SEGMENT_RECORDS` 同处） | 基座 `Settings` 为 `extra="forbid"`，窗口只能作模块常量（同 01-2 / 01-5 的约束） |
| 首请求 | **到达即扫**，同时记下窗口序号 | 与现状（每请求都扫）语义最接近；重启后第一请求就会清理，用例「一次请求 = 一次扫描」可读 |

### 4.2 键粒度：`(topic_id, partition_no)` <a id="key"></a>

清理本来就**按分区**执行（`RetentionService.apply` 只处理一个分区，`partition_no` 来自 `consume.partition` 或 `publish` 的 `key` 路由结果）。因此：

- 按 `(topic_id, partition_no)` 分键 → 与现语义完全等价，只是把「每请求一次」收敛为「每窗口每分区一次」；
- 按 `topic_id` 分键（首分区触发全主题扫描）→ 要么改变扫描范围（语义变化），要么让单请求耗时随分区数上升（与治理目标相反）。

**判据措辞随之修正**：任务 §3 与需求 01-7 的「同一窗口内对同一**主题**最多执行一次」改为「同一窗口内对同一**（主题, 分区）**最多执行一次」。多分区主题在同一窗口内每分区各扫一次——总量仍是「分区数 / 窗口」，与「主题数 / 窗口」只差一个与治理无关的常数因子。

### 4.3 判定实现 <a id="admit"></a>

```python
class RetentionThrottle:
    """请求驱动清理的窗口表（进程级；无 await，单事件循环内原子）。"""

    def __init__(self, *, window_ms: int = RETENTION_SCAN_WINDOW_MS,
                 clock: Callable[[], float] = _monotonic_ms) -> None: ...

    def admit(self, *, topic_id: int, partition_no: int) -> bool:
        """本窗口内该（主题, 分区）是否轮到扫描；首个到达的请求返回 True。"""
```

`apply_retention` 的落点（**清理之前**，不影响返回的 `(topic_id, partition_no)`）：

```python
if throttle.admit(topic_id=int(resolved.id), partition_no=target):
    outcome = await RetentionService(store=store).apply(...)   # 判定逻辑一行不改
```

`admit` 是纯内存判定、`RetentionService.apply` 是唯一副作用，两者顺序固定，没有「先扫后登记」的窗口。

### 4.4 与 8B_02 后台清理的衔接 <a id="background"></a>

| 项 | 定稿 |
| --- | --- |
| 常量 | 共用 `RETENTION_SCAN_WINDOW_MS`，后台清理以它为**采样窗口**（不另定第二份数值） |
| 键表 | **各自独立**：请求驱动持 `RetentionThrottle`，后台清理自持自己的游标 |
| 为什么不能共享 | 请求会把主题「占」掉窗口，后台到点一看「本窗口已扫过」就跳过——正好把该扫的漏掉；两种驱动的语义（增量触发 / 全量巡检）本就不是一件事 |
| 本任务不做 | 后台定时器、循环、生命周期钩子一律不引入 |

### 4.5 内存与失效 <a id="throttle-memory"></a>

窗口表条目是 `(int,int) → int`，量级是「主题数 × 分区数」，每条约几十字节；不做淘汰（`RETENTION_SEGMENT_RECORDS` 同理不做）。`partition_count` 只增不减，因此键集合只增不减——已登记为遗留，8B_02 引入后台清理时随「键表生命周期」一起处置。

### 5.2 接线点 <a id="wiring"></a>

| 位置 | 改动 |
| --- | --- |
| `api/data/messages.py::apply_retention` | 接 `cache`（传给 `TopicRouter`）+ `throttle`（清理判定） |
| `api/data/messages.py::delivery_service` / `_delay_service` / `ensure_member` | 组装 `TopicRouter` 时传 `cache` 与 `tenant_id` |
| `api/data/messages.py` 四个端点 | 追加 `TopicCacheDep` / `RetentionThrottleDep` 两个参数并下传 |
| `api/data/groups.py::join` | 同上（`_coordinator` 传 `cache` / `tenant_id`） |
| `api/frame/routes.py::_preflight` / `_pull` / `_resolve_ids` / `_stream_core` | 同上（长驻流预检与每轮拉取共用同一份缓存） |
| `api/admin/topics.py::_service` | 传 `cache`——**只用于写路径失效**；读路径本来就不经缓存（管理面读库最新） |
| `services/topic.py` | `TopicService(topics, partitions, uow, *, cache=None)`；两个写方法提交后失效 |

`TopicRouter` 的构造签名：

```python
def __init__(self, topics: TopicRepository, *, cache: TopicCache | None = None,
             tenant_id: int | None = None) -> None:
```

`cache` 与 `tenant_id` 必须**同时给或同时不给**（只给 cache 时抛 `ValueError`）——键里没有租户就是跨租户取到别人的主题，属越权，必须当场拒绝而不是默默降级。

`cache=None` 的语义是**不缓存、直接查库**（与现状完全一致），供未装配的直调方与管理面使用；生产装配点全部传值。

`RetentionService` 的判定与容量补删 · `DeliveryState` 的 inflight 账 · `NotifyingMessageStore` 的写入即唤醒 · `_collect` 的停等规则 · 每请求一次短会话 · 连接 / 池参数 · 契约快照 · 错误码表与文案。

## 6. 语义等价论证 <a id="equivalence"></a>

| 面 | 论证 |
| --- | --- |
| 响应结构 | 缓存只改变 `resolve()` 的数据来源，`MessageItem` / `PublishResult` / `ConsumeResult` / `AckResult` / `NackResult` 的字段装配一行未改；冷热两态走的是同一条装配代码 |
| 错误码 | 判定语句与顺序不变：命名空间 `350010` → 主题 `350001` → 分区号 `350009` → 清理；节流发生在判定之后，因此非法请求的报错路径与现状逐条一致 |
| 位点与停等 | 清理只前移 `start_offset`（`truncate_before`），不碰 LEO 与位点；节流只改「多久跑一次」，每次执行的判定与副作用不变 |
| 审计 | 数据面无审计埋点；清理不写审计（01-6 口径）。本任务零新增审计事件 |
| 延迟发布 | `publish` 的延迟分支不跑清理（现状如此），本次只把缓存接进 `_delay_service` 的主题解析 |
| 长驻流 | 预检仍先清理再校验成员；节流只影响「本次预检是否真的扫」，返回的 `(topic_id, partition_no)` 不变 |

唯一可观察的差别是**时序**：清理最多滞后一个窗口（≤1s），以及 `350003` 的出现时延同比滞后（保留期以天计，不构成业务可见差异）。这一条写进测试记录，属实。

## 7. 可观测 <a id="observe"></a>

只出结构化日志（指标与面板归 06 域），字段口径固定：

| 事件 | 触发点 | 字段 |
| --- | --- | --- |
| `msg_topic_cache` | `TopicRouter.resolve` | `outcome`（`hit` / `miss`）、`tenant_id`、`namespace`、`topic`、`elapsed_ms`（miss 只计查库耗时） |
| `msg_topic_cache` | `TopicService` 写方法 | `outcome=invalidate`、`tenant_id`、`namespace`、`topic` |
| `msg_retention` | `apply_retention` | `outcome`（`applied` / `throttled`）、`topic_id`、`partition`、`deleted_segments`、`elapsed_ms` |

`elapsed_ms` 取 `time.perf_counter()` 差，供 8B_12 直接从日志取分布；不新建 collector（无消费方，属提前实现）。

## 11. 风险与开放项 <a id="risk"></a>

| # | 项 | 处置 |
| --- | --- | --- |
| 1 | 直改库（`status` / `retention_*`）不触发失效 | 不加 TTL 的既定代价；写成硬约束，跨实例与直改库一致归 8B_05 |
| 2 | 多 worker 各持一份缓存，写不跨进程失效 | 本任务只保证单实例；现有部署 `workers = 1`；归 8B_05 |
| 3 | 窗口键表只增不减 | 条目为小整数对，量级 = 主题数 × 分区数；8B_02 引入后台清理时一并处置 |
| 4 | 清理最多滞后一个窗口 | 保留期以天计；`350003` 出现时延同比滞后，写进测试记录 |
| 5 | 16 并发下判据不可达（0.3ms） | 已改为 `concurrency=1` 主判据；16 并发只作参考值并注明换算 |
| 6 | 缓存命中率低时治理无效（主题极多、请求极散） | 命中率由 `msg_topic_cache` 日志直接可测；若实测偏低，归因写进测试记录，不调判据 |
| 7 | `resolve()` 返回类型变更影响 8 处调用点 | 属性名保持一致（`id` / `namespace` / `name` / `partition_count` / `retention_ms` / `retention_bytes` / `status`），改动为机械替换；`MsgTopic` 专属字段无人使用（已核对） |

## 12. 决策确认与对齐记录 <a id="align"></a>

### 12.1 已确认决策（16 项） <a id="decisions"></a>

| # | 事项 | 定稿 | 主要理由 |
| --- | --- | --- | --- |
| 1 | 缓存载体 | 进程内 `dict`，键 `(tenant_id, namespace, name)` → 不可变快照；精确失效 | 命中零比较；8B_05 只在协议层扩展 |
| 2 | 解析返回类型 | 统一 `TopicSnapshot` | 冷热两态同型，等价性由结构保证；避免 ORM 脱离会话 |
| 3 | 接入面 | `TopicRouter(topics, *, cache=None, tenant_id=None)` | 改动最小；换实现只换 cache 对象 |
| 4 | 失效点 | `TopicService` 写方法内收口 | 与 01-1「唯一入口」一致，新增端点自然继承 |
| 5 | TTL | 不加 | 「下一次请求即生效」严格成立，无时间不确定性 |
| 6 | 负结果 | 不缓存 | 新建 / 恢复后第一请求即可用 |
| 7 | 停用时序 | 写入口失效，下一请求即判 `350001`（仍在清理之前） | 与现状错误码、时序一致 |
| 8 | 节流键 | `(topic_id, partition_no)` | 清理本就按分区；按主题分键会改扫描范围 |
| 9 | 窗口 | 固定时间片 1s，只存窗口序号 | 判定一次比较；边界连扫对天级保留期无意义 |
| 10 | 首请求 | 到达即扫并登记 | 与现状最接近，用例可读 |
| 11 | 与 02-1 衔接 | 同一常量、两条路径各自独立键表 | 共享键表会让请求「占」掉窗口、后台漏扫 |
| 12 | 可观测 | 只出结构化日志（两类事件） | 零新增模块；指标面板归 06 域 |
| 13 | 验收并发 | `concurrency=1` 主判据，16 只作参考 | 16 并发下 p50 ≈ 16 × 服务时间，5ms 阈值失去含义 |
| 14 | 验收方式 | 复跑同一脚本前后对比 | 能回答「降了多少」，也是 8B_12 的回归接入点 |
| 15 | 记录落点 | 本任务新建 `实施/`、`测试/` | 与 01-1 ~ 03-5 同构；基准节交叉引用 03-1 |
| 16 | 保留配置端点 | 不新增（归 06-2），只预留失效收口 | 不并任务、不改序，契约零变更 |

### 12.2 口径回写 <a id="diff"></a>

| # | 项 | 原表述 | 本设计 | 理由 |
| --- | --- | --- | --- | --- |
| 1 | 节流粒度判据 | 任务 §3 / 需求 01-7：「同一窗口内对同一**主题**最多一次」 | 同一窗口内对同一**（主题, 分区）**最多一次 | 清理本就按分区执行；按主题分键要么改扫描范围、要么让单请求耗时随分区数上升 |
| 2 | 清理触发描述 | 01-6 详细设计 §4.4：「两个入口各调一次」 | 补「01-7 起改为每窗口每分区最多一次，判定逻辑不变」 | 触发频率变了，判定没变；不补会让后续读者按旧频率理解 |
| 3 | 判据措辞 | 任务 §3 / 需求：「同一实例同一并发下」 | 明确并发取 1（16 作参考） | 03-1 已实证 16 并发下装置跑满，p50 随并发线性放大，阈值含义随并发而变 |
