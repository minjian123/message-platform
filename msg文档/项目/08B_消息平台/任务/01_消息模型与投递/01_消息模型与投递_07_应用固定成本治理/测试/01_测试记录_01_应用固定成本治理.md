### 4.2 结果（并发 1，HTTP/1.1）

| 轮次 | publish p50 | connection p50 | **两档差值** |
| --- | --- | --- | --- |
| 治理前 R1 | 12.47 ms | 4.36 ms | 8.11 ms |
| 治理前 R2 | 16.63 ms | 2.22 ms | 14.41 ms |
| 治理后 R1 | **3.92 ms** | 2.26 ms | **1.66 ms** |
| 治理后 R2 | **3.88 ms** | 2.22 ms | **1.66 ms** |

吞吐（publish 档，同参数）：治理前 72.8 / 57.1 条/s → 治理后 **240.0 / 238.6 条/s**。

### 4.3 判读（写进结论的四条）

1. **判据达成**：治理后两轮差值都是 **1.66 ms ≤ 5 ms**；治理前两轮 8.11 / 14.41 ms 均超阈。
   治理后两轮几乎重合（3.92 / 3.88），说明这个量级已经稳定，不是偶然一次。
2. **降幅来自应用固定成本，不是传输**：`/msg/connection` 档前后基本不变（2.22 ~ 4.36ms，波动来自机器），
   变的是 publish 档——一次请求里 2~3 次主题解析收敛为「首次查库、其余命中」，保留清理从「每请求一次」
   收敛为「每窗口每分区一次」。差值从 ~8~14ms 掉到 1.66ms，与这两项节省的查询 / 扫描量吻合。
3. **差值 1.66ms 已是可测量的下限**：connection 档本身就是一次完整 HTTP 往返，publish 档多出来的
   只剩「一次会话 + 一次元数据读 + 一次投递」这部分真实工作量。继续压需要动会话口径（本任务明令不动）。
4. **16 并发只作参考**：治理后同参数一轮 publish p50 **41.04 ms**、352.3 条/s（p99 69.4ms）；
   03-1 治理前同参数为 168.5 ~ 280.3 ms。16 并发下 `p50 ≈ 并发数 × 单请求服务时间`，把它当判据会要求
   固定成本降到 0.3ms（详细设计 §1.2），故不作裁定依据。
