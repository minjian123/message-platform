## 3. 关键实现口径

1. **单实例零变化**：内部端口缺省 0，不监听、不建内部应用；传输仍用进程内实现；`replicas=[]`。
2. **fail-closed**：多实例缺内部端口 / 端点覆盖不全 / 端口与业务端口相同 / 令牌签发者不可用 → 启动失败。
3. **分配单一实现**：建主题、增分区、`ops.rebalance` 共用 `PartitionAssigner`；与 02-4 配置兜底同算法，升级不改既有分配。
4. **迁移先扩后缩**：`replace` 在同一台账行按 `step=expand → shrink` 推进；移除 leader 前先切主；追平判据为「目标在 ISR 且 LEO ≥ leader HW」。
5. **降级不计通过**：`force` / `isr_verified=false` 落 `degraded` 并写原因；状态命令与演练结论都不得写成「通过」。
6. **台账可续跑**：`planned/running/catching_up` 均可被 `apply --resume` 接续；CAS 条件更新 + 版本号防并发。
7. **演练单源扩 `target`**：本机六类 `local`、多实例三类 `docker`；`ops.drill run` 拒绝 docker 场景，`ops.cluster_drill` 只跑三类。
8. **客户端刷新**：`350033` → 读 `metadata_version` / `leader` / `epoch` → 改投；首期只验服务端语义，SDK 归 8B_03。
9. **演练网络**：三实例复用平台网络 `compose_default`（可直连 DB / Redis），**不再自建网络**；`cleanup` 只删自建 `msg-drill-net`，共享网络禁删。断网重连必须 `docker network connect --alias msg-N`——少了别名会让 `MSG_REPLICATION_NODE_ENDPOINTS` 的 `msg-N` 解析失败、复制直接停摆。
10. **建表**：首实例 `BMS_DATABASE__AUTO_CREATE=true`，`msg-2/3` 置 `false` 并 `depends_on: service_healthy`，规避多实例并发 `create_all` 撞表。
11. **镜像与端口**：构建与 compose 共用 `drill/msg:drill-<commit>`，编排注入 `MSG_REGISTRY_IMAGE_PREFIX` / `MSG_TAG`；宿主端口统一 `MSG_CLUSTER_DRILL_PORT_N`。
12. **每轮前置重置 + 每轮新建主题**：上一轮的副本拉取态 / epoch 会残留（产品缺陷，见 §4），先重启三实例回到健康基线；主题用 `drill.replica.probe.<场景>.<时间戳>`，不复用脏主题。
13. **判据采集链**（`chain.py`）：真实 HTTP 发布（`350033` 改投下一实例、`350032` 等待 ISR 回升，轮次间必须留间隔，否则改投预算瞬间烧光）；预热向每个实例各写一轮（副本需被写一次才建拉取态）；分区状态直读平台库（管理面 `GET /admin/topics` 仍 500，见遗留）；ISR 合计按分区取各节点自报最大值（降主节点的旧指标行不再更新，直接求和会误判）。
14. **注入期探针定向**：只写被隔离的那个实例判「是否被拒」，不能用集群任意节点能写来判——隔离旧 leader 后新 leader 仍可写，集群级发布一定成功。
15. **记录证据完整**：集群记录复用 07-6 契约，补 `environment.config_digest`（G2）与 `backup=mode=not_applicable + 理由`（G7）；三份 JSON / Markdown 落任务 `测试/记录/`。

## 4. 演练暴露缺陷及修复

| # | 现象（真机证据） | 根因 | 修复 | 提交 |
| --- | --- | --- | --- | --- |
| 1 | `ops.failover switch` 后 `acks=all` 永久 `350032`：leader 自报 ISR=2，但 `msg_replication_lag_records` 每发一条涨 1，等 3 分钟不收敛 | 升主时 `followers` 进度表仍按「非 leader 副本」构造，原 leader 不在表内，`serve_fetch` 以「follower 不在副本集内」永久 503，ISR 卡死 | `_apply_leader_change` / `apply_switch` 升主时按副本集重建 `followers` 并收敛 ISR，随后由拉取 / 扫描重新扩张；补升主回归用例 | `97d9c40` |
| 2 | 网络分区恢复后 leader 租约永不续期：`lease_expired last_confirmed_ms≈414 s`，只能 `docker restart` 恢复；期间刷新循环无任何异常日志 | 后台拓扑刷新在断网时卡死在一次无上限的 DB 拉取上，整条循环停摆（事件循环本身存活） | 每次分区拉取套 `asyncio.timeout(2s)` + 逐分区异常隔离 + `msg_replication_topology_failed` 告警；断网期租约按预期过期（保留 fencing），恢复后 1s 内自动续约 | `71baca0` |
| 3 | 恢复后各 leader 都报 ISR=3，但演练判「ISR 未回升」 | 指标里降主节点的旧 `msg_isr_size` 行仍在且不再更新，三实例直接求和在 5 附近徘徊 | 判据改为「按分区取各节点最大值再求和」，并只统计当前主题的分区 | `6a7baf9` |
| 4 | 脑裂场景判据 `stale_leader_rejected` 恒为降级，观测不到拒绝 | 注入期探针走集群级发布，新 leader 仍可写，必然成功 | 探针改为定向写被隔离实例（`publish_at`），非 200 即判被拒 | `568c366` |

另登记未修产品缺陷（不在本任务范围）：多实例并发建表撞表、副本需被写一次才建拉取态、无自动选举、管理面 `GET /admin/topics` 500、`switch` 后旧 leader 可能未主动 demote —— 见 §5。
