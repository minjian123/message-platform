## 5. 问题与处置 <a id="issues"></a>

### 5.1 `offset → file_store` 会成环，`PartitionNotBoundError` 下沉到端口模块

位点要在「租户无从解析」时抛与 02-1 同一类错误，但 `file_store.py` 已经 `from bms_msg.broker.offset import OffsetRealigner`，反向导入直接成环（`ImportError` 只在运行期才炸，静态检查发现不了）。

处置：把 `PartitionNotBoundError` 移到 `broker/log.py`（端口模块，两侧都依赖它、它不依赖任何一侧），`file_store.py` 改为导入——`from bms_msg.broker.file_store import PartitionNotBoundError` 仍可用（`__all__` 保留该项），存量用例零改动。

### 5.2 `OffsetTenantLocation` 用 property 而非属性，否则 pyright 判不兼容

最初写成：

```python
class OffsetTenantLocation(Protocol):
    tenant_id: int
```

pyright 报 `PartitionDirectory` 不满足 `OffsetDirectory`：`TopicLocation` 是 frozen dataclass，字段是**只读**的，而 Protocol 声明的是**可写**属性——结构子类型要求可变属性双向可赋值。改成只读 `@property` 后通过。

### 5.3 Protocol 方法体漏 `...` 被 pyright 判「无返回值」

`FlushableOffsetStore.run_once` 的声明只写了 docstring 没写 `...`，pyright 按「函数声明返回 `int` 但无 return」报错。协议方法一律 `...` 收尾（其余几个方法本来就写了，只有这处漏）。

### 5.4 双槽写入顺序在用例里搞反，导致「回退到上一版」断言失败

首版用例打坏**第二槽**的 CRC 期待回退到 3，实际读到 5。原因是 `_write` 把**新值写 slot0、上一版写 slot1**（不是按槽位序号递增），打坏 slot1 坏掉的是上一版。用例改为打坏 slot0。

这条值得记下来：槽的「新旧」由 `seq` 判定，与槽位下标无关；排障时不要按下标猜。

### 5.5 测试访问私有状态触发 pyright `reportPrivateUsage`

`store._entries` / `store._flushing` / `store._write` 在用例里判「脏标记是否保留」「是否在飞」「刷盘实现」。02-2 的做法是 `cast("Any", ...)` 绕开，本任务沿用（`cast("Any", store)._entries[...]`），不为此在实现上加公开面。

另外 `# noqa: SLF001` 是无效指令（本仓 ruff 没启用该规则），被 `RUF100` 判未使用，已删除。

### 5.6 两处存量用例必须适配（不改编号）

| 用例 | 原因 | 处置 |
| --- | --- | --- |
| `test_lifecycle.py`（Kiwi 2420） | `start_background_tasks` 现在要 `app.state.offset_store` 并会拉起刷盘循环 | 加 `_OffsetFlushStub`（记录 ensure/stop/close，`run_once` 恒 0），**不断言 02-3 行为**（偏序断言在 2429 的 O25） |
| `test_skeleton.py`（Kiwi 2414/2416/2417） | 装配冒烟断言 `offset_store` 是内存实现 | 改为 `FileOffsetStore`（这正是本任务的替换目标） |
| `test_registry_consistency.py`（Kiwi 2411） | 提交前预检的**选测**把 `test_entrypoints` / `test_skeleton` 与它排到一起跑，前两者装配后注册表停在「已构建」态，本用例再 `create(None)` 抛 `PluginError: 插件注册表已构建` | 在 `create()` 前补 `default_plugin_registry().reset()`（`test_skeleton` 早有同法）。**这是存量的用例隔离缺陷**，本次因 `main.py` 改动让装配用例进入选测才暴露；不是装配问题 |

### 5.7 覆盖率补口：一条真的不可达分支，用「删重复校验」而不是 pragma

`_entry_for_path` 原本自带 `parse_offset_filename(path.name) is None → return None`，但三个调用方（`list_group` 已过滤、`realign` 用的是自己拼的合法文件名）都不可能在非法文件名上调用它——这条分支永远走不到。

处置：删掉这段重复校验（不是加 `pragma: no cover`）。冗余的防御分支会长期挂着 0 覆盖，删掉比标注更干净。

另一处 `purge_group` 的「删完后目录非空」分支，靠用例里额外放一个非位点文件（`keep.txt`）走到。

### 5.8 覆盖率数据必须是「最终代码 + 清分片」

`engkit coverage` 会合并 `.cache/coverage/` 下的分片。中途改过 `offset.py`（删两行）与用例，若不先 `rm -f .cache/coverage/.coverage.*` 会读到旧行号的数据，表现为「缺行号指向不存在的代码」。每次判定前都先清、再采、再判。
