### 3.1 以 `pragma: no cover` 登记的分支

理由均为「结构上不可达」，逐处带说明：

| 位置 | 分支 | 理由 |
| --- | --- | --- |
| `file_store.py::_PartitionLog.read` | `cursor < segment.base_offset` | 段区间连续覆盖 `[start, leo)`，不存在空隙 |
| `file_store.py::_PartitionLog.locate` | 内层扫描「正常结束」 | `offset` 落在本段区间内时内层必命中并返回 |
| `file_store.py::_PartitionLog.locate` | 末尾 `return None` | 同上：`[start, leo)` 内必落某段且命中 |
| `file_store.py::_PartitionLog.read_range` | `locate is None` 的 break | `cursor < leo` 时 `locate` 必返回 |
| `file_store.py::_PartitionLog.read_bytes` | `_segment_by_path` 返回 None | 同一临界区内段不会消失 |
| `file_store.py::_PartitionLog.iterate_headers` | `current >= end` 的 break | `ends` 与段内条数一致，循环由 `iter_headers` 结束 |
| `segment.py::SegmentFile.iter_headers` | 头字节不足 | `read_frame` 已保证 `total >= 12 + header_len`，框架可读则头必可读 |

## 5. 问题与偏差 <a id="issues"></a>

| # | 项 | 处置 |
| --- | --- | --- |
| 1 | 首轮 `test_file_store` 全线失败：每条记录落盘多 1 字节 | **Windows 文本模式**导致 `0x0A` → `0x0D 0x0A`；写入标志补 `O_BINARY` 后全绿（详见实施记录 §5.1） |
| 2 | 契约套件断言「向下取整到段边界」在内存实现上不成立 | 该断言移出契约套件（违约行为不作契约），改由 F20 只验文件实现（实施记录 §5.2） |
| 3 | 覆盖率首轮 63.66%，且报「docstring 行未覆盖」 | 判定用的是旧采集数据（行号错位）；改为「最终代码单进程采集 + 绝对路径数据文件」后回到真实值 |
| 4 | `test_skeleton` 断言装配内层为内存实现 | 装配事实已变，改为 `FileMessageStore` 并补 `partition_directory` 断言 |
| 5 | 时间索引条目在密集写入下接近「每条一条」 | 体积占比仍约 2.7%（12,000 / 447,780），满足「显著小于数据」；若将来 payload 极小导致占比上升，再引入时间索引的条数间隔（接口不变） |

## 6. 遗留 <a id="leftovers"></a>

见实施记录 §7（14 项）。与测试直接相关的三条：

1. **CRC 校验用例归 02-2**：本任务只验「结构级截断」，伪造 CRC 不符但长度合法的记录在当前实现视为结构完整（读取期才抛错）。
2. **多副本 / 多 worker 一致性无对应用例**：目录登记表与 `log_id` LRU 是进程内状态，归 8B_05。
3. **`log_id` 冷查询性能未压测**：只断言「未命中扫段能命中」，扫段次数量级由 `msg_log_id_scan` 日志观测，容量结论归平台级容量实测。
