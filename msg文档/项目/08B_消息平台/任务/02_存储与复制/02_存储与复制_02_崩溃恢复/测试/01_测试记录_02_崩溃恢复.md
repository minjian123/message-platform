### 3.1 以 `pragma: no cover` 登记的分支

| 位置 | 分支 | 理由 |
| --- | --- | --- |
| `segment.py::scan_tail` → `_read_header` | 记录体读不满 | 循环已保证 `position + total ≤ size`；同一临界区内不会并发截断 |
| `segment.py::_read_header` | 头字节不足 | `read_frame` 已保证 `total ≥ 12 + header_len` |
| `segment.py::last_record_stamp` | 坏框架 / 声明超长 | 恢复已把末段修到完整，写入期段尾必然完整 |
| `segment.py::isolate_tail` | 短读 | `seek` 与 `size` 一致，读不满只可能是并发截断 |

其余分支（含对账的三种损坏、恢复点的四类不可用、尾随计数的两个 break）全部由用例覆盖，未用 `pragma` 掩盖。

## 4. 实测数据 <a id="measure"></a>

**恢复读取量**（3 段、每段 1 条 150 字节载荷、`each` 档、关闭后带探针重开）：

| 项 | 字节 |
| --- | --- |
| 三段日志合计 | 1,125 |
| 恢复读取合计 | **750** |
| 构成 | 两个非末段各读一条记录（对账）；末段扫描起点在文件尾 → 读 0 |

> 这是「每段一条记录」的极端构造，用来把对账成本占比放大到可见；正常 64 MiB 段下对账读 2 条记录约数百字节。

**截断取证**：尾部追加 4 字节半条记录 → 截断到上一条完整记录，取证文件大小 **4 字节**，`truncated_bytes` = 截断后段大小。

**位点回退**：已提交 5（组 g-1）/ 1（组 g-2），截断后 LEO=2 → g-1 夹到 **2**，g-2 保持 **1**（只夹越界那条，不整组归零）。

**索引残条**：追加 4 字节残条 → 加载后文件从 28 字节回到 **24 字节**（`index_repair_bytes=4`），后续追加定位仍命中。

## 6. 遗留 <a id="leftovers"></a>

见实施记录 §7（15 项）。与测试直接相关的三条：

1. **跨重启的位点回退无用例**：内存位点重启即清空，本任务只验「同进程内被夹住」与「协议被调用」；跨重启由 02-3 的文件实现承接，调用链不变。
2. **多 worker / 多实例无对应用例**：恢复点、段损坏标记均为单进程语义，归 8B_05。
3. **`each` 档写恢复点的性能未压测**：只验证正确性（R1 / R18），代价归平台级容量实测。
