## 1. 概述 <a id="overview"></a>

### 1.1 目标

把 02-1 留下的「length 级结构判定」升级为**真正的崩溃恢复**：只扫尾部、按 CRC 判真伪、截断留证、补建索引、对账非末段、回退越界位点、停机刷盘。

1. **恢复点**：每分区一个 `recovery-point.json`，记 LEO、段清单与每段末条 CRC；临时文件 + rename 原子替换；缺失 / 损坏退回推导，版本过高拒绝加载。
2. **尾部扫描**：从「恢复点末段 size」与「最后索引项位置」的较大者起扫，逐条校验 `length` + `crc`；遇坏记录截断，并把被截字节另存取证。
3. **索引**：修残条（崩溃可能留半条条目，会让后续条目整体错位）+ 补建尾部区间内缺失的条目。
4. **非末段对账**：按恢复点的段清单逐段 O(1) 校验（size + 末条 CRC），不符只标记并告警，不改文件、不阻塞启动。
5. **位点对齐**：独立协议承接「已提交位点超过新 LEO 就回退并告警」，内存位点实现夹取，02-3 的文件实现只需实现同一协议。
6. **优雅关闭**：`FileMessageStore.aclose()` 注册进 `ResourceManager`，逆序释放得到「先停后台循环、后刷日志」；关闭时无条件 fsync 并写恢复点。

## 2. 现状与差距 <a id="gap"></a>

| 能力 | 02-1 现状 | 本任务 |
| --- | --- | --- |
| 尾部扫描 | `SegmentFile.scan_tail()` 只判 `length` 与文件边界 | 加 `verify_crc` 与 `anchor` 参数，返回坏记录位置 / 尾随记录数 / 末条 CRC |
| 截断 | `truncate(size, max_relative_offset)` 直接丢弃 | 先隔离取证，再截断，并记尾随记录数 |
| 索引修复 | `_read_entries` 取整忽略残条，`_append_entry` 用 `O_APPEND` 追加 | **残条会让后续条目整体错位**（真缺陷）：加载时截到整数倍 |
| 索引补建 | 只在 `append_record` 时补 | 尾部扫描后按同一判据补建 |
| 恢复点 | 无（LEO 靠段名 + 末段扫描推导） | 新增文件，缺失/损坏退回推导，版本高拒绝 |
| 非末段损坏 | 不检测 | 按恢复点段清单 O(1) 对账，标记 + 告警 |
| 位点对齐 | 无（位点为内存态） | 独立协议 + 内存实现夹取 + 告警 |
| 优雅关闭 | 无（`BackgroundLoops` 只停循环） | `aclose()` 注册进 `ResourceManager` |

> **残条缺陷的机理**：索引条目定长（offset 索引 8 字节、时间索引 12 字节）。崩溃若把某条目写了一半，文件长度就不是条目整数倍；`_read_entries` 只读整条（丢弃残条），但下一次 `_append_entry` 用 `O_APPEND` 从**物理尾**追加，落在残条之后——新条目整体偏移 4 字节，此后的索引全部读偏、`scan_tail` 的锚点也偏。02-1 的「读取忽略残条」只挡住了「读到半条」，挡不住「后续写入错位」。

## 4. 恢复点 <a id="point"></a>

### 4.1 文件与内容

路径 `{partition}/recovery-point.json`（后缀不匹配段名正则 `^(\d{20})\.log$`，不会被段枚举误读）。

| 层 | 字段 | 说明 |
| --- | --- | --- |
| 外层 | `payload` | 下表的对象 |
| 外层 | `crc` | 对 `payload` 的规范化 JSON 字节算 CRC32（`sort_keys=True`、`separators=(",", ":")`、`ensure_ascii=False`） |
| payload | `format_version` | 当前 `1` |
| payload | `topic_id` / `partition_no` | 目录归属自检（对不上视为不可用） |
| payload | `leo` | **已 fsync 的 LEO**（见 §4.4 的偏序） |
| payload | `epoch` | leader 任期（02-4 / 02-5 预留，本期恒 0） |
| payload | `updated_at_us` | 写入时刻（epoch 微秒，排障用，不作判据） |
| payload | `segments[]` | 段清单，见下 |

段 stamp 四个字段：

| 字段 | 含义 | 空段（删光后承载 LEO 的 0 字节段） |
| --- | --- | --- |
| `base` | 段首 offset | 等于 LEO |
| `size` | 段文件字节数（**已 fsync 时**的大小） | `0` |
| `last_offset` | 段内末条记录的绝对 offset | `base - 1` |
| `last_position` | 段内末条记录的起始字节偏移 | `0` |
| `last_crc` | 段内末条记录的 CRC32 | `0` |

**为什么记 `last_position`**：非末段对账要读「段尾那一条」验 CRC，没有位置就只能靠索引二分 + 顺序扫（成本 O(索引间隔)）；记下位置后是**一次 seek + 一次 read**，每段 O(1)。

**为什么每分区一个文件**：LEO 是分区级概念，段只是它的分段；每段一个文件要在轮转 / 删除时同步多个文件，「同一时刻的一致快照」更难保证，且分区级 LEO 仍要另存一份。

### 4.2 写入：临时文件 + rename

```text
1 payload → 规范化 JSON → crc → 整体 JSON 字节
2 写 {dir}/recovery-point.json.tmp（O_WRONLY|O_CREAT|O_TRUNC|O_BINARY）→ fsync(fd) → close
3 tmp.replace(recovery-point.json)      # Windows 走 MoveFileEx(REPLACE_EXISTING)，同一目录同一卷
```

- **不做目录 fsync**：Windows 无对应语义（`O_DIRECTORY` 不存在），做了就产生不可测的平台分支；且恢复点只影响「下次启动少扫一点」，落后不损正确性（见 §4.4）。
- **写失败 fail-open**：`OSError` 只记 `msg_recovery_point_failed`（warning），不冒泡、不阻断 `append`。拒绝写是 02-6 存储水位的职责（`350022`），不能在这里另开一条拒绝路径。

### 4.3 读取：三类异常分开处置

| 情形 | 处置 | 日志 |
| --- | --- | --- |
| 文件不存在 | 退回推导（不报错，**向前兼容**：02-1 的数据目录没有该文件） | `msg_recovery_point_absent`（info） |
| JSON 解析失败 / 结构不符 / CRC 不符 / `topic_id`·`partition_no` 对不上 | 退回推导 | `msg_recovery_point_unusable`（warning，带 `reason`） |
| `format_version` 高于实现 | **抛 `UnsupportedRecoveryPointVersionError`，拒绝加载该分区** | —（由加载方冒泡） |

**为什么版本高要拒绝而不是退回推导**：退回推导会按旧格式理解未来数据，可能把新版本的记录当垃圾截掉——与记录 `format_version` 的口径一致（02-1 已定「版本高于实现即冒泡拒绝，不当损坏截断」），也与架构 08 §5「数据格式不回滚」一致。恢复点是**可再生**的索引类文件，但「可再生」不等于「可以按旧格式猜」。

### 4.4 写入时机：先 fsync、后写恢复点

恢复点只在**写路径**更新，且顺序固定为「fsync 数据 → 写恢复点」：

| 触发点 | 说明 |
| --- | --- |
| `_maybe_fsync` 判定刷盘后 | `batch` / `time` / `each` 三档；`each` 每条一次（成本随档位上升，属用户显式选择） |
| 段轮转前 | 先把旧段的 stamp 固化（旧段此后不再变化） |
| `truncate_before` 整段删除后 | 段清单变了，旧恢复点会指向已删段 |
| 优雅关闭 | 无条件 fsync 后写一次 |

`os` 档不刷盘 → 不写恢复点（只在轮转 / 关闭时写）。**先 fsync 后写**保证恢复点永不超前于真实数据：崩溃只需处理「恢复点落后」，不需要处理「恢复点超前」。

### 4.5 恢复点落后时的扫描起点

扫描起点取**两个锚点的较大者**（都以锚点之前的记录数为相对 offset）：

| 锚点 | 位置 | 相对 offset | 何时缺席 |
| --- | --- | --- | --- |
| 恢复点末段 | `stamp.size` | `stamp.last_offset + 1 - base` | 无恢复点、恢复点不可用、该段不在清单里、`stamp.size > 文件大小`（恢复点超前，视为不可信） |
| 最后索引项 | 索引末条的 `position` | 索引末条的 `relative` | 段内无任何索引条目 |

这是「从恢复点开始扫」与「只扫尾部 O(尾部)」两条要求的交汇点：

- 恢复点可信时，起点就在「已 fsync 的末尾」，只需扫未刷盘的那一小段（batch 档 ≤ 64 条）；
- 恢复点落后（`os` 档）时，索引项位置更靠后，起点退到索引项 → 扫描量 ≤ 一个索引间隔 + 尾部；
- 两者都缺席（空段 / 索引被删）时从 0 起 —— 这时的「全扫」是**单段内**的全扫，段本身有 64 MiB 上限，且这只发生在索引与恢复点同时丢失的灾难场景。

## 5. 非末段对账 <a id="verify"></a>

### 5.1 判定

对恢复点 `segments[]` 里**除末段之外**的每一段：

```text
段文件不存在          → 跳过（保留期清理删段后恢复点会落后，这不是损坏）
stamp.size == 0       → 只校验「段文件确实为 0 字节」，否则标记 size_mismatch
段文件大小 != stamp.size → 标记 size_mismatch
读 stamp.last_position 的记录：
  读不到 / 框架非法 / CRC != stamp.last_crc → 标记 crc_mismatch
其余                  → 通过
```

末段跳过（它由 §6 的扫描负责，扫描比 stamp 更权威）。恢复点里没有的段（新建段）跳过。

### 5.2 标记与告警

标记落**内存**（`{base: reason}`，可经 `corrupted_segments()` 只读查询），逐段出 `msg_segment_corrupted`（warning，带 `base_offset` / `reason` / `expected` / `actual`）。

- **不落盘**：一次误判会变成永久标记，而恢复点下次写入就会覆盖它；
- **不改名隔离**：中间段消失会让 `[start, leo)` 出现空洞，offset 与记录的一一对应即被破坏；任务 §2.5 也只要求「标记并告警」；
- **不阻塞启动**：该段照常参与读取，读到坏记录时由 `CorruptedRecordError` 冒泡（读取期不静默跳过，01-2 已定）。

### 5.3 与「不做全量校验」的共存

架构 04 §9 明说「只扫尾部，中间静默损坏无法发现（靠副本比对）」。本设计的段尾对账**没有**违反它：

- 成本 O(段数)、每段读一条记录，不是 O(全量)；
- 抓得到「段尾损坏 / 段被截短 / 段被替换」，抓不到「段中间某条记录静默翻转」——后者留给 8B_05 的副本比对；
- 它存在的意义是「让可见」而不是「让可修」：非尾部段若真坏了，至少启动日志里有段地址与原因，而不是等消费者读到才炸。

## 6. 尾部扫描与截断 <a id="scan"></a>

### 6.1 `scan_tail` 的接口演进

```python
def scan_tail(
    self,
    *,
    verify_crc: bool = False,
    anchor: tuple[int, int] | None = None,   # (position, relative_offset)
) -> TailScan
```

- `verify_crc=False` 保持 02-1 的既有语义（只判 `length` 与文件边界），**既有三条用例与既有调用一字不改**；
- 恢复路径显式传 `verify_crc=True`：逐条读整条记录并算 CRC（尾部有界，读载荷的成本可接受）；
- `anchor=None` 沿用「最后一条索引项」，与 02-1 完全一致。

`TailScan` 在原四个字段后**追加带默认值的字段**（不改既有字段语义与顺序）：

| 字段 | 含义 |
| --- | --- |
| `entries` | 扫描到的 `(position, relative, header)` 序列（补建索引用；尾部有界） |
| `last_crc` / `last_position` | 最后一条完整记录的 CRC 与起点（写恢复点、算末段 stamp） |
| `corrupted_position` | 第一条坏记录的起点；`None` 表示扫到文件尾无坏记录 |
| `trailing_records` | 坏记录之后「疑似完整」的记录数（尽力而为，见 §6.3） |

### 6.2 判定顺序

逐条固定四步，任一失败即停并记 `corrupted_position`：

1. 读 12 字节框架 → `read_frame` 校验 `length` 区间与 `header_len`；
2. `position + 4 + length <= size`（不完整即坏）；
3. 解头（`decode_header_blob`）——**这是版本校验的唯一时机**，版本高即 `UnsupportedRecordVersionError` 冒泡（不截断）；
4. `verify_crc` 时算 CRC 并比对。

### 6.3 坏记录之后的数据：截断 + 取证

**硬约束**：offset 是连续编号，中间跳过一条就无法保持「offset ↔ 记录」的一一对应；「救出后面的好记录」必然要重写段文件，而段是只追加的、任务 §2.9 也明确不做段修复。所以**只能截断到第一条坏记录之前**。

处置顺序（仅在有坏记录时执行）：

```text
1 读 [complete_bytes, size) 的字节 → 写 {base:020d}.log.corrupt-{ts}
2 由 stamp 与扫描结果算出 max_relative_offset（最后一条完整记录的相对 offset，可为 -1）
3 truncate(size=complete_bytes, max_relative_offset=...)   # 连带丢弃越界索引条目
4 出 msg_partition_recovered（warning）
```

- `ts` 格式 `%Y%m%dT%H%M%S%f`（UTC），UTC 便于跨机对齐排障时刻；
- 取证文件后缀 `{base:020d}.log.corrupt-{ts}`，**不匹配**段名正则，不会被当成段读；
- 保留最近 `CORRUPT_TAIL_KEEP`（缺省 8）份，超出删最早——防「持续损坏把磁盘再吃满一份全量数据」；
- `trailing_records`：从 `corrupted_position` 起用 `length` 字段试探（不校验 CRC），能连续读出几条完整框架就记几条，遇非法即停。它**不用于恢复**，只写进告警——让人一眼看出「丢的是最后一条，还是丢了一大片」。

### 6.4 索引补建

在截断与取证之后、`LEO` 定稿之前执行 `backfill_index(entries)`：

| 索引 | 补建判据（与写入路径**同一判据**） | 备注 |
| --- | --- | --- |
| `.index` | 首条必写；其后 `position - 上一条 position >= index_interval` | 只需 position 与 relative |
| `.timeindex` | 首条必写；其后 `published_at_us - 上一条 >= time_interval`（且时间单调不减） | 需要头里的 `published_at`，故 `entries` 带头 |

- **只补尾部区间**：补建输入是本次扫描到的 `entries`，不做全量重建（架构 04 §9 的取舍）；
- **幂等**：已存在同 relative 条目不重复写；补建前后条目仍单调；
- 补建条数进恢复日志（`index_rebuilt`）。

### 6.5 索引残条修复

加载段时对**末段**执行 `repair_index_tail()`：

```text
index_bytes % 8  != 0  → 截断到整数倍，记 dropped_bytes
time_bytes  % 12 != 0  → 截断到整数倍，记 dropped_bytes
```

- 只处理末段：崩溃只可能发生在最后写的段（历史段在轮转时已 fsync 并关闭）；
- 截断后 `_read_entries` 与 `_append_entry` 的物理偏移重新对齐，后续写入不再错位；
- 丢弃字节数进恢复日志（`index_repair_bytes`）。

> 这是本任务修的一处**真缺陷**，不是新增能力：02-1 的「读取忽略残条」只挡住了读半条，挡不住后续追加整体错位。

## 7. 位点对齐 <a id="offset"></a>

### 7.1 为什么单开协议

`OffsetStore` 只有 `get` / `commit` 两个方法，**没有枚举能力**——「已提交位点超过新 LEO 就回退」需要按 `(topic, partition)` 枚举所有组的位点。把 `realign` 塞进 `OffsetStore` 会改动 02-3 的端口签名（其前置契约明确「端口签名不变」），因此单开一个小协议：

```python
class OffsetRealigner(Protocol):
    async def realign_partition(
        self, *, topic_id: int, partition_no: int, ceiling: int
    ) -> ConcurrentStableList[OffsetAdjustment]: ...
```

`OffsetAdjustment`：`group` / `topic_id` / `partition_no` / `previous` / `current`。

- `ceiling` = 恢复后的新 LEO；
- 只夹「大于 ceiling」的位点，**不回退到 0**（任务 §5 前置契约：位点回退只回退到新 LEO）；
- 返回调整清单，由 `FileMessageStore` **统一出告警**——日志口径一处，02-3 实现该协议时不必重复写日志。

### 7.2 触发条件与时机

| 项 | 口径 |
| --- | --- |
| 触发 | 恢复时发生截断（`complete_bytes < 文件大小`）**或** 恢复点声明的 `leo` 大于推导出的 LEO |
| 时机 | 分区懒加载完成后，该分区**首个异步端口调用**前（`append` / `fetch` / `leo` / `start_offset` / `segments` / `truncate_before` / `locate` / `read_range` / `read_bytes` 统一入口） |
| 一次 | 每分区只对齐一次（`_pending` 字典 pop 即消费） |
| 未注入 | 出 `msg_offset_alignment_skipped`（warning），不阻断——装配缺陷要可见但不该让服务写不进去 |

### 7.3 内存实现的语义

`InMemoryOffsetStore.realign_partition`：遍历自身 `_offsets`，把键里 `topic_id` / `partition_no` 匹配且值大于 `ceiling` 的条目夹到 `ceiling`，返回清单。

进程重启后内存位点本就清空（02-3 才落盘），所以本任务真正能验的是「同一进程内、截断后位点被夹住」与「协议被正确调用」；跨重启的位点回退由 02-3 的文件实现承接，调用链与本任务完全相同。

## 8. 优雅关闭 <a id="close"></a>

### 8.1 注册位置与顺序

`ResourceManager` 是**逆序释放**（`aclose` 取 `resources[-1]`）。`app.state.resources` 在 `configure_service()` 之前就建好，因此：

| 顺序 | 资源 | 释放次序 |
| --- | --- | --- |
| 1 | `engine_registry` / `primary_health`（基座注册） | 最后 |
| 2 | **`StorageCloser`（本任务，`configure_service` 里注册）** | 次之 |
| 3 | `BackgroundLoops`（`startup_hooks` 里注册） | 最先 |

释放次序 3 → 2 → 1：**先停后台循环（延迟转投 / 重放），再刷日志并写恢复点**，最后才释放数据库引擎。装配顺序本身承载偏序，不需要额外协调代码。

### 8.2 关闭动作

```text
for 每个已加载分区:
    持分区锁 → fsync 末段 → 写恢复点 → 关写句柄
清空分区表
出 msg_store_closed（分区数 / 总 LEO）
```

- **无条件 fsync**：档位决定的是「运行期崩溃窗口」，关闭是显式关键时刻，不受 `os` 档影响（一次性成本）；
- **「先日志后位点」的偏序**：本任务只保证「日志刷盘 + 恢复点」在前；位点刷盘由 02-3 的文件实现放在其后（其关闭钩子注册得更晚 → 释放更早，需要在 02-3 装配时核对次序，已登记为交接项）。

### 9.2 恢复观测探针（「不扫全量」的机器判据）

```python
class RecoveryProbe(Protocol):
    def on_bytes_read(self, *, amount: int) -> None: ...
```

- `FileMessageStore(probe=...)` 可选注入，缺省 `None`（生产零开销：仅一次 `is not None` 判断）；

- 它是通用接缝（06-3 接指标时可直接复用），不是测试专用开关。

## 14. 风险与开放项 <a id="risk"></a>

| # | 项 | 处置 |
| --- | --- | --- |
| 1 | `each` 档每次刷盘都写恢复点（一次 JSON + rename） | 档位是用户显式选择（审计场景）；实测代价记平台级容量实测；若偏高改为「每 N 次刷盘写一次」，格式不变 |
| 2 | 恢复点随段数增长（每段约 120 字节） | 按一天一段，千段 ≈ 120 KB，可接受；真成问题时改「只记最近 N 段」也是向前兼容的增量 |
| 3 | 段尾对账抓不到中间静默翻转 | 架构 04 §9 既定取舍，靠 8B_05 副本比对；本节与 §5.3 已写明边界 |
