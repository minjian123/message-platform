## 2. 背景与范围 <a id="scope"></a>

**现状**：切换服务的 phase 1 之后会向旧主发一次降级通知（`demote`），**异常只记一条警告日志就继续**（`election.py` 的 `_finish`）。通知没送到时，旧主只能靠两条兜底自行发现：租约 5 秒过期后拒写，以及每秒一次的拓扑刷新把角色降为从节点。

**要解决的风险**：这段窗口里旧主仍按本地租约判定「自己可写」，客户端可能拿到写成功回执，而这条写入正落在切换后将被截断的尾部——对外承诺是「已提交不丢」，实际却可能丢。同一窗口内的双主并存还会污染 ISR 与水位口径。

**本子任务做三件事**：

1. **三态定性**（先证后修）：旧主可达 / 旧主不可达 / 旧主重启回归，各自测出「通知是否送到、旧主何时转只读、有没有已回执却被截断的写入」，结论进测试记录。
2. **让降级通知成为有预算、可观测、失败可补偿的动作**：按定性结果决定改实现还是只补观测与判据。
3. **判据与用例**：单测覆盖三态，并在三实例真容器环境复跑一条「旧主在预算内降级」判据。

**不做**（划清边界，避免扩大战场）：

- 不做杀进程 / STONITH 类隔离；
- 不做自动回切（02-9 已明确不做，防震荡）；
- 不改 `force` 降级的语义，不改租约时长与刷新周期；
- 不引入后台补偿任务，不做客户端 SDK 主动改投（SDK 归台账 #34 的规划承接）；
- 不改管理面切换端点契约（06-2 已交付）。

## 3. 完成标准 <a id="accept"></a>

**定性门槛**（必须先有结论，才允许动实现）：

- 三态各有一组真容器实测证据：「通知是否抵达旧主」「旧主从可写转只读的时刻」「切换窗口内是否存在已回执却被截断的写入」；
- 结论写成表，附时间戳与容器日志来源，能被人复核。

**实现门槛**（按定性结果二选一，不允许含糊）：

- 若确认存在窗口：切换流程必须保证旧主**在预算内必定转只读**；通知失败时不得静默放过——要么拦下切换（降级路径可查），要么留可补偿痕迹并在旧主回归后收敛；
- 若证明现状已满足要求：**不改实现**，只补观测（指标或审计字段）与回归判据，并在记录中写明「不改」的理由与支撑证据。

**通用门槛**：

- 变更模块行 + 分支覆盖率 100%，静态检查全绿；
- 三实例真容器复跑通过，新增判据「旧主在预算内降级」为硬判据；
- 文档三项校验（链接 / 文档范围 / 行尾）通过。

## 4. 边界 <a id="boundary"></a>

| 项 | 处理 |
| --- | --- |
| 通知的重试次数与超时预算 | 本任务在详细设计里定稿，不引入后台补偿任务 |
| 旧主不可达时的拒写依据 | 仍为「租约过期 + 刷新循环」，本任务不改租约与刷新周期 |
| 自动回切 | 不做（02-9 既有结论） |
| 客户端改投新主 | 服务端只保证元数据字段与 `350033` 的 `data`，SDK 侧归台账 #34 |
| 管理面切换入口与二次确认 | 06-2 已交付，本任务不改端点契约 |
| 复用现有降级原语 | 直接调既有 `demote`（复制协调器角色切换），不另写一套降级路径 |
