## 1. 现状事实 <a id="facts"></a>

下表全部来自现有实现，行号对应本轮改动前的代码，是后续定性与修法的依据。

| # | 事实 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | phase 1 完成后向旧主发**一次**降级通知，异常被 `try/except Exception` 吞掉，只记 `msg_leader_switch_demote_failed` 警告，流程继续宽限 → 激活 → 收口 | `election.py` `_finish`（`self._control.demote(...)` 与紧随的 `except`） | 通知失败对调用方**不可见**：切换照样返回成功 |
| 2 | 降级通知的实现把「不可达」原样上抛，注释明写「由切换服务忽略并靠租约兜底」 | `network.py` `HttpControlTransport.demote` | 兜底是设计内行为，不是意外 |
| 3 | 旧主收到通知后：角色改 `follower`、`epoch = max(epoch, to_epoch)`、`switch_state = switching`、唤醒等待者 | `replication.py` `demote` | 通知抵达即**立即停写**，`_ensure_leadership` 先判角色，写入立刻 `350033` |
| 4 | 通知没抵达时的两条兜底：刷新循环每 `1000ms` 重载拓扑并收敛角色；租约 `5000ms` 过期后拒写 | `DEFAULT_REPLICATION_EPOCH_REFRESH_MS` / `DEFAULT_REPLICATION_LEADER_LEASE_MS` 与 `refresh_once` / `_ensure_leadership` | 旧主最迟约 1s 自行转只读（刷新正常时）；DB 不可达时最迟 5s |
| 5 | 切换水位 `watermark` 取自 **phase 1 之前**对旧主的快照 `hw` | `election.py` 预检处 `old_snapshot.hw`（phase 1 之前） | 快照时点之后、通知生效之前旧主**已提交**的写入不在水位内 → 目标节点按水位截断会切掉它们 |
| 6 | 宽限 `switch_grace_ms` 缺省与租约同为 `5000ms`，且配置校验强制「宽限 ≥ 租约」 | `replication.py` 配置校验 | 宽限期足以覆盖租约过期，但**不覆盖**「通知已送达且旧主继续提交」的写入 |

**由事实 1 + 4 得出的缺口 A（计划已登记）**：通知失败静默，旧主靠自己发现，最长约 1s 内仍可能接受写入并回执。

**由事实 5 得出的缺口 B（本轮新发现，计划未登记）**：即使通知**成功**，水位也取早了。快照到通知生效之间可能有已提交写入落在水位之外，目标节点按旧水位截断即等于丢掉已提交数据。缺口的本质不是"通知有没有送到"，而是"水位是不是最终水位"。

## 2. 缺口影响面 <a id="impact"></a>

| 缺口 | 触发条件 | 后果 | 现有判据能否发现 |
| --- | --- | --- | --- |
| A：通知失败静默 | 旧主进程忙 / 网络抖动 / 端点临时错误 | 切换窗口内旧主继续回执写入，客户端拿到成功；该写入在目标激活时被截断 | 单测可断言；真容器需注入通知失败 |
| B：水位取早 | 快照与通知抵达之间旧主仍有提交（ISR 拉取推进 → HW 前移） | 同上，但**即使通知成功也会发生**，且是"已提交被截断"，直接违反「已提交不丢」 | 现有用例不覆盖（用例通知与快照同轮完成，窗口为 0） |

两处缺口的对外表现一致：**客户端拿到写成功回执，随后那条消息不存在**。这正是 8B_05 退出条件「不丢已提交」要守的线。

## 3. 候选修法 <a id="options"></a>

### 3.1 方案甲：通知失败即中止切换（严格）

- 通知失败且旧主**可达**（快照成功但降级返回错误）→ 抛 `LeaderSwitchError("demote_failed")`，DB 停在 `switching`（全分区停写），由调用方按既有重试语义再切。
- 通知失败且旧主**不可达**（快照与通知都失败）→ 维持现状（宽限 + 租约兜底），结果记 `degraded`。
- 水位：在通知**成功之后**再取一次旧主快照，用其 `hw` 作为最终水位；若目标 LEO 已小于该水位，则按「保留尾部」处理而不截断。

优点：语义最强，可达场景下不再有静默窗口；缺点：一次端点抖动就会让切换失败并延长停写，运维体验变差（虽然停写本身是安全态）。

### 3.2 方案乙：通知带预算重发 + 水位后置 + 降级可查（折中，推荐）

- 通知改为**带超时预算的两次尝试**（首次 + 一次快速重发），任一成功即视为已确认停写。
- 通知成功 → **重取旧主快照**，水位取 `max(预检 HW, 通知后 HW)`；目标 LEO 不足该水位时转「保留尾部」路径，不截断已提交数据。
- 通知两次都失败 → 切换**继续**（仍靠宽限 ≥ 租约兜底），但：结果标记为降级、审计写入 `demote_confirmed=false`、指标新增一个结果标签，运维可在事后查到"这次切换的旧主没被确认停写"。
- 不改租约、不改刷新周期、不改端点契约。

优点：不把网络抖动升级成切换失败，同时让缺口从"静默"变成"可查 + 水位正确"；缺点：仍有"未确认停写"的窗口，只是被标记出来。

### 3.3 方案丙：只补观测（最小）

只把通知结果写进审计与指标，不改通知次数、不改水位。优点：改动最小；缺点：缺口 B 完全没修，"已提交丢失"仍存在，等于只把问题记录下来。

### 3.4 对比

| 维度 | 甲 严格中止 | 乙 重发 + 水位后置 | 丙 只补观测 |
| --- | --- | --- | --- |
| 缺口 A | 可达即修 | 大幅收窄并标记 | 不修 |
| 缺口 B | 修 | 修 | 不修 |
| 切换成功率 | 受端点抖动影响 | 基本不受影响 | 不变 |
| 运维可查性 | 失败可查 | 降级可查 | 降级可查 |
| 改动面 | 中（新增失败分支 + 重试语义） | 中（通知重发 + 水位重取 + 结果标签） | 小 |
| 长期演化 | 语义最干净，但与"故障期间自动换主"目标相冲 | 与 02-9 自动切主的口径一致（自动路径已要求预算内收敛） | 债留后续 |

## 4. 水位口径的两种写法 <a id="watermark"></a>

| 写法 | 语义 | 风险 |
| --- | --- | --- |
| 预检 HW（现状） | 动作开始前的水位 | 快照之后的已提交写入被切掉（缺口 B） |
| 通知后重取 HW（推荐） | 旧主确认停写瞬间的水位 | 需校验目标 LEO ≥ 新水位；不足则转「保留」而非截断 |

「保留」路径本身已存在（旧主不可达时的处理），复用它不新增机制。

**两个边界（实施时补齐）**：

| 边界 | 定稿 |
| --- | --- |
| 确认停写后旧主立即不可达（重取快照失败） | 水位退回预检值，仍按 `truncate=true` 走原路径，不按未知水位截断 |
| 确认停写后目标快照不可得 | 视为「目标 LEO 未知」，不触发保留，仍按最终水位截断（目标 LEO 低于水位时 `truncate_to` 自然不生效） |

## 5. 观测与留痕 <a id="observe"></a>

| 出口 | 现状 | 本轮 |
| --- | --- | --- |
| 结构化日志 | `msg_leader_switch_demote_failed`（仅失败） | 增 `msg_leader_switch_demoted`：`attempts` / `confirmed` / `elapsed_ms` |
| 切主结果指标 | `truncated` / `retained` / `noop` / `degraded` / `failed` 闭集 | 见 §6 待拍板：新增 `demote_unconfirmed` 或复用 `degraded` |
| 审计 | `begin` / `finished` 字段 | `finished` 增 `demote_confirmed` 与 `watermark_source`（`precheck` / `post_demote`） |
| 切换结果对象 | `SwitchResult` 无通知字段 | 增 `demote_confirmed: bool = True` 与 `watermark_source: str = precheck`（带默认值，既有构造点零改动） |

不按节点 / 分区分键，避免指标基数爆炸（沿用 02-9 口径）。

## 8. 风险与对策 <a id="risk"></a>

| # | 风险 | 对策 |
| --- | --- | --- |
| 1 | 通知重发把切换时延拉长 | 每次尝试设短预算，总预算计入 `SwitchResult.duration_ms` 可查 |
| 2 | 通知后重取快照失败（旧主刚好挂掉） | 落「保留尾部」路径，不按未知水位截断 |
| 3 | 水位后置使截断变少、旧主尾部堆积 | 保留条数进审计与指标，堆积后续经 02-2 恢复流程处理 |
| 4 | 新增结果标签影响既有看板 | 标签闭集扩展需同步文案与用例（见待拍板项） |
| 5 | 演练入口已剥离，复跑成本高 | 复用 compose override，不重建整套演练框架；证据只落判据两项 |
