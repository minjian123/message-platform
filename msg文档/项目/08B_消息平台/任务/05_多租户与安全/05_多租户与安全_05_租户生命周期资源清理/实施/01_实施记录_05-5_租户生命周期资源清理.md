## 3. 实施过程 <a id="process"></a>

1. **开工前上下文**：读 AI 开发规范、需求 05-6、架构 07 §4 / §5 / §9、bms 07D `01-4`、05-1 详细设计与实施记录、msg 数据库设计体系与相关代码。
2. **Kiwi 登记**：登记 1 条新用例（2453），覆盖四事件 / 版本幂等 / 停用断连 / 删除保留期清理 / 失败重试；未复用 2451 / 2452。
3. **表与模型**：先建表文件并登记总览，再落 `MsgTenantLifecycle` 模型、`MSG_TABLE_RECORDS`、`MODEL_MODULES` 与测试库建表集。
4. **账本与运行时**：实现 DB 账本 + 文件账本兼容读；把 `app.state` 的连接 / 流 / 延迟 / 消息存储 / 位点 / 组 / 死信 / 投递 / 唤醒 / 缓存 / 节流 / 目录登记收进 `TenantLifecycleRuntime`，在 `configure_service()` 末尾登记。
5. **四动作**：`tenant.created` 回归；`suspended` 取消连接与长驻流；`activated` 取消待清理；`deleted` 写删除计划 + 易失资源清理 + 强审计。
6. **到期清扫**：按主题 `retention_ms` 计算 deadline，逐主题删数据 / 位点 / DB 行；`purge_after` 取最早到期点，`purged_at` 标记完成；启动钩子周期驱动。
7. **延迟转投**：`DelayScheduler` 增加 `TenantAvailability` 检查，复用基座 `SourceTenantGuard`；停用期间保留记录、不转投。
8. **契约与文档**：任务文档事件名改 `suspended` / `activated`；架构 07 §5.2 改为「停用 / 删除按保留期处理」；本记录 / 测试记录 / 计划回写。

## 4. 关键实现说明 <a id="key"></a>

### 4.1 账本

- `msg_tenant_lifecycle` 一条 `(tenant_id, action)` 一行；`applied_version` 为业务级幂等键。
- `deleted` 行额外持有 `deleted_event_at` / `purge_after` / `purged_at` / `failure_count` / `last_error`。
- `mark_deleted` **不写** `applied_version`，动作完整成功后才由分发器 `mark_applied` 推进；避免「清理计划已写、易失清理失败」被误判已处理。
- 05-1 `.lifecycle.json` 只兼容读；DB 无行时回退读文件，不再写回。

### 4.2 停用 / 启用

- 不修改 `msg_topic.status`；数据面由基座租户守卫拒绝，管理面只读查询仍可看。
- `ConnectionRecord` / `StreamSession` 增 `tenant_id`；停用按租户取消连接、标记长驻流 `cancelled`，流循环每轮检查后结束。
- `DelayScheduler` 在转投前调用 `GuardTenantAvailability.is_active()`；停用 / 不存在 / 租户源不可达均 fail-closed，记录保留下一轮再判。

### 4.3 删除与到期清扫

- `on_deleted`：写删除计划；取消非终态重放任务；清延迟区（内存 + `.delay` + 时间轮）；清组 / 死信 / 投递状态 / 唤醒器 / 主题缓存 / 保留节流；取消连接 / 流；强审计。数据目录、位点、主题 / 分区行保留到到期。
- `TenantPurgeService`：逐主题按 `deleted_event_at + retention_ms` 到期；活跃重放任务先取消并延后一轮；关闭 `FileMessageStore` 租户句柄 → 删位点 → 删数据目录 → 删 DB 行 → 移除目录登记 → 强审计 → 更新 `purge_after` / `purged_at`。
- 路径安全：`_safe_rmtree` 要求目标位于数据根内且不等于数据根本身。
- 失败：清扫失败记 `failure_count` / `last_error`，下轮重试；审计失败不标记 `purged_at`，下轮补审计。

### 4.4 05-1 路径偏差修正

05-1 的 `on_created` 原先把租户目录建在 `data_root()/{tenant_id}`，而实际消息存储布局是 `data_root()/data/{tenant_id}/...`。本任务把 `MsgTenantResourceHandler` / `FileTenantLifecycleLedger` 的缺省根改为 `data_root()/DATA_ROOT_SUBDIR`，并在主装配把 `TenantPurgeService` 的 `data_root` 传为 `root / DATA_ROOT_SUBDIR`。注入 `root` 的 05-1 用例行为不变。

### 4.5 审计

- 停用 / 启用：普通审计（`msg:tenant.suspend` / `msg:tenant.activate`），失败只记指标，不阻断基座已生效状态。
- 删除 / 清理：强审计（`msg:tenant.delete` / `msg:tenant.purge`），失败上抛 / 不标记完成，下轮重试。
- 审计记录归基座审计链，不随 msg 资源删除；本期不写 `record_ref`（非具体日志记录操作）。
