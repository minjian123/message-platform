## 2. 任务内容 <a id="content"></a>

1. **ACL 模型**：主题级授权记录——`tenant_id` / `module_key` / `topic`（`resource_key`）/ 主体（用户或角色）/ 操作类型（`publish` / `subscribe` / `describe` / `manage`）/ 生效状态；存储 msg 自持，不写平台表。
2. **判定顺序**：严格按「基座 RBAC（`msg:query` / `msg:manage`）→ 主题 ACL → 租户 / `module_key` 归属」执行；任一步拒绝即终止；**ACL 不得前置**，避免泄露主题存在性。
3. **生效范围**：ACL 只在同一 `module_key` 内生效；跨租户、跨 `module_key` 一律拒绝，且不因 ACL 放行。
4. **三处易漏点必须覆盖**：① 跨租户订阅（订阅方租户与主题归属不一致）；② 管理接口只校验登录、不校验资源权限；③ 重放接口可指定任意主题。每条都要有拒绝用例，不接受「默认安全」的口头结论。
5. **缓存与失效**：ACL 判定可缓存，但失效以变更版本戳为准，不自建与基座并行的状态缓存；ACL 变更即时生效。
6. **留痕**：ACL 的授予 / 收回 / 变更走基座审计链（接 05-4），带作用域字段与操作人。
7. **边界**：不自建 RBAC 引擎、不复制权限码体系、不在业务层逐处手写「是否管理员」；判定收敛为单点接口，为后续上收基座预留替换点。
8. **测试**：判定顺序不可绕过、跨租户 / 跨 `module_key` 拒绝、三处易漏点、变更即时生效与留痕、单实例与多 worker 下判定一致；变更模块行 + 分支覆盖率 100%。

## 3. 完成标准 <a id="accept"></a>

- 四类操作（`publish` / `subscribe` / `describe` / `manage`）均有 ACL 判定且顺序不可绕过；
- 跨租户订阅、管理接口越权、重放任意主题三类请求被拒绝，并有自动化用例；
- ACL 只在同一 `module_key` 内生效，跨模块访问被拒；
- ACL 变更即时生效，且在基座审计链可查；
- ACL 判定收敛为单点接口，可替换、可上收；
- 无自建 RBAC 引擎、无复制权限码体系；
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
