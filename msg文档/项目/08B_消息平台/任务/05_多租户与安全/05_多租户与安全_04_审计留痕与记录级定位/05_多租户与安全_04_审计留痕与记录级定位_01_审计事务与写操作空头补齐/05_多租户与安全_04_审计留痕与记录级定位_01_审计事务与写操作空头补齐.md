## 2. 任务内容 <a id="content"></a>

1. **审计进同一事务**：强审计事件改为写进业务 `UnitOfWork` 的同一会话（不再自开短事务），业务提交即审计入账、业务回滚即审计不留；审计写失败抛 `InternalError`（10000），业务一起回滚；删主题的 `cleanup.kick()` 移到 `finally`，保证「业务已受理但后台未启动」也能自愈。
2. **删消息端点**：`POST /api/v1/msg/admin/messages/{log_id}/delete`（单条）与 `POST /api/v1/msg/admin/messages/delete`（批量，`log_ids` ≤ 100）；存储层用**墓碑标记**（追加删除标记，读路径过滤），位点连续、副本天然一致，磁盘到保留期回收；每次删除写强审计（`record_ref = msg.message/log_id`）。
3. **敏感查询留痕**：消息检索、死信详情、重放详情三类查询写普通审计（新动作名），失败只告警、不影响查询响应。
4. **主题停用 / 启用端点**：`POST /api/v1/msg/admin/topics/{id}/disable` 与 `/enable`，`msg:manage` + 强审计；停用只拒绝数据面发布 / 消费（350028），管理面查询、改保留期、扩分区、删除照常；重复调用幂等。
5. **死信重放补偿**：重放任务创建后置 `replaying` 失败时取消刚建的任务再抛 350030，消除孤儿任务。
6. **并发建主题兜底**：唯一约束 `IntegrityError` 兜底为 350008（不再 500）。
7. **死信忽略 / 归档 CAS**：改为条件更新（`WHERE status IN (...)`），并发处置只允许一个成功，另一个 350030。
8. **`cleanup_policy` 白名单**：契约层只接受 `delete`，非法值 10001；服务层兜底同一判据，不再「配置看似生效实际不生效」。
9. **清理完成核对**：`_complete` 前置核对主题行已物理删除；仍在 `deleting` 时不置 `completed`，保留轮次并告警，避免「删不掉也建不了」。
10. **延迟丢弃端点**：`POST /api/v1/msg/admin/delayed/{log_id}/discard`（`msg:manage` + `confirm` + 强审计 + `record_ref`），把已装配但不可达的 `DelayDisposalService` 接上。
11. **前端接线**：06-2-3 预留的主题停用 / 启用按钮接上；消息查询页与死信 / 重放详情补「删消息」入口（按 `msg:manage`）。

## 3. 完成标准 <a id="accept"></a>

- 强审计与业务同事务：制造审计写入失败时业务不落库、响应 10000；审计成功而业务回滚时审计也不留。
- 删除消息后：`fetch` / 消息检索 / `find_by_log_id` 均看不到该记录，LEO 与位点不变；重启后仍不可见；副本同样不可见。
- 批量删除超过 100 条返回 10001；逐条结果可区分「已删 / 不存在 / 已删过」。
- 三类查询各写一条审计，审计失败不影响 200 响应。
- 停用后数据面发布 / 消费 350028，管理面写操作仍可用；启用后恢复；重复停用 / 启用幂等。
- 死信重放并发时只有一个成功，另一个 350030 且无孤儿任务。
- 并发建同名主题稳定返回 350008。
- `cleanup_policy` 非 `delete` 返回 10001。
- 清理台账只在主题行确实删除后置 `completed`。
- 延迟丢弃端点可用且留痕。
- 变更模块行 + 分支覆盖率 100%；ruff / pyright / 契约零漂移 / 文档三项全绿；前端相关门禁全绿。
