## 2. 任务内容 <a id="content"></a>

1. **形态**：首期支持 **unary + server streaming**；client streaming 与双向流后置；端点 `POST /rpc/{service}/{method}/stream`（概要设计 3.2），一次请求、多次响应。
2. **帧与结束**：复用 03 帧协议，RPC 流帧类型在 `7-15` 取号；响应带序号；流结束用 `flags.end` / EOF 标记；正常结束与异常中断可区分；不新增 close 帧（沿用 03-5 的 EOF 约定）。
3. **背压**：复用 03-5 的 HTTP/2 窗口 + 应用层 inflight（条数 / 字节双阈值）；服务端推送受窗口与 inflight 约束，慢消费者暂停；不得无界缓冲；RPC 流与事件订阅共用等待机制，但按 RPC 请求隔离，不引入消费组 / ack / offset 语义。
4. **流内错误**：流开始后错误用 error 帧表达（`code` / `layer` / `retryable` / `detail`）；HTTP 状态码只用于流建立前的失败；客户端收到 error 帧后结束流并交给错误处理，不得把 200 当成功。
5. **半开流**：连接层心跳由 03-4 负责，流层设置空闲超时；超时服务端结束流并释放；客户端按失败处理或重连；首期不提供断点续传 / resume token。
6. **deadline 与取消**：整条流共享 04-2 的 deadline 与取消；客户端取消即停止推送并释放；不按每帧单独设 deadline，空闲超时另设。
7. **客户端 API**：`RpcClient.stream(...)` 返回异步迭代器；支持正常 `break` / 取消清理；错误在迭代中抛出；不实现 client streaming。
8. **复用订阅能力**：`subscribe` 本质是 server streaming；RPC 流复用同一背压与帧机制，但保持「一次请求对应一个调用方」的语义，不引入消息位点。
9. **测试**：连续推送 N 条；慢消费者触发背压；流内错误；半开超时释放；客户端取消；正常结束；契约快照。
10. **边界**：不做 client streaming / 双向流；不做断点续传；不做 bms 适配（04-5）；不做认证授权（05 域）。

## 3. 完成标准 <a id="accept"></a>

- 服务端流可连续推送且背压生效（窗口 / inflight 满时暂停，不无界缓冲）。
- 流内错误可被客户端识别；正常结束与异常中断可区分。
- 半开流在空闲超时后释放；客户端取消后服务端停止推送并释放资源。
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
