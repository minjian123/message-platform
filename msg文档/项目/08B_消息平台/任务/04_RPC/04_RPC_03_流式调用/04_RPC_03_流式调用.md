## 2. 任务内容 <a id="content"></a>

### 2.0 子任务拆分 <a id="split"></a>

本任务于 2026-11-06 拆为两个嵌套子任务，**各一份设计、各一次提交、各一条 Kiwi 用例**：

| 子任务 | 范围 | 验收面 |
| --- | --- | --- |
| [04-3-1 服务端流式](04_RPC_03_流式调用_01_服务端流式/04_RPC_03_流式调用_01_服务端流式.md) | `/stream` 端点、流帧与结束位、流内错误、空闲超时、背压、注册表流端口、`350024` | ASGI 面 + 真机 h2c（`httpx` 逐块读） |
| [04-3-2 客户端流式消费](04_RPC_03_流式调用_02_客户端流式消费/04_RPC_03_流式调用_02_客户端流式消费.md) | 传输层读队列、`RpcStream`、结束三态与序号校验、取消与空闲兜底 | 单测 + 真机端到端（生产 `RpcClient`） |

拆分的依据：两段改的是不同层（`api/rpc/*` 与 `client/*`），服务端可独立验收；传输层改动单独成提交、单独判覆盖率，回滚粒度清晰（与 04-7 的拆法同构）。下面的条目对两个子任务共同有效，细则以各自详细设计为准。

1. **形态**：首期支持 **unary + server streaming**；client streaming 与双向流后置；端点 `POST /rpc/{service}/{method}/stream`（概要设计 3.2），一次请求、多次响应；**只接帧形态**（`application/x-msg-frame`），JSON 请求明确拒绝（`10001`）。
2. **帧与结束**：复用 03 帧协议，**沿用 `FrameType.RPC = 48` + `flags.response`**；末帧置 `flags.end_of_stream`（03-2 已预留、本任务首次启用）；响应序号进帧头 `seq`（0 起逐帧 +1）；正常结束与异常中断可区分；不新增帧类型、不新增 close 帧（沿用 03-5 的 EOF 约定）。
   - **2026-11-06 回写**：原写「RPC 流帧类型在 `7-15` 取号」有误——`protocol/contract.py` 的 `reserved_types` 已把 `7-15` 登记为**数据面预留**、`48-63` 为 **rpc** 段，`FrameType.RPC = 48`（04-1 已因同一原因回写过一次）。取 `7-15` 会占掉数据面后续扩展位，故不照字面实现。
3. **背压**：复用 03-5 的 HTTP/2 窗口 + 应用层 inflight（条数 / 字节双阈值）；服务端推送受窗口与 inflight 约束，慢消费者暂停；不得无界缓冲；RPC 流与事件订阅共用等待机制，但按 RPC 请求隔离，不引入消费组 / ack / offset 语义。
4. **流内错误**：流开始后错误用 error 帧表达（`code` / `layer` / `retryable` / `detail`）；HTTP 状态码只用于流建立前的失败；客户端收到 error 帧后结束流并交给错误处理，不得把 200 当成功。
5. **半开流**：连接层心跳由 03-4 负责（10s 探 / 30s 判死），流层设置空闲超时——**服务端 60s 先到、客户端 90s 兜底**（阈值刻意错开，避免两侧同时到点、排障时分不清谁先放弃）；超时服务端发 `350024` 结束流并释放；客户端按失败处理或重连；首期不提供断点续传 / resume token。
6. **deadline 与取消**：整条流共享 04-2 的 deadline 与取消；客户端取消即停止推送并释放；不按每帧单独设 deadline，空闲超时另设。**流式不套用一元「预算 + 余量」的整段本地超时**（否则长流必被本地掐断），客户端只兜「单次读 90s 无数据」。
7. **客户端 API**：`RpcClient.stream(...)` 返回 **`RpcStream` 句柄**——支持 `async for`（逐条取结果）、`async with`（退出即发 `RST_STREAM(CANCEL)`）、`aclose()`（幂等）；错误在迭代中抛出；**`async for` 里 `break` 不会自动发 `RST_STREAM`**，须配合 `async with` 或显式 `aclose()`（`async generator` 的 `break` 不触发 `aclose`，靠 GC 兜底时机不定）；不实现 client streaming。
8. **复用订阅能力**：`subscribe` 本质是 server streaming；RPC 流复用同一背压与帧机制，但保持「一次请求对应一个调用方」的语义，不引入消息位点。
9. **测试**：连续推送 N 条；慢消费者触发背压；流内错误；半开超时释放；客户端取消；正常结束；契约快照。
10. **边界**：不做 client streaming / 双向流；不做断点续传；不做 bms 适配（04-5）；不做认证授权（05 域）。

## 3. 完成标准 <a id="accept"></a>

- 服务端流可连续推送且背压生效（窗口 / inflight 满时暂停，不无界缓冲）；响应帧 `seq` 从 0 单调递增、末帧置 `end_of_stream`。
- 流内错误可被客户端识别（未注册 `350023` / 预算耗尽 `350004` / 空闲超时 `350024` / 业务原码）；正常结束与异常中断可区分，且「无收尾帧即断流」也能被判为异常。
- 半开流在空闲超时后释放；客户端取消（`RST_STREAM`）后服务端 ≤150ms 内停止推送并释放资源，同连接其它调用不受影响。
- `RpcClient.call()` 的签名、行为与错误码零变化（一元面不受流式改动影响）。
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
