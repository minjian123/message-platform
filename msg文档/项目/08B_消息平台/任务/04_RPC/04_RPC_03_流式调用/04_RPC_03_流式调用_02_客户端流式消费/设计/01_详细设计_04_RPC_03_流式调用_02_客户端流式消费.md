## 1. 概述 <a id="overview"></a>

### 1.1 目标

把 04-7-1 明写「届时在本类上加读队列」的那一步做掉，并给调用方一个不靠 GC 兜底的流式 API：

1. **传输层只加一类能力**：`H2Stream` 支持逐块读（`read_chunk()`），`RpcTransport` 支持 `open_stream()`；一元 `send()` 与池行为**一个字节不改**。
2. **句柄而非生成器**：`RpcClient.stream()` 返回 `RpcStream`——支持 `async for`（需求 04-3 §2.7 的字面要求）、`async with`（退出即发 `RST_STREAM`）、`aclose()` 幂等。`async generator` 在 `break` 后不会立即 `aclose()`，取消时机不确定，正是 04-2 / 04-7 修掉的那类问题。
3. **结束三态与序号都可判**：`end_of_stream` → 正常；`ERROR` 帧 → 按码抛；EOF 无收尾 → 协议错。`seq` 必须从 0 单调 +1。
4. **取消沿用一条既成路径**：`abort(reason)` → `RST_STREAM(CANCEL)` → 服务端 50ms 探测中断；客户端事件仍是 `msg_rpc_client_cancel`。
5. **不把一元的时间预算套到流上**：整条流的期限由服务端预算兜底；客户端只兜「长时间没有数据」（90s）。

## 2. 现状与差距 <a id="gap"></a>

| 现状 | 差距 |
| --- | --- |
| `H2Stream.wait_response()` 循环等 `_event`，`_finished` 才返回；`on_data` **故意不唤醒**等待者 | 一元语义要求「等收齐」，流式要求「到一块读一块」；两者必须在同一个类里共存而不互相干扰 |
| `RpcTransport.send()` 只有「发完收齐」一个出口 | 流式需要「先发请求、再逐块取」，且要有独立的 `abort` 落点 |
| `AsgiRpcTransport.send()` 把整个响应体收进 `collected["body"]` 后一次性返回 | 进程内测试要能**边产边读**，否则背压与取消在 ASGI 面完全测不出来 |
| `RpcClient` 只有 `call()` | 缺流式入口；请求帧编码逻辑已在 `call()` 里，应抽出复用而不是复制一份 |
| `msg_rpc_client_cancel` 已有 `reason` / `rst_sent` / `stream_id` | 流式正常结束没有事件可看，排障时分不清「跑完了」与「没日志」 |

## 4. 契约 <a id="contract"></a>

### 4.1 传输层：协议与流对象

```python
class TransportStream(Protocol):
    @property
    def stream_id(self) -> int: ...
    async def read(self) -> bytes | None: ...   # None = 已收 END_STREAM
    def abort(self, reason: str | None = None) -> bool: ...  # 幂等；返回「本次是否真发出 RST」

class RpcTransport(Protocol):
    async def send(self, request: RpcHttpRequest) -> RpcHttpResponse: ...
    def open_stream(self, request: RpcHttpRequest) -> AbstractAsyncContextManager[TransportStream]: ...
    async def aclose(self) -> None: ...
    def stats(self) -> TransportStats: ...
```

| 决策 | 理由 |
| --- | --- |
| `open_stream` 返回**异步上下文管理器**，不是裸对象 | 发送请求是异步的（要取连接、可能建连），而 `stream()` 本身希望是同步构造（否则 `async with await client.stream(...)` 很难看）；把「进入 = 发请求」放进 `__aenter__`，调用方写法干净，异常也统一在进入时抛 |
| `read()` 用 `None` 表示结束，而不是抛 `StopAsyncIteration` | 传输层不认识「迭代协议」；`None` 是最小的「没有更多字节」表达，句柄层再翻译成 `StopAsyncIteration` |
| 中止复用 `abort(reason)`，不新造 `close()` | 04-7-2 的 `abort` 已含幂等、`rst_sent` 累积、`close_reason` 六态与日志；再造一个名字会让「同一动作两个入口」 |
| `TransportStream` 不暴露 `close_reason` | 句柄层只需要「发出去了没有」；细分状态留在 `H2Stream`，由传输层日志消费（与 04-7-2 §5.3 同取向） |

### 4.2 客户端 API

```python
class RpcClient:
    def stream(self, service, method, payload=b"", headers=None, *,
               trace_id=None, caller=None, deadline_ms=None, tenant=None) -> RpcStream: ...

class RpcStream:
    async def __aenter__(self) -> RpcStream: ...
    async def __aexit__(self, *exc) -> None: ...
    def __aiter__(self) -> RpcStream: ...
    async def __anext__(self) -> RpcReply: ...
    async def aclose(self) -> None: ...
```

用法（写进 docstring，作为唯一推荐写法）：

```python
async with client.stream("demo", "ticker", b"5") as replies:
    async for reply in replies:
        handle(reply.payload)
        if enough:
            break            # 退出 with 时发 RST_STREAM(CANCEL)
```

| 决策 | 理由 |
| --- | --- |
| **惰性打开**：`stream()` 不发请求，`__aenter__` / 首次 `__anext__` 才发 | 「构造即发请求」会在 `async for` 之前就占用一条流；调用方拿到句柄却没消费等于服务端白跑（正是 04-2 的病根） |
| `break` 不自动发 RST，必须靠 `async with` / `aclose()` | `async for` 的 `break` 语言层面不通知迭代器；靠 GC 兜底时机不定。契约里写明，并用**用例**把「不写 `async with` 就漏 RST」这件事固定成已知行为 |
| `RpcStream` 单消费者，不支持并发 `__anext__` | 多消费者会把「谁是下一个」变成竞态；需要多路消费的场景各自开流（h2 多流本来就便宜） |

### 4.3 结束与异常映射

| 收到 | 处理 |
| --- | --- |
| `48` + `response`，`seq` 符合预期 | 产出 `RpcReply(payload, headers)`；若置 `end_of_stream`，标记结束（本帧照常产出，下次 `__anext__` 抛 `StopAsyncIteration`） |
| `ERROR` 帧 | `code == 350004` → `RpcCallTimeoutError(budget_ms=…)`；其余 → `RpcCallError(code, retryable, layer, retry_after_ms)`（全部照搬帧头，客户端不自行分类） |
| `seq` 不符 / `request_id` 不符 / 其它帧类型 | `RpcCallError(0, layer="protocol")` |
| `read()` 返回 `None` 但既无 `end_of_stream` 也无 `ERROR` | `RpcCallError(0, "流异常中断", layer="protocol")` |
| `read()` 抛传输层错误（对端 reset / 连接故障 / 帧不可解析） | `RpcTransportProtocolError` → `layer="protocol"`；其余 `RpcTransportError` → `layer="transport"`（与一元同梯度，不混成 `protocol`——「协议坏了」与「连接断了」是两类事实） |
| 本地空闲超时（90s 无任何块） | `abort(timeout)` → `RpcCallTimeoutError`（`350004` / `outcome=unknown`） |
| 调用方 `aclose()`（流未结束） | `abort(cancelled)` → 不抛（`aclose()` 本身不抛流内错误） |
| 调用方 `task.cancel()`（读中） | `abort(cancelled)` → `CancelledError` 原样穿透（与 04-7-2 同口径：取消不包装、不吞，但本流必须被中止） |

**为什么协议错给 `code=0`、`layer=protocol`**：这类错误不是服务端判定的业务结果（服务端可能什么都没回），给一个产品码会诱导调用方按码重试。04-7-1 的异常梯度已确立同一口径。

## 5. 实现 <a id="impl"></a>

### 5.1 读队列

```python
# H2Stream 新增（与既有 _event / _finished 并存）
self._chunks: deque[bytes] = deque()
self._chunk_event = asyncio.Event()

def on_data(self, data: bytes) -> None:      # 由连接的读取任务调用
    if not data:                             # 空 DATA（end_stream() 的形态）没有信息量，不入队
        return
    self._chunks.append(data)
    self._chunk_event.set()                  # 流式：唤醒读等待者

async def read_chunk(self) -> bytes | None:  # None = 已结束
    while True:
        if self._chunks:
            return self._chunks.popleft()
        if self._finished:
            if self._error is not None:
                raise self._error           # 带着错误收口：不能悄悄结束
            return None
        self._chunk_event.clear()
        await self._chunk_event.wait()
```

| 决策 | 理由 |
| --- | --- |
| 复用既有 `_finished` / `_error` 标志，不新建流状态机 | 一元与流式共享「流什么时候完」的事实，两套状态必然漂移；`wait_response()` 仍只看 `_finished`，语义不变 |
| `on_data` 现在也 `set()` 一个读事件 | 一元路径不读 `_chunk_event`，多一次 `set()` 无副作用（无人等待时事件保持置位，下次进 `wait` 立即返回，正是 `clear()` 放在 `wait` 之前的原因） |
| **收口事件同样 `set()` 读事件**（`on_end` / `on_reset` / `on_connection_error`；实施期补） | 只醒「来了数据」不够：「没有数据、只有结束」正是末帧之后的常态，不醒就会让读者睡到调用方自己的超时 |
| **空 DATA 帧不入队**（实施期补） | `h2.end_stream()` 的线上形态是「空 DATA + `END_STREAM`」，入队会让 `read()` 先吐一个 `b""`；结束由 `on_end()` 单独表达，丢空块不丢信息 |
| 队列元素是**原始字节块**而非「已切好的帧」 | 切帧要跨块（一帧可能横跨两个 `DATA`），属编解码层职责；传输层只回答「来了多少字节」 |
| 不设队列上限 | 上限由 h2 窗口决定（前提是只在 `DataReceived` 时 `acknowledge`，见 §9 风险 3 的实测修正）；再叠一层上限会与窗口语义打架 |

### 5.2 `H2Transport.open_stream`

```text
取连接（与 send 同一个 _connection_for，含空闲回收）
  → connection.send_request(request, on_open=…)
  → 等响应头（status）
  → status != 200？中止本流并抛 RpcTransportClosedError
  → 返回 _H2TransportStream(stream, connection)
     · read()  → stream.read_chunk()
     · abort() → stream.abort(reason)（同步 write，沿用 04-7-2）
```

异常映射与 `send()` 同表（超时 / 关闭 / 协议 / 不支持），**不新增第五条**。建连与发请求阶段失败在 `__aenter__` 里抛出，调用方拿到的是 `RpcCallError`。

**非 200 在打开阶段判掉**（实施期补）：流端点对帧请求恒回 200（建流前失败也是 `200 + 单帧 error`），
所以非 200 只可能来自路由 / 权限 / 网关——那时响应体根本不是帧流，交给句柄层只会得到「帧不可解析」
这种误导性协议错。因此 `status` 不进 `TransportStream`（句柄层不需要它），在传输层就变成
`RpcTransportClosedError("RPC 流端点返回 HTTP {status}")`。响应头之前对端 `RST_STREAM` 则原样抛
「对端中止了 h2 流」，不降级成「HTTP 0」。

### 5.3 帧解析循环

```text
buffer 挂在句柄上（跨 __anext__ 保留）
while True:
    batch = decode_frames(buffer)        # 逐帧滑走；不完整尾包保留
    buffer = buffer[consumed:]           # 用 bytes 切片，不用 del bytearray[…]
    for frame in batch.frames: 判定并产出 / 抛错
    若本批已产出至少一帧 → return 该帧给 __anext__
    chunk = await stream.read()          # None → 结束判据（§4.3）
    if chunk is None: → 无收尾则协议错
    buffer += chunk
```

| 决策 | 理由 |
| --- | --- |
| 用 `decode_frames` 而非自己切头 | 03-2 已实现「长度校验先行、不按声明长度预分配、不完整尾包保留」，复用它才有资格说「与协议同源」 |
| 一次 `read()` 可能解出多帧，先攒后逐条产出 | `__anext__` 一次只返回一条结果（迭代协议要求），剩余帧留在 `_pending`，下次直接吐 |
| **缓冲挂句柄，不用局部变量**（实施期补） | 循环会在「本批已产出一帧」时 `return`；局部缓冲随之丢弃，尾部的半帧就丢了，下一块到达时帧头错位（用例把两帧切在偏移 5 时必现） |
| **缓冲用 `bytes` 而非 `bytearray`**（实施期补） | `Frame.payload` 是缓冲的 `memoryview` 切片；`FrameBatch` 还活着时 `del buffer[:consumed]` 会抛 `BufferError`（不能缩容有导出的缓冲）。`bytes` 切片另开一块，视图与缓冲生命周期解耦 |
| 切帧在句柄层、不在传输层 | 传输层不认识帧（04-7-1 已把「协议」与「字节」分开），把帧语义塞回去会让传输层依赖 `protocol.frame` |

### 5.4 取消与收尾

| 触发 | 动作 | 事件 |
| --- | --- | --- |
| `aclose()` / `async with` 退出（流未结束） | `abort(cancelled)`；幂等（已结束则不发帧） | `msg_rpc_client_cancel`（`reason=cancelled`） |
| 空闲超时 | `abort(timeout)` + `RpcCallTimeoutError` | 同上（`reason=timeout`） |
| 帧解析 / 协议错 | `abort(error)` + 抛错 | 同上（`reason=error`） |
| 正常结束 | 不发帧；`abort` 不参与 | `msg_rpc_client_stream`（`frames` / `bytes` / `duration_ms` / `seq_max`） |

**为什么 `aclose()` 不抛流内错误**：`aclose()` 的语义是「我不看了」，抛错会让 `async with` 的 `__aexit__` 在清理路径上二次抛异常，把调用方的真实异常盖掉。

### 5.5 不套用整段本地超时

一元调用的本地超时是「预算 + 200ms」包住整次调用（04-2 / 04-7-1）。流式**不能照搬**：

| 方案 | 后果 |
| --- | --- |
| 照搬「预算 + 余量」包住整条流 | 预算 30s 的流 30s 后必被本地掐断——哪怕服务端正正常推、调用方也没意见；长流等于不可用 |
| 只兜「单次 `read()` 的空闲」 | 服务端按预算收尾（发 `350004`），客户端只在「完全没有数据」时兜底；两者不重叠 |

因此：`RpcStream` 里唯一的计时器是「单次 `read()` 的 90s 空闲上限」；`deadline_ms` 只作为**请求字段**发给服务端（服务端据此决定何时收尾）。

### 5.6 观测

| 事件 | 字段 |
| --- | --- |
| `msg_rpc_client_stream`（正常结束） | `request_id` / `service` / `method` / `stream_id` / `frames` / `bytes` / `seq_max` / `duration_ms` |
| `msg_rpc_client_cancel`（中止，沿用 04-7-2） | 上述关联字段 + `reason` / `rst_sent` / `elapsed_ms` / `frames`（新增：已产出的帧数） |

**为什么不把两者合成一条**：一是 04-7-2 的事件已被 06-3 规划为「取消」出口，改名要动指标口径；二是「跑完了」与「不看了」本来就是两个视角，靠 `stream_id` 对账即可。

## 9. 风险与开放项 <a id="risk"></a>

| # | 风险 / 开放项 | 处置 |
| --- | --- | --- |
| 1 | `break` 不自动发 RST，调用方漏写 `async with` 就漏取消 | 契约写明 + 用例固定该行为；`RpcStream` 的 docstring 只给 `async with` 一种写法；后续 SDK（8B_03）封装时强制上下文 |
| 2 | `AsgiRpcTransport.open_stream` 是测试专用并发驱动，与真传输行为可能有差 | 关键路径（停推时延、窗口背压）一律在**真机 h2c** 用例里验，ASGI 面只验协议与异常映射 |
| 3 | 读队列无上限 | **实测修正（2026-11-06）**：`connection.py` 在收到 `DataReceived` 时立即 `acknowledge_received_data()`，窗口一直在回补，因此「读得慢 → 窗口不回补」并不成立——客户端不会反向限流服务端（真机用例观测：服务端 30/30 帧时客户端只读了 2 帧）。挡住生产的仍是服务端 `InflightUsage` 双阈值（04-3-1）。**不改 ack 时机**：一元 `wait_response()` 从不 pop 队列，改成「读完再 ack」会让超过窗口的响应永远等不到结束，且与「不动连接层事件分派」冲突。客户端侧真背压（按流记账的 ack 时机）留作后续评估 |
| 4 | 客户端空闲 90s 与服务端 60s 存在 30s 空窗 | 空窗是设计意图（服务端先收尾）；服务端若卡死，客户端 90s 兜底，期间连接仍可用（RST 只作用于本流） |
| 5 | 流式调用的 `deadline_ms` 缺省仍是 30s（构造值） | 长流需调用方显式给更长预算（上限 600s）；04-5 适配时按业务给值，本任务只保证「给了就按给的走」 |
| 6 | 压测脚本仍用 `httpx` | 沿用 04-7-1 遗留，归 8B_12 |
