**为什么拆两段**：传输层（连接 / 流 / 池 / 异常 / 注入面迁移）与取消（把 `task.cancel()` 接到流中止 + 真机验收）改动面与验证方式不同。传输层先独立全绿，取消只是它上面的一层接线与验收；混在一次改动里，失败时的定位面覆盖「新增传输 + 改客户端 + 迁移存量用例」三段。

## 3. 任务内容 <a id="content"></a>

1. **单个 stream 取消**：客户端能在**不关闭整条 h2 连接**的前提下取消一次调用（发 `RST_STREAM(CANCEL)`），同连接其它在途调用不受影响。〔04-7-1 提供原语；04-7-2 接线与验收〕
2. **传输层自持**：客户端侧连接池 / 并发流 / 流生命周期由本任务实现（`h2` 自持连接；实测 `httpx` 取消不发 RST、`httpcore` 无公开的流重置出口），不再依赖「关整个连接池」这种粗粒度手段。〔04-7-1〕
3. **取消与超时分工**：取消发 `RST_STREAM`；预算耗尽仍由服务端回 `350004`（服务端日志 `outcome=cancelled` 与 `deadline_exceeded` 可区分）。〔04-7-2〕
4. **对外契约不变**：`RpcClient.call(service, method, ..., deadline_ms=)` 与 `RpcCallTimeoutError(350004)` 保持不变，04-5 的适配不跟着改；`timeout_ms` 弃用别名在本任务删除（04-5 尚未适配，唯一零成本窗口）。〔04-7-1〕
5. **对接服务端**：命中 04-2 已交付的断开探测（`invoke_rpc(disconnected=...)`），**不改服务端代码**。〔04-7-1 / 04-7-2 均不改〕
6. **测试**：真 h2c 下取消单 stream → 服务端 150ms 内中断（一个轮询周期 + 一帧往返）、同连接其它调用成功；沿用 04-2 的 `serve_service` 体例。〔04-7-2〕
7. **边界**：不改帧 / 契约形状（RST 是传输层事实）；不做流式（04-3）、不做重试（04-4）、不做实例摘除（04-6）。〔全程〕
8. **观测**：取消事件补 `rst_sent`（为 06-3 统一出口留采集点）。〔04-7-2〕

## 4. 完成标准 <a id="accept"></a>

- 取消单个在途调用后，服务端在 **150ms 内**（一个轮询周期 50ms + 一帧往返 + 调度余量；需求原文的 100ms 作观测值）停止处理且未跑完，同连接其它调用正常返回。
- `RpcClient` 对外签名与错误码不变（04-5 适配零改动）；取消后仍以 `CancelledError` 结束。
- 传输层自持且可测：流中止只影响本流、池按 origin 分、`aclose()` 后在途流归零。
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
