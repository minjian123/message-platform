## 2. 背景与范围 <a id="scope"></a>

B6 含两处：

1. **取消只 `cancel()` 不 `await`** —— 已在 04-2 交付时按「必须等清理完成」实现（`_cancel_and_wait`），本轮只补登记，不改代码；
2. **handler 自抛 `TimeoutError` 变 500** —— 现设计与实现都只做「不伪装成预算耗尽」（原样上抛），**没有对外分类**：端点层不认这个异常，落到基座兜底 `10000` / 500。调用方拿不到语义化码，也分不清「本跳没时间」与「下游超时」。

本子任务只做第 2 处：给「handler 自己抛出的超时」一个一等错误码与契约位置。

**不做**：流式 deadline（04-3 边界）、bms 客户端适配（04-5 边界）、重试策略（04-4）。

## 3. 完成标准 <a id="accept"></a>

- handler 自抛 `TimeoutError` 时，HTTP 与帧两种形态都返回 `350034`（504、business、`retryable=false`、`data.outcome=unknown`），不再出现 500 / `10000`；
- 与 `350004`（本跳预算耗尽）在码、指标标签、`data.source` 三处可区分；
- 契约快照、产品错误码登记、前端文案、帧分类集合四处一致，`contract_snapshot check` 零漂移；
- 变更模块行 + 分支覆盖率 100%，静态全绿。

## 4. 边界 <a id="boundary"></a>

| 项 | 处理 |
| --- | --- |
| 流式调用的流内超时 | 归 04-3（流内 `350024` / `350004` 已定），本任务不碰 |
| bms `msgclient` 是否把 350034 映射到 `RpcCallTimeoutError` | 归 04-5 适配面；本任务只保证服务端码与 `layer` / `retryable` 正确 |
| 客户端重试与熔断 | 归 04-4（本码按 business / 不重试参与其既有判定） |
