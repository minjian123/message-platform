## 2. 任务内容 <a id="content"></a>

1. **预算头**：请求头携带**剩余预算（毫秒）**；跨机器不使用「本地超时」或需时钟同步的绝对时间；字段名、编码与缺省值在详细设计定稿。
2. **逐跳扣减**：每跳按「剩余预算 − 排队 / 已处理时间」计算下游预算，留出返回余量；下游只接收剩余预算，不接收原始总超时；预算耗尽立即停止，不进入 handler、不再调下游。
3. **服务端落实**：handler 接收取消令牌；预算到期取消处理任务；释放锁、游标、临时缓冲等资源；错误返回沿用 `350004`（已预留，留给 8B_03 远程调用deadline），并携带已用 / 剩余时间；`retryable` 与「超时未知」语义由 04-4 统一。
4. **取消**：客户端取消通过 HTTP/2 `RST_STREAM` 传递；服务端监听 stream 取消 / 连接断开，取消 handler 任务并向 downstream 继续传播；取消后不再写响应。
5. **尽力而为**：取消不保证副作用回滚，不替代幂等；已完成的副作用由调用方按业务幂等键处理；取消与超时在错误码 / 日志 / 指标上可区分。
6. **客户端 API**：最小 `RpcClient` 以 `deadline_ms` 为主参数（`timeout_ms` 降为 deprecated 别名）；超时、取消、失败返回不同结果；**无在途等待表**——一元调用一 stream 一请求，服务端无跨请求等待状态、客户端由 `httpx` 收口，故「等待表清理」落为「无表可清」+ 三条可测断言（请求结束后长驻流名额恒 0、连接数不随调用次数增长、客户端 `aclose()` 后无遗留任务）。
7. **超时与失败区分**：超时视为「结果未知」，不得等同于「失败」直接重试；是否重试由 04-4 按幂等键与 `retryable` 判定。
8. **测试**：A → B → C 三跳假服务；A 超时后 C 不再长跑；B 预算递减正确；客户端 `RST_STREAM` 后服务端释放资源；连接断开清理等待项；超时 / 失败 / 取消三类结果可区分；真机 h2c 取消验证。
9. **边界**：不做流式 deadline（04-3）、不做重试 / 熔断策略（04-4）、不做 bms 适配（04-5）、不做认证授权（05 域）。

**详细设计**：[01_详细设计_04_远程调用_02_超时传播与取消](设计/01_详细设计_04_远程调用_02_超时传播与取消.md)（21 项决策已逐项确认）

**实施回写（2026-11-06，详见[详细设计](设计/01_详细设计_04_远程调用_02_超时传播与取消.md) §5.4 / §13.2 与[实施记录](实施/01_实施记录_04_远程调用_02_超时传播与取消.md) §7）**：

1. **取消判据改为两路并存**：原定「`CancelledError` 单一判据」经实测推翻——hypercorn 收到 `RST_STREAM` 只投 `http.disconnect`、不取消任务；执行期另加 50ms `is_disconnected()` 轮询。
2. **§2.3 / §2.4 的「精确取消」收口为「预算兜底 + 断开兜底」**：实测客户端栈（`httpx 0.28` / `httpcore 1.0`）在等待响应头期间被取消时**不发 `RST_STREAM`**；客户端发送端能力**立项 [04-7](../04_远程调用_07_客户端精确取消/04_远程调用_07_客户端精确取消.md)**，服务端接收侧已就位、届时零改动。
3. **预算预检插在限流之前**：预算耗尽的请求不进 handler、也不消耗 `(tenant, service)` 配额（否则刷 `deadline_ms=0` 能打穿配额桶）。
4. **§2.6 的「等待表清理」回写为「无表可清」**：一元调用一 stream 一请求，服务端无跨请求等待状态、客户端由 `httpx` 收口；验收改为三条可测断言（长驻流名额恒 0 / 连接数不随调用增长 / `aclose()` 后无遗留任务）。

## 3. 完成标准 <a id="accept"></a>

- 多层调用时下游不会在上游超时后继续长跑；预算逐跳递减可断言。
- 客户端取消后服务端处理中断、资源释放，等待项无泄漏。
- 超时与失败在错误码 / `retryable` 语义上可区分；超时不被直接当作失败重试。
- 变更模块行 + 分支覆盖率 100%，静态检查全绿。
