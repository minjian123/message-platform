**为什么三份文件而不是并进既有文件**：`kiwi_id` 是模块级标注，并进 `test_rpc_client.py` / `test_transport_stream.py`
会把 04-1 / 04-7 的用例号混标成 2438，两边都对不上账。

**为什么切帧与三态用脚本替身**：判据要的是「第几块里有几帧」这种精确时序（一帧跨两块、一次读三帧），
只有 `ScriptedRpcTransport` 能摆出来；真 app 与真 hypercorn 的行为分别由 ASGI 用例与 h2c 文件兜住
（详细设计 §9 风险 2 的处置）。

## 6. 实测观测 <a id="observe"></a>

| 观测项 | 值 | 说明 |
| --- | --- | --- |
| 停推时延（`break` + `async with` 退出 → 服务端生成器收尾） | **0.4 / 0.5 / 0.4 ms**（三次复测） | 判据 ≤150ms；远小于一元那条 50ms 轮询下界——流式每次 `yield` 都要写出，`RST_STREAM` 一到在途写即失败并取消生成器（详见实施记录 §6.4）。收尾时刻用 `finally` 记：取消可能落在 `await`（`CancelledError`）或 `yield`（`aclose()` 的 `GeneratorExit`）上，只认前者会偶发漏记（§6.7） |
| 慢消费时的超前帧数 | 服务端 30/30 帧时客户端只读 2 帧（最大超前 29） | 印证「客户端不另设额度」：读得慢不会反向卡住服务端（客户端侧无端到端背压，见实施记录 §6.6） |
| 空闲兜底 | 注入 20ms → 客户端放弃、`reason=timeout`、`rst_sent=True`、服务端名额归还 | 生产阈值 90s 无法实跑，用注入值验证同一代码路径 |
| 同连接复用 | 流取消后一元 `demo.echo` 仍 `200`，`connections == 1`、`open_streams == 0` | `RST_STREAM` 只作用于本流 |
| 连续推送 | 20 帧逐条到达，payload 与 `seq` 一一对应，收尾在途归零 | 帧序与产出一致（服务端 04-3-1 的 `seq` 契约在客户端被逐帧校验） |
