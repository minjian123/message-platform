## 3. 关键决策落地 <a id="decisions"></a>

### 3.1 设计未写死、由实现补的口径（已回写设计 §5.1 / §5.2 / §5.3 / §4.3）

| 口径 | 为什么 | 落点 |
| --- | --- | --- |
| **收口事件也唤醒读等待者**（`on_end` / `on_reset` / `on_connection_error` 都 `set()` 读事件） | 设计 §5.1 的示例只在 `on_data` 里唤醒；但「没有数据、只有结束」正是末帧之后最常见的一刻——只醒不醒得来看数据，读者会一直睡到调用方自己超时 | `client/transport/stream.py` |
| **空 DATA 帧不排队** | `h2.end_stream()` 会发一个空 DATA 帧（`END_STREAM`），`DataReceived.data` 是 `b""`；排进队列会让 `read()` 先吐一个空块，用例与调用方都得额外过滤。结束由 `on_end()` 单独表达，丢空块不丢信息 | 同上 |
| **非 200 在打开阶段判掉**（`status` 不进 `TransportStream`） | 流端点对帧请求恒回 200（建流前失败也是 `200 + 单帧 error`），非 200 只可能来自路由 / 权限 / 网关——那时响应体不是帧流，交给句柄层只会得到「帧不可解析」这种误导性协议错 | `pool.py::_open_stream()` |
| **切帧缓冲挂句柄，不学伪代码用局部变量** | 设计 §5.3 伪代码里 `buffer` 是 `__anext__` 的局部量；但循环会在「本批已产出一帧」时 `return`，尾部的半帧随之丢失，下一块到达时帧头已错位 | `client/stream.py` |
| **读中传输层错误按层映射**（`RpcTransportError` → `layer=transport`、`RpcTransportProtocolError` → `layer=protocol`） | 设计 §4.3 只写了「EOF 无收尾 → `protocol`」；对端 reset / 连接故障是另一类事实，混成 `protocol` 会让排障分不清「协议坏了」还是「连接断了」 | 同上 |

## 6. 问题与处置 <a id="issues"></a>

### 6.1 `bytearray` 不能在有导出视图时缩容

切帧缓冲一开始用 `bytearray` + `del buffer[:consumed]`（与 `decode_frames` 的注释一致）。实测直接抛
`BufferError: Existing exports of data: object cannot be resized`：`Frame.payload` 是缓冲的 `memoryview`
切片，只要 `FrameBatch` 还活着，扩容 / 缩容就非法。

**处置**：缓冲改 `bytes`，消费用 `buffer = buffer[consumed:]`（切片另开一块，旧块由视图继续引用）。
代价是每块一次尾部拷贝（尾部通常不足一帧），换来「帧视图与缓冲生命周期解耦」。

### 6.2 设计 §5.3 伪代码的局部 `buffer` 会丢半帧

伪代码在 `__anext__` 里 `buffer = bytearray()`，循环内「已产出至少一帧即 return」。第一块若是半帧
（帧头都不完整），`return` 后局部缓冲随之丢弃，第二块到达时帧头已错位 —— 表现为「seq 从 1 开始」或
「帧不可解析」。用例 `test_frame_across_two_chunks_is_reassembled`（把两帧切在偏移 5）正是这条。

**处置**：缓冲挂到句柄（`self._buffer`），跨 `__anext__` 保留；设计 §5.3 已回写。

### 6.3 空 DATA 帧让 `read()` 先吐一个空块

`h2.end_stream()` 的线上形态是「空 DATA + `END_STREAM`」，客户端 `DataReceived.data == b""`。若照单
入队，`read()` 会先返回 `b""` 再返回 `None`，`test_stream_reads_chunk_by_chunk_until_end` 第一次就撞上。

**处置**：`on_data` 丢弃空块（结束由 `on_end()` 单独表达），设计 §5.1 已回写。

### 6.4 流式停推走的是「写失败即取消」，不是一元那条 50ms 探测

04-2 / 04-7-2 的停推时延下界由 50ms 断开探测决定，实测 51.8~55.2ms。流式的实测是 **0.4~0.5ms**：
服务端每次 `yield` 都要过 h2 状态机写出，`RST_STREAM` 一到，在途写立刻失败并取消生成器（03-1 的
「写失败才取消生成器」路径），根本轮不到轮询。

**处置**：不改代码（两条路径各自成立），在测试记录里写明「流式判据实际远严于 ≤150ms」；这也解释了
为什么流式取消不需要额外等一个轮询周期。

### 6.5 覆盖率首轮缺 7 行 / 5 分支，三处都是「不可达或可归一」

| 缺口 | 性质 | 处置 |
| --- | --- | --- |
| `client/stream.py` 循环内 `if self._ended` | 不可达：末帧一定先入 `_pending` 再置位，`pending` 空 + `ended` 只可能出现在下一次 `__anext__` 的入口 | 删掉该判断（入口已判），留注释说明顺序依赖 |
| `pool.py` 两处 `if opened:`（超时 / 其它异常） | 同一个 `if` 的两份拷贝，各要 True / False 两支 | 合并成一个 `except BaseException`：先 `abort` 再按 `isinstance(exc, TimeoutError)` 分流；`for candidate in opened` 替掉 `if opened` |
| `transport/stream.py` 的 `raise self._error or …` 与 `abort()` 里 `if self._error is None` | 右支 / False 支不可达（`sent` 为真即流还在表里，不可能已有错误；HTTP/2 也不允许无响应头即结束） | 改成单条件（`if self._error is not None: raise`）与直接赋值，去掉死分支 |

补了 3 条用例覆盖「已关闭」「打开超时」「打开期对端 reset」三条真实路径后归零。

### 6.6 客户端「窗口不回补」不成立（口径与实现的因果需修正）

决策 6 写的是「客户端读得慢 → 窗口不回补 → 服务端写阻塞」。实测口径与实现对不上：
`connection.py` 在**收到** `DataReceived` 时立刻 `acknowledge_received_data()`（04-7-1 就那样写，本任务
未动它），窗口因此一直在回补，客户端不会因为「读得慢」反向卡住服务端；真正挡住生产的仍是服务端那一侧的
`InflightUsage` 双阈值（04-3-1）。

**为什么不改成「读完再 ack」**：一元路径 `wait_response()` 只等 `END_STREAM`、从不 pop 队列，改成读完
再 ack 会让 > 窗口的响应（如 200 KB 用例）永远等不到结束；这与「不改连接层事件分派」的设计约束也冲突。

**处置**：本任务按「不另设额度」实施（读队列不设上限，注释写明前提），把偏差登记到设计 §9 风险 3，并
把真机用例改成断言**当前实现的真实行为**（客户端不反向限流、按序收全）。端到端背压若将来要做，需要
「按流记账的 ack 时机」——归 8B_12 与 04-6 之后单独评估。

### 6.7 服务端「停推」有两条路径，`except CancelledError` 会偶发不命中

真机用例第一次跑（单独跑）稳定通过，进提交前预检的并行档（`-n auto`）后偶发失败：客户端已记
`msg_rpc_client_cancel(reason=cancelled, rst_sent=True)`、服务端已记 `msg_rpc_stream(outcome=cancelled)`，
但用例里那个「被取消时记时刻」的 `except asyncio.CancelledError` 没命中。

根因是服务端取消落点不唯一：处理器挂在 `await` 上时抛 `CancelledError`；挂在 `yield` 上（`open_rpc_stream`
手上正握着已产出的一帧）时，收口走的是 `_close_iterator()` → `aclose()`，抛的是 `GeneratorExit`。
并行档下「停在 yield 上」的窗口更容易被撞上。

**处置**：用例改用 `try/finally` 记收尾时刻（两条路径都会走到），断言改为「生成器收尾时刻 ≤150ms +
产出冻结」，语义仍是「服务端停止产出」，且不再依赖取消落点。这不是实现缺陷——两条路径都是「停止推流」的
正确形态，只是**用例不能只认其中一条**。

## 7. 偏差与遗留 <a id="leftovers"></a>

**偏差（均已回写设计）**：

1. 设计 §5.1 只写「`on_data` 唤醒读者」；实现必须让**收口事件也唤醒**，否则末帧后读者会睡到超时。
2. 设计 §5.3 伪代码的局部 `buffer` 会丢跨块半帧；实现把缓冲挂到句柄。
3. `status` 不进 `TransportStream`：非 200 在打开阶段判掉（口径与「传输层不解释业务」并不冲突——非 200
   在这里不是业务结果，而是「这条路根本不是帧流」）。
4. 读中传输层错误按 `transport` / `protocol` 分层映射（设计 §4.3 只覆盖 EOF 无收尾）。
5. 决策 6 的「窗口不回补」与实现不符（见 §6.6），已在设计 §9 风险 3 记录。

**遗留**：

| # | 遗留 | 归口 |
| --- | --- | --- |
| 1 | 客户端读队列无上限，长流的在途量只会被服务端双阈值与服务端侧窗口约束；「客户端侧真背压」需改为按流记账的 ack 时机 | 8B_12 / 后续 |
| 2 | `break` 不自动发 `RST_STREAM`（语言层不通知迭代器）——已在契约与用例固定，SDK 封装必须强制 `async with` | 8B_03 |
| 3 | 流式 `deadline_ms` 缺省仍是 30s（构造值）；长流需调用方显式给更长预算（上限 600s） | 04-5 按业务给值 |
| 4 | 客户端只有 `msg_rpc_client_stream` / `msg_rpc_client_cancel` 两条日志事件，指标出口未定 | 06-3 |
| 5 | 空闲兜底阈值 90s、慢消费下的内存曲线未压测 | 8B_12 |
