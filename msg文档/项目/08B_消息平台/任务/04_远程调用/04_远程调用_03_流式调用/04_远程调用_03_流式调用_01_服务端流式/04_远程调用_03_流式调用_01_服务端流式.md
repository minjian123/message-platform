## 2. 任务内容 <a id="content"></a>

1. **形态**：首期只做 **server streaming**（一次请求、多次响应）；client streaming 与双向流后置；端点 `POST /rpc/{service}/{method}/stream`，**只接帧形态**（`application/x-msg-frame`），JSON 请求明确拒绝（`10001`）。
2. **流帧**：沿用 `FrameType.RPC = 48` + `flags.response`，**末帧置 `flags.end_of_stream`**（03-2 已预留该位、至今未启用）；响应序号放帧头 `seq`（0 起、逐帧 +1），payload 仍是「结果原始字节」。不新增帧类型号、不动 `reserved_types`。
3. **结束三态可区分**：正常结束 = 收到带 `end_of_stream` 的 `48` 帧；异常结束 = 收到 `ERROR` 帧（`code` / `layer` / `retryable` / `detail`）；无收尾帧即断流 = 客户端可判「异常中断」。
4. **流内错误**：流建立之后的错误一律用 `ERROR` 帧表达，HTTP 状态码只用于「流建立前的失败」；不得把 200 当成功。
5. **背压**：h2 窗口（`yield` → ASGI `send` 被 `hypercorn` 的 `StreamBuffer` 高水位挡住）+ 应用层 inflight 双阈值（条数 / 字节，「已产出未写出」的帧计入在途）；超限**暂停产出**、不返错误；不得无界缓冲。
6. **半开流**：流层空闲超时（连续 `RPC_STREAM_IDLE_MS` 无帧写出即结束流并发 `350024`）；连接层心跳仍由 03-4 负责（10s / 30s），两层互不计入对方的计时。
7. **deadline 与取消**：整条流共享 04-2 的 `Deadline`，每次产出前判剩余预算，耗尽发 `350004` 帧并结束；客户端取消沿用 04-2 的 `is_disconnected` 50ms 轮询与 `CancelledError` 快路径，命中即 `_cancel_and_wait` 并释放。
8. **注册表扩展**：新增 `RpcStreamHandler` 协议与 `RpcRegistry.register_stream()`；同一 `(service, method)` 只能是一种形态（unary 或 stream），冲突即拒启。
9. **配额与名额**：配额沿用 04-1 的 `(tenant, service)` 令牌桶（流式与一元同一本账）；每条流占**一个单连接长驻流名额**（03-4 的 `350021` 判据），`finally` 归还。
10. **观测**：新增服务端事件 `msg_rpc_stream`（`outcome` / `frames` / `bytes` / `duration_ms` / `seq_max`），与 `msg_rpc` 分工明确（一个一元、一个流式）。
11. **契约**：`x-msg-frame.rpc` 增 `stream` 段（端点 / 结束位 / `seq` / 空闲阈值 / 流内错误码），公开契约 `paths` +1；新增 `350024`（business / 不重试）并五处对齐。

## 3. 完成标准 <a id="accept"></a>

- 服务端流可连续推送 N 帧：`seq` 从 0 单调递增、末帧置 `end_of_stream`、帧序与 handler 产出序一致。
- 背压生效：慢消费者时 handler 的「已产出未写出」帧数不超过 inflight 阈值，内存不随发送量增长（用例可断言，不靠观测）。
- 流内错误可被识别：未注册方法（`350023`）、预算耗尽（`350004`）、空闲超时（`350024`）、业务错误（原码）都以 `ERROR` 帧收尾，且与「正常结束」可区分。
- 半开流在空闲超时后释放：流登记与连接名额归还，handler 被取消且不等满预算。
- 客户端取消（`RST_STREAM`）后服务端在 ≤150ms 内停止产出（沿用 04-7 判据），同连接其它调用不受影响。
- 非帧请求 / 超限参数 / 超额调用分别返回 `10001` / `350006` / `350005`，与一元端点同码同层。
- 变更模块行 + 分支覆盖率 100%，静态检查全绿，文档三项（links / docs-scope / eol）通过。
