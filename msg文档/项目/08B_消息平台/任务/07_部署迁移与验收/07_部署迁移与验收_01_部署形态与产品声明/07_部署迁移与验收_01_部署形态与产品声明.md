## 3. 任务内容 <a id="content"></a>

1. **单服务形态**：`msg` 以单服务容器部署，容器内端口 8000，接入平台 Docker 网络（`PLATFORM_NETWORK`）；镜像由 `MSG_REGISTRY_IMAGE_PREFIX` + `MSG_TAG` 显式指定，禁止 `latest` 兜底。
2. **产品声明**：`deploy/registry/msg.toml` 保持七段完整（产品档案 / 服务行 / 产品路由 / 数据源 / 能力 / 种子 / 错误码），经平台装载校验后产品、服务行与路由可识别；对外命名空间 `/api/msg/v1/msg/...`，内部前缀 `/api/v1/msg/...`，网关按服务目录路由到 `msg:8000`。
3. **三样持久化**：消息日志、位点文件、元数据库必须持久化——消息日志挂独立卷（不与系统盘 / 容器可写层混放），位点文件与 `data/` 平级，元数据库随平台库；容器重启后数据不丢。
4. **探针口径**：统一使用基座共享应用挂载的 **`/healthz`**（存活）与 **`/readyz`**（就绪）；就绪探针必须检查「能写」——元数据可达、日志目录可写、存储水位未超拒绝阈值，不能只检查进程存活。
5. **升级与回滚**：先 GOAWAY 再停（停止接新流、等在途完成），一次只替换一个实例；保留上一版本镜像与配置；日志格式只增不删，回滚后旧版本必须能读新数据。
6. **边界**：不修改基座网关 / 认证 / Redis / MySQL / 可观测后端；不在 msg 仓部署基座基础设施；不实现多实例分区迁移（归 8B_05）；容器内 TLS 终止是否启用按架构 08 §11 待定项，由详细设计定稿后再实施。
7. **测试**：`docker compose config` 解析、镜像 tag 必填、卷挂载与端口断言、健康 / 就绪正反用例（可写 / 磁盘满 / 元数据不可达）、重启后三样数据保留、优雅关闭与 drain；变更模块行 + 分支覆盖率按项目口径达标。

## 4. 完成标准 <a id="accept"></a>

- `deploy/compose/msg.yml` 与 `deploy/Dockerfile` 可从工作区根构建并启动，容器加入平台网络，容器内 8000 可访问；
- 平台装载 `msg.toml` 通过，产品 / 服务行 / 产品路由可识别，网关可路由到 `msg:8000`，对外与内部命名空间一致；
- 消息日志、位点文件、元数据库三样均持久化，容器重启后数据不丢；
- `/healthz` 正确反映进程存活，`/readyz` 正确反映可写性（元数据不可达、日志不可写、水位超拒绝阈值时返回 503）；
- 升级 / 回滚流程文档化，并完成一次单实例替换与回退演练；
- 变更模块行 + 分支覆盖率达标，静态检查与文档校验全绿。
