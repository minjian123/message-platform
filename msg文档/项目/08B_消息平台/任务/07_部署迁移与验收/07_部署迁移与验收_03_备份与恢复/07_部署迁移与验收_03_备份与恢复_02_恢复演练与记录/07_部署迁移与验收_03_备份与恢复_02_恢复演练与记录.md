## 2. 任务内容 <a id="content"></a>

1. **恢复演练流程**：在隔离环境按「停服务 → 恢复元数据库 → 恢复位点快照 → 确认消息日志段 → 启动并对齐 → 校验」执行；每一步记录命令、耗时与结果，不跳步。
2. **恢复顺序与对齐**：元数据库先于位点、位点先于服务启动；日志缺失时从最近可用段开始，并显式登记「缺口范围」；启动后由 02-3 的位点对齐协议保证位点不越过日志尾，02-7 重建延迟区并按剩余时间投递。
3. **校验项**：表集合与 manifest 一致；位点文件校验和一致；分区 LEO 与位点关系合法；已确认消息抽样可读；未到期延迟消息不提前、不丢；消费组位点可继续消费。
4. **失败分支**：位点快照缺失 / 损坏、元数据库恢复不完整、日志段缺口、恢复中途失败——每种给出处置与回退到上一份备份的路径，不允许「部分恢复后直接接流量」。
5. **演练记录**：固定字段——环境、版本、配置版本、备份时间、恢复开始 / 结束、RTO / RPO、数据完整性结论、失败注入、问题与处置、遗留与归口；记录随任务 `测试/` 留痕。
6. **可重复**：恢复脚本参数化（备份目录、目标环境、是否演练模式），同一份备份可重复演练；演练前自动备份、演练后清理隔离环境，不污染共享数据。
7. **边界**：不在生产环境做破坏性恢复；不自动执行数据库 downgrade；不把消息日志全量复制当恢复手段。
8. **测试**：一次完整恢复演练；位点越尾、日志缺口、快照损坏三类失败分支；恢复后延迟消息校验；脚本重复执行结果一致。

## 3. 完成标准 <a id="accept"></a>

- 可按「元数据库 → 位点文件 → 消息日志 → 校验对齐」完成一次完整恢复演练；
- 恢复后位点与日志对齐，已确认消息不丢，未到期延迟消息按剩余时间投递；
- 位点快照缺失 / 损坏、日志缺口、恢复中途失败均有处置与回退路径；
- 演练记录含环境、版本、配置、RTO / RPO、数据完整性结论、问题与遗留；
- 恢复脚本可重复执行，演练前后不污染共享环境；
- 变更模块行 + 分支覆盖率按项目口径达标，静态与文档校验全绿。

## 5. 前置契约（已交付） <a id="contract"></a>

07-3-1 已交付备份侧产物，恢复演练按下列契约消费；字段与目录形态的权威说明见 [07-3-1 详细设计](../07_部署迁移与验收_03_备份与恢复_01_备份脚本与调度/设计/01_详细设计_07-3-1_备份脚本与调度.md)。

| 契约 | 口径 |
| --- | --- |
| 快照目录 | 备份根下以 UTC 备份标识命名的目录，内含 `manifest.json` 与 `offsets/`；位点文件相对路径与源目录一致 |
| 最新可用 | 备份根的 `current.json` 指向最新可用备份标识；恢复侧只认含完整清单的目录，不认写入期临时目录 |
| 元数据库 | `metadata.source = platform_database_backup`，`tables_expected` / `tables_in_dump` / `covered` 供恢复前核对表集合完整 |
| 位点校验和 | `offsets.files` 逐项给 `path` / `size` / `sha256`；恢复侧按同一份清单逐文件复算，不一致即判快照损坏 |
| 日志摘要 | `log_segments.backed_up = false`；`partitions[].segment_bases` / `leo` / `leo_source` 给出段范围与日志末端，`needs_alignment` 列出恢复点不可用、须按最近可用段对齐的分区 |
| 恢复顺序 | `recovery_order`：元数据库 → 位点文件 → 消息日志 → 校验对齐 |
| 版本与配置 | `service` 给服务版本与契约版本，`config_version` 给四份配置的内容摘要，供演练记录填写版本字段 |
| 失败与清理 | 失败只删写入期临时目录；最新一份与指针所指目录永不删除，回退到上一份备份的路径始终存在 |
