## 2. 落实的口径 <a id="decisions"></a>

| 口径 | 落实方式 |
| --- | --- |
| 立项形态 | 03-6 的嵌套子任务 03-6-1，不新增需求（需求计数仍为 48） |
| 通道选择 | `MessagingTransport` 由具体类改为契约（`Protocol`），落 `FrameTransport` / `JsonTransport` 两个实现，`MessagingConfig.channel` 决定构造时用哪个（缺省 `FRAME`）；运行期切换不做 |
| 对外签名 | `MsgProducer.publish` / `publish_many`、`MsgConsumer.join` / `poll` / `ack` / `ack_many` / `nack` / `heartbeat` / `close` 与全部返回模型一字未改 |
| 请求形态 | 业务字段进帧头（`request_id` 由通道现生成）、消息体走 payload 段；帧头不放 `payload` 键 |
| 响应还原 | 结果帧按请求类型分派还原成 `ApiOutcome.data`；`consume` 按 `messages[i].length` 切片，切片另挂 `ApiOutcome.payload_segments` |
| 幂等键 | 落帧头 `headers["x-msg-idem-key"]`，与 JSON 请求体的 `headers` 同构 |
| 成员端点 | `join` / `heartbeat` / `leave` 无帧类型，请求以 `frame_type=None` 表达，由帧实现委托内部 JSON 实现（共享同一 httpx 客户端） |
| 承载 | 沿用 httpx 发二进制 POST，帧编解码用基座 `msgclient/frame.py`；不复用 RPC 的 HTTP/2 自持连接 |

## 3. 代码改动 <a id="code"></a>

| 模块 | 内容 |
| --- | --- |
| `messaging/transport.py` | 新增 `ApiRequest`（`frame_type` 可空 = 该端点无帧形态）、`ApiOutcome.payload_segments`、`MessagingTransport` 契约；两个实现共用的 `HttpxChannel` 父件（超时 / 请求头 / 关闭 / 异常三分类翻译）与 `to_wire` 序列化边界 |
| `messaging/transport_json.py` | 原 JSON 实现迁入（行为不变：字段摊平 + 消息体 base64 + 统一响应体解析 + `Retry-After` 两来源） |
| `messaging/transport_frame.py` | 帧实现：编帧（`request_id` + 字段 + payload）、响应解码（结果帧 / 错误帧分派）、`length` 切片与长度校验、网关非帧响应的 JSON 兜底、编码期超限转参数错误 |
| `messaging/transport_factory.py` | `build_transport(config, client=None)` 按 `channel` 造实现（单独一层避免契约与实现互相 import） |
| `messaging/config.py` | 新增 `TransportChannel` 与 `channel` 字段（缺省帧）；字符串形态规整成枚举，非法取值构造期 `ParamError` |
| `messaging/producer.py` | `body()` 改为 `request()` 返回 `ApiRequest`；幂等键写进 `fields["headers"]` |
| `messaging/consumer.py` | 各端点构造 `ApiRequest`；`poll` 优先用 `payload_segments`、否则解 base64；成员端点路径修正为 `/msg/join`、`/msg/heartbeat`、`/msg/leave` |
| `messaging/__init__.py` | 出口补 `ApiRequest` / `TransportChannel` / `FrameTransport` / `JsonTransport` / `build_transport` |
| `tests/msgclient/messaging/_support.py` | 假服务端与通道无关化：脚本只写业务数据，按请求形态回帧或回 JSON；`fields()` / `payload()` 把两种请求形态抹平成同一视图 |
| `tests/msgclient/messaging/test_producer.py`、`test_consumer.py`、`test_transport.py` | 整组按通道参数化（`channel` 夹具），断言改走 `fields()` / `payload()`，同一份断言跑两遍 |
| `tests/msgclient/messaging/test_transport_frame.py` | 新增（Kiwi 2513）：请求形态、切片重组、四类装配错误、错误帧还原、网关兜底、编码期拒收、成员端点委托 JSON、工厂选实现 |
| `tests/msgclient/messaging/test_transport_json.py` | 新增：JSON 通道专属（base64 请求体、`data.retry_after_ms` 回落、三种不合法响应、脏元素跳过） |
| `bms文档/后端基类清单.md` | `msgclient/messaging/` 行补登本次新增对外名 |

## 4. 偏差 <a id="deviation"></a>

| # | 设计原文 | 实施口径 | 原因 |
| --- | --- | --- | --- |
| 1 | §3.2 `ApiRequest.frame_type` 为整数 | 改为可空（`int \| None`），空值即「该端点无帧形态」 | 成员三端点没有帧类型，若不表达「无帧形态」，帧实现无从判定该委托 JSON |
| 2 | §4.3 「空批时 `payload` 必为空」直接由服务端保证 | 客户端另校验 `Σ length == len(payload)`，不符判对端装配错误 | 静默按错位切分会把「A 的载荷给 B」，比报错危险得多 |
| 3 | §4.6 编码期超限给 `350006` / 参数错误 | 同设计；另把版本 / 结构类编码失败统一按 `350018` + 参数错误处理 | 都是「请求未发出」，调用方处理方式一致，不必分两套 |
| 4 | §7 成员端点路径修正 | 同设计；另在用例里补「成员端点打到真实路径且内容类型为 JSON」的断言 | 该缺陷正是因为只有 Mock 断言、没有形态断言才漏到交付后 |
| 5 | §10.1 公共组含「消费：`join` → `poll` → `ack` → `nack` → `heartbeat` → `close`」 | 拆成多条小用例（各自独立可定位），未合并成一条长链 | 一条长链失败时无法判断哪一步坏了，且步骤间会互相掩盖错误 |

## 5. 未完成与遗留 <a id="leftovers"></a>

| # | 项 | 归口 |
| --- | --- | --- |
| 1 | 成员三端点（`join` / `heartbeat` / `leave`）帧形态：同一次会话混合两种承载 | 需给 03-2 增 JOIN / LEAVE 帧类型（服务端改动），不在本子任务 |
| 2 | 服务端发布幂等：幂等键只随消息头下发，跨进程去重仍无抓手 | 需新需求（服务端去重），03-6 风险 R3 延续 |
| 3 | 订阅长驻流消费（SSE / 帧流） | 后续子任务 |
| 4 | 帧通道真机复跑（多实例切主后自动改投的真实判据） | 部署阶段，与台账 #43 同批 |

| 6 | 客户端本地载荷上限前置校验（现在只在编码期拒收） | 若要求「发布前给出明确参数错」，可在生产端加校验，属行为变更 |
