## 2. 背景与范围 <a id="scope"></a>

03-6 首发时走 JSON 数据面，原因是当时帧错误帧不携带异常 `data`（`350033` 的 `leader` / `epoch` 拿不到，切主改投无从谈起）。该前置已由 `msg` 仓 `1ea1005` 解除：三处错误帧均随附 `detail`，并顺带修掉「126 位雪花 ID 超出 MessagePack `uint64` 上限导致整帧装配失败」。

本子任务把 SDK 的传输层从 JSON 换成帧形态，**对外方法签名与返回模型一律不变**（`MsgProducer.publish` / `publish_many` / `MsgConsumer.join` / `poll` / `ack` / `ack_many` / `nack` / `heartbeat` / `close`）：

1. 请求字段从请求体搬到帧头，消息体直接走 payload 二进制段（不再 base64）；
2. 响应从帧头还原成 `ApiOutcome.data`，拉取的消息体按 `messages[i].length` 从 payload 切片重组；
3. 通道做成契约 + 两个实现，`MessagingConfig.channel` 只决定构造时用哪个，**默认帧**、JSON 保留为可选中实现；
4. 顺手修正已交付的成员端点路径缺陷（`/msg/groups/*` → 服务端实际的 `/msg/*`）。

**不做**：给成员三端点（`join` / `heartbeat` / `leave`）新增帧类型（服务端无 JOIN / LEAVE 帧类型，帧闸门只挂数据面四端点）；订阅长驻流消费；位点回退；服务端发布幂等；复用 RPC 的 HTTP/2 自持连接。

## 3. 完成标准 <a id="accept"></a>

- 默认配置下生产端与消费端全部走帧形态，`msg` 仓源码零改动；
- 两条通道参数化跑**同一组**用例，公共断言完全相同（请求业务字段、payload 字节、回执、错误分类一致）；
- `350033` 在帧通道下仍能从 `detail` 取到 `leader` / `epoch` 完成改投；
- 拉取到的消息体是原始字节，与 JSON 通道逐字节相同；
- 成员端点路径与服务端一致（真机联调不再 404）；
- 变更模块行 + 分支覆盖率 100%，静态检查与文档校验通过。

## 4. 边界 <a id="boundary"></a>

| 项 | 处理 |
| --- | --- |
| 成员三端点（`join` / `heartbeat` / `leave`） | 继续走 JSON：服务端只有 JSON 形态（`FrameType` 无 JOIN / LEAVE），设计登记为遗留 |
| 服务端发布幂等 | 本子任务不引入；幂等键随消息头下发，仍只是「消费侧可见 + 本地表」 |
| 订阅长驻流（SSE / 帧流） | 归后续子任务，本子任务只有拉取循环 |
| 网关拦截返回的非帧响应 | 帧通道兜底按 JSON 统一响应体解析；都不合法按「对端不是本服务」处理 |
