## 1. 现状核对 <a id="facts"></a>

| # | 现状 | 位置 | 对本设计的影响 |
| --- | --- | --- | --- |
| 1 | 传输层只有一个 JSON 实现，生产端 / 消费端直接依赖具体类 | `msgclient/messaging/transport.py`、`producer.py`、`consumer.py` | 需要先抽契约、再落两个实现，调用方只依赖契约 |
| 2 | 请求体由生产端组装成内置 `dict`，消息体 `base64` 进 `body["payload"]` | `producer.py::body` | 「字段搬帧头」= 同一份字段换承载，组装口径应只在通道实现里分叉 |
| 3 | 幂等键写进请求体的**消息头** `headers["x-msg-idem-key"]`，**不是** HTTP 头；服务端发布路径不读它（`msg` 仓全仓无读取方，`rpc/idempotency.py` 只服务 04-4 RPC） | `producer.py:337-339` | 帧通道把它落帧头 `headers` 映射即与 JSON 同构；「HTTP 头」前提不成立，设计按帧头写 |
| 4 | 帧闸门只挂数据面四端点（`publish` / `consume` / `ack` / `nack`）；`FrameType` 无 JOIN / LEAVE，成员三端点只有 JSON | `msg` 仓 `api/frame/routes.py::mount_data_plane`、`api/data/groups.py`、`bms_core/msgclient/frame.py::FrameType` | 「换帧通道」只覆盖四端点；成员端点留 JSON，混合形态要在设计写清 |
| 5 | 消费端成员端点常量是 `/msg/groups/{join,heartbeat,leave}`，服务端实际是 `/msg/join`、`/msg/heartbeat`、`/msg/leave`（`msg` 仓 `config.toml` 白名单同为 `/api/v1/msg/join`） | `consumer.py:40-53` vs `msg` 仓 `api/data/groups.py` | 已交付缺陷：用例用 `MockTransport` 按常量路径脚本化，真机必 404；本子任务一并修正 |
| 6 | 结果帧：`publish` 六字段全在帧头；`consume` 在 header 给 `count` / `messages`（每条带 `length`）/ `paused` / `inflight_*`，payload 是各消息体按序拼接；`ack` / `nack` 给 `committed_offset` | `msg` 仓 `api/frame/responses.py::result_frame` | 响应还原按帧类型分派；消息体按 `length` 切片，不做整包重排 |
| 7 | 错误帧头带 `code` / `message` / `retryable` / `layer` / `category` / `detail` / `retry_after_ms` | 同上 `error_frame`（`1ea1005` 起带 `detail`） | `data` 取 `detail`；`retryable` / `category` **不读**——码表仍是唯一判定出处 |
| 8 | 帧请求必填 `request_id`，且「键在而值非法」是 `10001`、「缺键」是 `350018`；帧头出现 `payload` 键直接被拒 | `msg` 仓 `api/frame/gate.py::build_frame_gate` / `_model_input` | 消息体只能进 payload 段；`request_id` 由通道生成 |
| 9 | 基座 `encode_frame` 对 header > 64 KiB、payload > 1 MiB 抛 `MsgPayloadTooLargeError`（`350006`） | `bms_core/msgclient/frame.py` | 超限在**编码期**就拒（请求未发出），类别与远端拒绝不同，需在失败分支写明 |

## 3. 通道契约与模块划分 <a id="contract"></a>

### 3.1 模块划分 <a id="layout"></a>

```text
backend/libs/bms_core/src/bms_core/msgclient/messaging/
├── __init__.py            # 对外出口：增 TransportChannel / ApiRequest / JsonTransport / FrameTransport / build_transport
├── config.py              # 增 channel 字段（缺省 FRAME）+ 构造期校验
├── codes.py               # 不动（码表仍是错误分类唯一出处）
├── errors.py              # 不动
├── transport.py           # 契约与值对象：ApiRequest / ApiOutcome / MessagingTransport（Protocol）+ 两个实现共用的 httpx 父件 HttpxChannel
├── transport_json.py      # JsonTransport（原 transport.py 的实现迁入，行为不变）
├── transport_frame.py     # FrameTransport（新增；成员端点请求委托内部 JSON 实现）
├── transport_factory.py   # build_transport(config, client) 按 channel 造实现（单独一层避免契约与实现互相 import）
├── producer.py            # 构造 ApiRequest；幂等键落 headers；改投 / 退避逻辑不动
├── consumer.py            # 构造 ApiRequest；按 segments 取 payload；成员端点路径修正
└── stats.py               # 不动
```

**为什么契约用 `Protocol` 而不是抽象基类**：与基座 RPC 传输同一形态（`msgclient/transport/base.py::RpcTransport` 是 `Protocol`，生产实现 `H2Transport(BaseFrameworkObject)`）；两个实现照样继承 `BaseFrameworkObject`，基类体系不受影响。

### 3.2 值对象 <a id="values"></a>

**`ApiRequest`（一次业务请求的通道无关表达）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `frame_type` | 整数或空 | `PUBLISH` / `CONSUME` / `ACK` / `NACK`；**空表示该端点没有帧形态**（成员三端点），帧实现会把这类请求交给 JSON 实现 |
| `path` | 字符串 | 端点路径（如 `/msg/publish`），两通道一致 |
| `fields` | `ConcurrentStableFrozenDict[str, object]` | 业务字段（命名空间 / 主题 / 分区 / `headers` / `acks` …），**不含 `payload`** |
| `payload` | 字节 | 消息体原始字节（仅 `publish` 非空） |

**`ApiOutcome`（解析成功的响应；业务成败看 `code`）** —— 在 03-6 三字段基础上**增一个字段**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` / `message` / `data` / `retry_after_ms` | 同 03-6 | 语义不变 |
| `payload_segments` | `ConcurrentStableFrozenList[bytes]` | **新增**：`consume` 每条消息体的原始字节，与 `data["messages"]` 按下标一一对应；JSON 实现恒为空列表 |

**不变量**：`payload_segments` 非空时，长度必须等于 `data["messages"]` 的长度，且各段之和等于帧 payload 总长（不符即按「对端不是本服务」处理）。

### 3.3 契约方法 <a id="methods"></a>

| 方法 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| `headers()` | — | `ConcurrentStableDict[str, str]` | 租户 → 自定义头 → 鉴权，后者覆盖前者；两实现共用同一份规则 |
| `post(endpoint, request)` | 服务地址、`ApiRequest` | `ApiOutcome` | 发一次请求并解析；传输异常按「未发出 / 结果未知」两类翻译 |
| `close()` | — | 无 | 关闭底层客户端（幂等） |

**签名变更说明**：03-6 的 `post(endpoint, path, body)` 改为 `post(endpoint, request)`——请求的业务字段与消息体原本混在一个内置 `dict` 里，帧通道需要两者分开承载。这是**内部件**变更（`MsgProducer` / `MsgConsumer` 对外方法一字未改），且 03-6 未对外发布，登记在 §13。

### 3.4 工厂与配置 <a id="factory"></a>

| 项 | 口径 |
| --- | --- |
| `TransportChannel` | 枚举：`FRAME = "frame"`、`JSON = "json"` |
| `MessagingConfig.channel` | 缺省 `FRAME`；构造期校验必须是 `TransportChannel` 成员，否则 `ParamError` |
| `build_transport(config, *, client=None)` | 按 `config.channel` 返回 `FrameTransport` / `JsonTransport`；`client` 供用例注入 `MockTransport` |
| 调用方 | `MsgProducer` / `MsgConsumer` 构造签名不变，仍接收一个 `MessagingTransport`；用哪个实现由装配处（或 `build_transport`）决定 |

## 4. 帧通道实现口径 <a id="frame"></a>

### 4.1 请求组装 <a id="frame-request"></a>

| 项 | 口径 |
| --- | --- |
| 媒体类型 | `Content-Type: application/x-msg-frame`（服务端据此判「这是帧请求」） |
| 帧头 | `request_id`（必填）+ `fields` 全部键值，一律原样透传（服务端按请求模型白名单取，未知键忽略） |
| `request_id` | 缺省 `uuid4().hex`；可注入 `request_id_factory` 以便用例断言 |
| payload 段 | `publish` 放消息体原始字节；`consume` / `ack` / `nack` 必须为空（服务端会拒非空） |
| 标志位 | `NEED_RESPONSE`（服务端据此对未知类型回错误帧而不是空 200）；`publish` 且声明压缩时另置 `COMPRESSED`，与服务端 `flags.compressed` 与 `compression` 自洽校验对齐 |
| HTTP 头 | 仍带 `X-Tenant-ID` 与鉴权头（中间件按 HTTP 头解析租户）；帧头 `tenant` **不写**（写则必须与请求身份一致，多一处不一致就多一条失败分支） |

**字段落点对照（同一 `fields` 换承载）**

| 业务字段 | JSON 通道落点 | 帧通道落点 |
| --- | --- | --- |
| `namespace` / `topic` / `group` / `consumer_id` / `partition` / `offset` / `acks` / `max_messages` / `max_wait_ms` / `key` / `delay_level` / `content_type` / `compression` / `trace_*` / `reason` | 请求体同名键 | 帧头同名键 |
| `headers`（含 `x-msg-idem-key`） | 请求体 `headers` 映射 | 帧头 `headers` 映射 |
| 消息体 | 请求体 `payload`（base64 文本） | payload 段（原始字节） |

### 4.2 响应还原 <a id="frame-response"></a>

`decode_frames(response.content)` 取第一帧，按**请求帧类型**分派：

| 请求帧类型 | `data` 键 | 说明 |
| --- | --- | --- |
| `PUBLISH` | `message_id` / `log_id` / `topic` / `partition` / `offset` / `deliver_at` | 与 JSON `PublishResult` 同名同义；`deliver_at` 帧头是 ISO 文本 |
| `CONSUME` | `count` / `messages` / `paused` / `inflight_messages` / `inflight_bytes` | `messages` 每条是元数据映射（含 `length`，**不含 `payload`**） |
| `ACK` / `NACK` | `committed_offset` | 两种确认类结果同构 |

- `request_id` / `protocol_version` 不进 `data`（只在日志里用），避免把传输层字段漏进业务模型；
- 结果帧的 `retryable` / `category` / `layer` **不读**：类别与动作一律由本地码表给（03-6 §7 唯一出处），两通道判定才等价。

### 4.3 消息体重组 <a id="frame-segments"></a>

```text
payload 总长 = Σ messages[i].length
messages[i].payload = payload[cursor : cursor + length]；cursor 依次前进
```

| 情形 | 处理 |
| --- | --- |
| `Σ length == len(payload)` | 按序切片，写入 `payload_segments` |
| 不等 | 抛 `MsgClientError`（`category=server_bug`、`action=fatal`，「帧内消息体长度与元数据不一致」）——对端装配坏了，重试无意义 |
| 空批（`messages` 为空） | `payload` 必为空、`payload_segments` 为空列表 |

消费端不再解 base64：`poll` 优先按 `payload_segments` 取值；`payload_segments` 为空（JSON 通道）时回落解析 `data["messages"][i]["payload"]` 的 base64。

### 4.4 错误帧 <a id="frame-error"></a>

| 帧头字段 | 映射 |
| --- | --- |
| `code` / `message` | `ApiOutcome.code` / `.message`（`code != 0` 即业务失败） |
| `detail` | `ApiOutcome.data`（非映射则空映射；`350033` 的 `leader` / `epoch` 由业务层继续读） |
| `retry_after_ms` | `ApiOutcome.retry_after_ms`；为空再看 HTTP `Retry-After` |

业务层（生产端 / 消费端）拿到 `code != 0` 后**照旧查本地码表**，与 JSON 通道走同一条分类路径——这是「两通道错误分类等价」的实现基础。

### 4.5 非帧响应的兜底 <a id="frame-fallback"></a>

网关 / 反代可能在请求到达服务前就拦截（429 限流、502 不可用），此时响应不是帧。处理顺序：

1. 先按帧解码；成功即按 §4.2 还原；
2. 解码失败（magic 不符 / 长度非法 / 版本不支持）→ 按 JSON 统一响应体解析（`code` / `message` / `data`）——网关错误体能解出来就沿用同一套码表分类；
3. JSON 也解不出整型 `code` → `MsgClientError`（`category=server_bug`、`action=fatal`，「响应既不是帧也不是统一响应体」）。

### 4.6 编码期失败 <a id="frame-encode-error"></a>

`encode_frame` 的结构上限失败（header > 64 KiB、payload > 1 MiB、版本越界）发生在**请求发出之前**：

| 现象 | 码 | 类别 | 动作 | 结果未知 |
| --- | --- | --- | --- | --- |
| 消息体超 1 MiB | `350006` | `param_error` | `fatal` | 假 |
| 帧头超 64 KiB | `350018` | `param_error` | `fatal` | 假 |
| 版本无法编码 | `350018` | `param_error` | `fatal` | 假 |

与远端拒绝同码（`350006`）不同类别：远端拒绝时是业务拒绝，本地拒收时是参数问题——两者「不可重试、未写入」一致，调用方处理方式相同。

## 5. 两通道等价性契约 <a id="parity"></a>

| 维度 | 要求 |
| --- | --- |
| 对外方法 | 名称 / 入参 / 返回模型完全一致（本子任务不改任何对外签名） |
| 请求业务字段 | 同一 `fields`：JSON 在请求体、帧在帧头，键名与值一致 |
| 消息体 | JSON 通道 base64 往返后与帧通道原始字节逐字节相同 |
| 回执与结果 | `PublishAck` / `PollResult` / `CommitResult` / `Assignment` 字段相同 |
| 错误分类 | 同一码在两条通道得到相同的 `category` / `action` / `outcome_unknown` |
| 重试与改投 | 计数、退避、改投选路逻辑只在生产端写一份，通道不参与判定 |

## 6. 幂等键落点 <a id="idem"></a>

| 项 | 口径 |
| --- | --- |
| 落点 | `fields["headers"]["x-msg-idem-key"]`；JSON 落请求体 `headers`，帧落帧头 `headers` |
| 服务端可见性 | `PublishRequest.headers` 是闸门白名单字段，随消息存储，消费侧能从消息头读到 |
| 不变的部分 | 服务端**仍不做发布去重**；本地幂等表仍只在同进程内有效（03-6 风险 R3 不变） |
| 为什么不放帧头顶层字段 | 服务端请求模型没有该字段，闸门按白名单取键，多写的键会被静默丢弃 |

| `HEARTBEAT_PATH` | `/msg/groups/heartbeat` | `/msg/heartbeat` |

数据面四端点 `/msg/publish`、`/msg/consume`、`/msg/ack`、`/msg/nack` 本就正确，不动。用例补一条「成员端点请求打到真实路径」的断言，防止再次写错。

## 8. 失败分支与边界 <a id="failures"></a>

| # | 场景 | 行为 |
| --- | --- | --- |
| 1 | 帧解码失败且 JSON 也解不出 | `server_bug` / `fatal`，不重试 |
| 2 | 帧内 `Σ length` 与 payload 总长不符 | `server_bug` / `fatal`，不重试 |
| 3 | 响应体只有半帧（连接中断在尾部） | `decode_frames` 返回 0 帧 → 按「响应既不是帧也不是统一响应体」处理 |
| 4 | 建连失败 / 建连超时 | `transient` / `retry`（请求未发出，重试安全） |
| 5 | 读超时 / 读中重置 | `unknown` / `fatal` + `outcome_unknown`（与 JSON 通道同口径） |
| 6 | 错误帧 `code != 0` | 查本地码表分类，与 JSON 通道一致 |
| 7 | 同一帧里带多帧（服务端只会回单帧） | 只取第一帧；多余帧不解析（保持「服务端零改动」前提下的宽松读法） |
| 8 | 消息体超 1 MiB | 编码期拒收（§4.6），不发请求 |

### 10.1 参数化公共组（两条通道各跑一遍，断言完全相同）
