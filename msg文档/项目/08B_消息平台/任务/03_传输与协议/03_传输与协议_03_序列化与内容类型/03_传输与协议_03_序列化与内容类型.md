## 2. 任务内容 <a id="content"></a>

1. **默认序列化**：header **强制 MessagePack**；payload 由生产者决定原始字节；协议头带 `content_type`，为将来按 topic 切 Protobuf 留口。
2. **broker 透明**：broker 只解 header，**不解 payload、不做字符集转换**；`content_type` 只作为头字段透传与展示。
3. **schema 演进**：沿用 bms 事件契约「字段只增不删、不改名、不改语义」；消费者按旧契约能读新消息。
4. **消费端校验**：协议必填头（topic / tenant / message_id / log_id 等）由帧入口统一校验；业务 payload 的 schema 校验通过可注册校验器扩展（正式 SDK 归 8B_03），校验失败**进死信**，不得静默忽略。
5. **压缩**：按批压缩，由**生产者压缩、消费者解压**；`flags` 标记压缩算法；broker 不理解压、原样存储与转发，压缩后仍可零拷贝。
6. **兼容测试**：字段新增后老消费者可读；字段缺失或类型错误进死信；压缩消息经 broker 转发后消费者可解压。
7. **契约与文档**：`content_type` 取值、压缩标记、校验失败错误码登记进契约快照与协议说明。
8. **边界**：不做帧结构（03-2）、不做连接与背压（03-4 / 03-5）、不做业务 Schema Registry（范围外）、不做 broker 端解包审计。

## 3. 完成标准 <a id="accept"></a>

- 新增可选字段后，旧消费者仍可读取；字段缺失 / 类型错误时消息进死信且原因可见。
- 压缩消息由生产者压缩、消费者解压，broker 转发字节不变。
- `content_type` 可随消息透传，broker 不解析 payload（有护栏用例）。
- 兼容性与压缩用例全绿；变更模块行 + 分支覆盖率 100%，静态检查全绿。
