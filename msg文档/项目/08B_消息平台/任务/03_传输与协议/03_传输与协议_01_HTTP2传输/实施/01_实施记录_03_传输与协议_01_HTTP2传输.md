## 2. 实施概览 <a id="overview"></a>

```mermaid

    A["Kiwi 2420 登记"] --> B["传输基元<br/>transport.py + 4 常量"]
    B --> C["根路径入口<br/>DATA_PLANE_ROUTES + frame 路由"]
    C --> D["SSE 长驻流 + 连接元数据"]
```

共用同一份端点规格；新增 SSE 长驻流与连接元数据；延迟推进器 / 重放执行器改由 `startup_hooks()` 启动；
契约快照接入预检。

## 3. 实施过程 <a id="process"></a>

1. **Kiwi 登记**：登记 1 条策展用例，平台回读编号 **2420**（分类「平台骨架」/ P2 / CONFIRMED / 标签「自动化」）。
2. **传输基元**（`broker/transport.py`）：`ConnectionMeta` + `connection_meta()`（把 ASGI 的 `"2"`/`"1.1"`
   归一成 `HTTP/2`/`HTTP/1.1`）、`StreamSession`/`StreamRegistry`（活跃流登记，供「断开即释放」可断言）、
   `StreamTuning` + `default_stream_tuning()`、`sse_event()`/`sse_comment()`（`data` 单行）。
   常量落 `core/config.py`：`SUBSCRIBE_POLL_INTERVAL_MS=200` / `SUBSCRIBE_MAX_SECONDS=60` /
   `SUBSCRIBE_MAX_SECONDS_LIMIT=600` / `SUBSCRIBE_KEEPALIVE_MS=15000`。
3. **规格单点化**（`api/data/messages.py`）：端点改为「先定义函数、再由 `DATA_PLANE_ROUTES` 挂载」，
   `mount_data_plane(target)` 一处挂两条聚合；私有出口改公开复用（`message_item` / `apply_retention` /
   `ensure_member` / `delivery_service`）；错误码清单与权限码公开（`*_ERROR_CODES` / `*_PERMISSION`）。
4. **根路径入口**（`api/frame/routes.py`）：`/msg/{publish,consume,ack}` 复用同一 handler；
   新增 `GET /msg/subscribe`（SSE，逐批 `consume` + 200ms 轮询 + 注释行保活 + `close(deadline)` /
   `error`+`close(member_lost)` / `close(client_closed)`）与 `GET /msg/connection`。
   预检（保留清理 + 成员守卫）在**进流之前**完成，失败走普通 JSON 错误。
5. **契约模型**（`schemas/transport.py`）：`ConnectionInfo`、`SubscribeQuery`（复用数据面共享字段，
   `max_seconds` 上界 600 由契约层拒绝 `10001`）。
6. **装配**（`main.py` / `api/router.py` / `api/deps.py`）：`service_routers()` 返回两条聚合（`/api/v1` + 根路径）；
   `configure_service()` 注入 `stream_registry` 与 `uow_factory`；`startup_hooks()` 返回
   `start_background_tasks`（`broker/lifecycle.py`：启动两个循环并登记 `BackgroundLoops` 到 `ResourceManager`，
   停机逆序 `stop()`；幂等）。
7. **依赖与文档口径**：`services/msg/pyproject.toml` 移除 `uvicorn[standard]`；`asgi.py` docstring 改 hypercorn
   （明确「正常启动走 `python -m bms_msg`」）。
8. **ops**：`backend/ops/contract_snapshot.py`（`export` / `check`，内存构建应用取 OpenAPI、不启 lifespan），
   `engkit.toml` 启用预检步骤（用 `{python}` 而非 `uv run`：本仓无 `uv.lock` 与仓内 `.venv`）；
   契约快照重导（+5 路径）。
9. **真机冒烟**（platform + tenant + msg 三进程）与**基准分层取证**（详见 §5、测试记录 §4）。
10. **跨仓阻塞与修复**：冒烟首轮数据面一律 `350012`，定位为 bms `is_tenant_id` 上限 20 位与真实租户主键
    （31~35 位）不符；按拍板走 **bms 缺陷修复**（上限 39），bms 侧记录见
    《[06_数据拓扑升级_04 实施记录 · §7](../../../../../../../bms文档/项目/02_后端基座与服务化地基/任务/06_数据拓扑升级/06_数据拓扑升级_04_租户解析与库键派生健壮性/实施/01_实施_04_租户解析与库键派生健壮性.md#defect-tenant-id-width)》。

## 4. 问题与处置 <a id="issues"></a>

| 问题 | 现象 | 处置 |
| --- | --- | --- |
| ASGI `http_version` 不是 `HTTP/2` | `scope["http_version"]` 给的是 `"2"` / `"1.1"` | `connection_meta()` 归一为 `HTTP/2` / `HTTP/1.1`；未知值原样透出、缺失给 `unknown` |
| FastAPI 0.141 的 `include_router` 不再扁平化 | 断言「两条路径同一函数对象」时 `app.routes` 里是 `_IncludedRouter`（无 `path`） | 改从 OpenAPI 侧比对（`x-error-codes` / `requestBody` / `description` 三处逐一相等），判据更强且不依赖内部结构 |
| httpx 退出 `stream()` 上下文不发 `RST_STREAM` | 「取消流」用例里服务端一直登记为活跃，5s 断言失败 | 用例改为关闭客户端连接（真实断连形态）；超时后 hypercorn 才收到 `StreamReset` → `http.disconnect` → 生成器取消 → `finally` 注销 |
| 生成器收到 `close` 后若不推进到结束，`finally` 不执行 | 成员撤销用例断言 `active == 0` 失败 | 用例加 `_drain_until_close()`：取到 `close` 后继续推进到 `StopAsyncIteration` |
| 真机启动：msg 声明上报 5s 读超时 | platform 的 `PUT /internal/declarations` 因调用 tenant 服务缺失而耗时 6.5s | 冒烟脚本一并起 `tenant`；另关 `BMS_TRACER__SAMPLER`（本机无 OTLP collector，导出重试会拖事件循环） |
| 真机数据面 `350012` | `is_tenant_id` 上限 20 位 vs 租户主键 31~35 位 | 按拍板改 bms 上限为 39（缺陷修复，见 §3 第 10 条） |
| 真机缺 dev 数据面租户 | 无令牌时 `frame_tenant()` 依赖中间件解析结果 | 冒烟注入 `BMS_TENANT__DEV_OVERRIDE_TENANT=demo`（既有 dev 口径，不改代码） |
| 基准首轮全部失败 | 3000 条零成功，报 `40002 未注册的 permission 实现：null` | 基准脚手架补导入 `bms_core.permission.null` / `tenant_module.null` 占位实现 |
| 基准 publish 档被应用成本淹没 | 两档 p50 ≥ 280ms、h2c 反而更慢 | 改为**分层测量**：增「纯 GET `/msg/connection`」对照档作判据（设计 §8.3） |
| 真机栈 benchmark 读超时 / 连接池耗尽 | 32 并发下平台库池 5+10 用尽、租户解析逐请求回源 | 基准改在「最小装配 + 真 hypercorn」端口上取数（同业务路由、同 JSON，仅去掉平台租户/审计开销），并在记录中说明理由 |

### 5.2 基准结果（分层）

原始结果：`.cache/bench/http2.json`、`/tmp/bench.txt`、`/tmp/bench_control.txt`（本机临时产物，不入库）。

| 档 | 端点 | 条数 | 并发 | 吞吐 | p50 | p99 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 传输层对照 | `GET /msg/connection` | 3000 | 16 | HTTP/1.1 **211.7** / h2c **304.5** (条/s) | 52.4 / 53.6 ms | 102.0 / 70.7 ms | 吞吐比 **1.44x**、p99 **70.7ms** → **未达 2x / 50ms** |
| 应用路径 | `POST /msg/publish` | 1200 | 16 | HTTP/1.1 **56.5** / h2c **25.2** (条/s) | 280 / 624 ms | 465 / 986 ms | 仅作观测量（应用固定成本主导，见设计 §8.3） |

判读：传输层确实更快（+44%）但**未达 2 倍**；p99 超 50ms。主因两条：① 压测客户端与服务端同机同 CPU，
Python httpx 客户端自身即瓶颈（两档 p50 都在 50ms 量级，说明排队在客户端）；② publish 档每请求固定成本
（主题解析 + 保留清理 + 会话）≈17ms，远大于传输差异。
