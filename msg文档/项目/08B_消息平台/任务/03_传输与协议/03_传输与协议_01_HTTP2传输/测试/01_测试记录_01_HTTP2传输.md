## 2. 用例与覆盖范围 <a id="cases"></a>

Kiwi 2420 覆盖：根路径入口与 `/api/v1` 同语义同错误码、连接元数据、SSE 长驻流（事件序列 / 保活 / 到期 /
成员撤销 / 断开释放）、真 h2c（协商 / 同连接多 stream / 断连释放）、生命周期钩子、契约快照脚本。

```text
msg/backend/
├── services/msg/tests/
│   ├── broker/test_transport.py            # 传输基元：元数据归一 / 流登记 / SSE 编码
│   ├── broker/test_lifecycle.py            # startup_hooks：起停循环、幂等、资源回收
│   ├── api/test_frame_entry.py             # 根路径三端点 + 连接元数据 + 契约路径
│   ├── api/test_subscribe_stream.py        # SSE 生成器级 + HTTP 预检级
│   ├── api/test_frame_transport_h2c.py     # 真 hypercorn：h1/h2c、多 stream、断连释放

└── tests/ops/test_contract_snapshot.py     # 契约快照 export / check / 漂移 / 缺件 / 失败分支
```

## 4. 基准结果 <a id="bench"></a>

### 4.1 环境与参数

| 项 | 值 |
| --- | --- |
| 机器 | 开发机（与服务端同机同 CPU；客户端 Python httpx，**客户端即瓶颈之一**） |
| 被测服务 | **最小装配 + 真 hypercorn**：`scripts/bench/run_bench.py`（同业务路由 + 内存存储 + 桩租户源；不启 lifespan、不装审计发件箱、平台库为临时 SQLite）；差异清单写在脚本 docstring |

### 4.2 传输层对照（判据档：只有协议不同）

| 档 | 端点 | 吞吐 | p50 | p99 |
| --- | --- | --- | --- | --- |
| HTTP/1.1 | `GET /msg/connection` | 211.7 条/s | 52.4 ms | 102.0 ms |
| h2c | `GET /msg/connection` | 304.5 条/s | 53.6 ms | 70.7 ms |

**吞吐比 1.44x**（判据 ≥ 2x）→ 未达标；**h2c p99 70.7ms**（判据 ≤ 50ms）→ 未达标。

### 4.3 应用路径（观测量：协议 + 业务固定成本）

| 档 | 端点 | 吞吐 | p50 | p99 | 失败 |
| --- | --- | --- | --- | --- | --- |
| HTTP/1.1 | `POST /api/v1/msg/publish` | 56.5 条/s | 280.3 ms | 465.0 ms | 0 |
| h2c | `POST /msg/publish` | 25.2 条/s | 623.8 ms | 986.3 ms | 9 |

> h2c 档 9 个失败已于 2026-11-05 归因并定性（装置问题，非业务失败），复跑与处置见 §4.5。

### 4.4 判读（写进结论的三条）

1. **传输层确实更快（+44%）但未达 2 倍**：与规划 §7 风险 14「hypercorn 明文吞吐低于 uvicorn httptools」
   一致；这是判据本身的结论，**不调参硬凑**。
2. **应用路径的两档数字不能当判据**：每请求固定成本（主题解析 + 保留清理 + 一次会话）≈17ms，
   远大于传输差异；publish 档 h2c 反而更慢（定论见 §4.5.6：与失败无关，是装置成本结构）。
3. **同机压测的局限**：两档 p50 都在 50ms 量级，说明排队主要发生在客户端；绝对值不可外推为容量结论。

→ 结论：**8B_01 第 5 项（基准对比）未达成**，按规划 §7 / §9 触发刹车评审（评审输入：本节 + 设计 §8.3 +
实施记录 §7 遗留 1~3）。**评审结果：2026-11-05 判 go（功能驱动），性能判据降为容量观测**（规划 §9.3）。

### 4.5 失败归因与复跑（2026-11-05 收口） <a id="failure-rca"></a>

> 起因：§4.3 的 9 个失败**只有计数、没有原因**（03-1 计划行「偏差与遗留」）。本节是「补记原因 → 原参数复跑
> → 定性 → 处置」的全过程留痕。原始数据：`.cache/bench/http2_repro_fail.json`（复现档）、
> `.cache/bench/http2.json`（现行装置）、`.cache/bench/http2_031_20261105_original.json`（03-1 首次）。

#### 4.5.1 先给脚本补归因能力

| 改动 | 作用 |
| --- | --- |
| `Result.failure_reasons` / `failure_samples` | 按「HTTP 状态码 / 业务码 / 异常类型」归类计数，另留 5 条原文（响应体前 160 字符或异常 `repr`） |
| `_business_code()` | 非 JSON 响应不再抛 `JSONDecodeError`（**旧逻辑在 HTML 错误页上会直接中断整个基准**，连失败样本都留不下） |
| `Result.warmup_failures` | 预热失败单独计数（此前被完全忽略） |
| JSON `params` 段 | 条数 / 并发 / 预热 / 载荷 / 单连接预算随原始数据落盘，复跑可逐项对齐 |

#### 4.5.2 原参数复跑（`--total 1200 --concurrency 16`，预热 200）

| 档 | 成功 | 失败 | 吞吐 | p50 | p95 | p99 |
| --- | --- | --- | --- | --- | --- | --- |
| HTTP/1.1 + JSON | 1200 | 0 | 89.8 条/s | 168.5 ms | 273.1 ms | 299.3 ms |
| h2c + JSON | 1184 | **16** | 39.0 条/s | 401.8 ms | 498.2 ms | 526.9 ms |

失败归因：**16 × `HTTPError WriteError`**（样本 `WriteError('')`），**没有任何非 200 响应、没有任何业务码错误**——
失败发生在客户端**写连接**这一步，请求根本没进业务处理。旧装置语义下 03-1 记录的是 9 条、本轮 16 条，
差异只是「连接断开那一瞬有几个人在途」（worker 内串行，谁在写谁中招）。

#### 4.5.3 机理：服务端按设计的「连接退休」

- hypercorn 默认 `keep_alive_max_requests = 1000`：单条 h2 连接上第 **1001** 个请求到达时，
  `Protocol.h2` 执行 `close_connection()`（发 GOAWAY）主动退休该连接；
- httpx / httpcore 对**在途** stream 不重试：写失败映射 `anyio.ClosedResourceError → httpx.WriteError`
  （异常消息为空，故样本是 `WriteError('')`），读侧映射 `RemoteProtocolError(<ConnectionTerminated …>)`；
- 基准 h2 档是**一条连接**（`http2=True, http1=False`；httpx 对 h2 只维护一条连接），
  预热 200 + 测量 1200 = 1400 条，必然越过 1000 一次 → 一次性带走当时在途的那批请求。

四组对照（同一台机、同参数、只改一个变量）：

| 场景 | 单连接请求数 | h2c 失败 | 失败原文 | 吞吐比 |
| --- | --- | --- | --- | --- |
| 400/100 —— 未越界 | 500 | 0 | — | 0.61x |
| 1000/200 —— 越界 | 1200 | **8** | `RemoteProtocolError('<ConnectionTerminated error_code:0, last_stream_id:2001>')` | 0.50x |
| 1200/200 + 服务端限额抬到 1e9 | 1400 | 0 | — | 0.50x |
| 1200/200 + 分轮 800（本次修复） | ≤800 | 0 | — | 0.45x |

**铁证**：`last_stream_id:2001` —— 客户端流号从 1 起按奇数递增，2001 正是**第 1001 个请求**，
与 `keep_alive_max_requests=1000` 严丝合缝。

#### 4.5.4 定性

| 判据 | 观察 | 指向 |
| --- | --- | --- |
| 非 200 响应 | 0 条 | 服务端没有拒绝请求 |
| 业务码失败 | 0 条 | 业务语义 / 错误码链路无异常 |
| 失败形态 | 全为客户端连接读写异常 | 传输装置层，不在 handler |
| 失败位置 | 一次性成批（同批 16 条），随后自愈（后续 1184 条全成） | 单次连接事件，非持续缺陷 |
| 服务端行为 | 1000 条退休是 hypercorn 的**设计行为** | 服务端无过错 |

→ **结论：装置问题**（服务端连接生命周期 + 客户端不重试在途流），**不是 msg 传输缺陷**。
因此**不改业务代码、不新增用例**（业务语义未变，Kiwi **2420** 沿用，不新登记、不改派）。

#### 4.5.5 处置（改脚本并留痕）

- 新增 `--connection-requests`（缺省 **800**）：单连接按预算**分轮**，在**轮边界**换连接——无在途请求、
  不重试、不改写失败语义，真实失败仍是失败；参数同时落 JSON `params`；
- 修复后同参数复跑：**0 失败**（§4.5.2 是修复前，修复后为 1200/1200、吞吐比 0.45x）；
- 顺带修掉非 JSON 响应崩溃点（§4.5.1）；
- **起服务脚手架入库**：此前「最小装配 + 真 hypercorn」只有本机 `tmp/bench_harness.py`（不入库），
  评审后的判据「脚本与报告可复现」其实不成立；现落 `scripts/bench/run_bench.py`（仓相对路径、解释器取
  `sys.executable`、差异清单写进 docstring），入库后用同一条命令复跑得
  **90.5 / 39.2 条/s、0 失败**，与入库前一致（见 §4.1「复跑」）；
- 口径写进脚本 docstring（`_run_phase`）与《实施记录》§4 / §7，避免下一个大条数压测再当缺陷查。

#### 4.5.6 疑点闭环：publish 档 h2c 慢 2.2 倍是否与那 9 个失败同根因

**明确结论：不是同一根因**，三条独立证据：

1. **算术**：失败只占 1.3%（16/1200），即便全部算成功也只到 ~40.6 条/s，与对照档 89.8 条/s 的 2.3 倍差距无关；
2. **对照**：失败为 0 的三组（未越界 / 限额抬高 / 分轮）吞吐比分别是 0.61x / 0.50x / 0.45x ——
   方向与量级都没变，说明慢与失败无关；
3. **方向反转**：同一装置下纯 GET 对照档 h2 **快 1.44x**（§4.2），换成 publish 档 h2 **慢到 0.45x** ——
   差异随「每请求应用成本」出现，符合「客户端每请求开销 + 单连接写路径串行」的成本结构，
   不是协议能力差异（也与评审 §9.3「装置闭环、客户端即瓶颈」的判定一致）。

→ 归口：**容量取值归 8B_12**（独立压测机 + 编译型客户端），性能不作 8B_01 门禁；本轮只留诊断记录，不调参。
