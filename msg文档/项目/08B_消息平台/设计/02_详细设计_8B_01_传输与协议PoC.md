## 1. 目标与范围 <a id="scope"></a>

**目标**：用最小可运行代码验证「HTTP/2（h2c）+ MessagePack + 单机 broker」这条技术路线，拿到与 HTTP/1.1 + JSON 的基准对比，作为是否继续 L3 的 go/no-go 依据。

**范围**：

- 单进程、单 topic、单 partition、单消费组；
- 发布 / 订阅 / ack / 重试 / 死信；
- 内存队列 + 最小文件日志 + 重启恢复；
- 基准脚本与报告。

**不含**：RPC、多分区、多消费组、rebalance、高可用、多租户、管理台、事务消息。

## 2. 技术选型 <a id="tech"></a>

| 项 | 选择 | 理由 | 备选 |
| --- | --- | --- | --- |
| HTTP/2 | `h2` 库直接实现 h2c | 不引入 ASGI 框架，基准测的是协议本身；h2c 本地无需 TLS 证书 | `hypercorn` + TLS（框架开销干扰基准） |
| 序列化 | MessagePack（`msgpack`） | Python 原生、紧凑、无 schema；与二进制帧天然契合 | Protobuf（跨语言时再引入） |
| 运行时 | `asyncio` | 与 bms 现有异步栈一致 | 线程池（不必要） |
| 存储 | 内存队列 + 追加文件日志 | 先验证协议与消费模型；文件日志接近 L3 目标 | 数据库表（后续可选） |
| 测试 | `pytest` + `pytest-asyncio` | 与 bms 口径一致 | — |

> 决策：PoC **不用** ASGI / FastAPI 承载消息协议，避免框架层开销掩盖传输差异；业务管理面（8B_06）再引入 ASGI。

## 3. 协议 <a id="protocol"></a>

### 3.1 连接与流

- 一个 TCP 连接 = 一个 HTTP/2 连接（h2c，prior knowledge）。
- 每个请求一个 stream：
  - `POST /msg/publish`：发布一条消息，响应 `{offset}`；
  - `GET /msg/subscribe`：长驻流，服务端持续推送消息；
  - `POST /msg/ack`：确认消费；
  - `POST /msg/nack`：显式拒绝（可选，PoC 可只靠超时）。
- 头：`:method` / `:path` / `content-type: application/x-msgpack` / `x-tenant` / `x-trace-id`。
- 流控：依赖 h2 的 `WINDOW_UPDATE`；服务端在发送队列积压时暂停推送。

### 3.2 负载

```text
PublishRequest  = { topic, key?, payload, headers?, tenant?, trace_id? }
PublishResponse = { offset, partition }
SubscribeItem   = { message_id, topic, partition, offset, key?, payload, headers?, created_at }
AckRequest      = { consumer, topic, partition, offset }
ErrorResponse   = { code, message, retryable }
```

- `payload` 为 bytes；其余为 MessagePack 标量 / map。
- `message_id` 由 broker 生成（雪花或 UUID），用于幂等与排障。

### 3.3 错误码（PoC）

| 码 | 含义 |
| --- | --- |
| `35001` | 主题不存在 |
| `35002` | 分区不可用 |
| `35003` | 消费组不存在 |
| `35004` | 超时 |
| `35005` | 背压 / 限流 |
| `35006` | 消息过大 |
| `35007` | 认证 / 授权失败（PoC 可先不做） |

## 4. 单机 broker <a id="broker"></a>

### 4.1 模型

```text
Broker
├── topics: {topic -> Partition}
Partition
├── queue: deque[Message]          # 未消费
├── inflight: {offset -> (msg, deadline)}  # 已投递未 ack
├── next_offset: int
├── log: FileLog
└── dlq: FileLog
```

- **单分区**：offset 单调递增；同 key 有序（PoC 单分区天然有序）。
- **订阅**：服务端从 `next_offset` 开始推送；未 ack 的消息在 `inflight`，超时后重投。
- **ack**：从 `inflight` 移除，推进消费位点。
- **重试**：超时重投；`retry_count` 超限 → DLQ。
- **消费组**：PoC 单组单消费者；位点存 `consumer/{group}.offset`。

### 4.2 文件日志

```text
data/{topic}/{partition}.log
├── record = [4B length][MessagePack bytes]
└── 追加 + 可选 fsync（按批次）
data/{topic}/{partition}.offset   # 已 ack 位点
data/{topic}/dlq.log              # 死信
```

- 写入：追加记录 → 更新内存索引 → 返回 offset。
- 恢复：启动时扫描日志，按长度前缀读取；遇到不完整尾部则截断。
- fsync：`sync_every_n` 可配（PoC 默认 1，测吞吐时可调大）。

### 4.3 背压

- 单连接最大未 ack 消息数 / 字节数；
- 超限时暂停订阅流（不读新消息），或对 publish 返回 `35005`；
- 具体阈值在配置中给默认值，PoC 只验证不崩。

## 5. 恢复与可靠性 <a id="recovery"></a>

- **重启恢复**：扫描日志重建 `next_offset`；读取 `offset` 文件恢复已 ack 位点；未 ack 消息重新进入可投递状态。
- **至少一次**：ack 前崩溃 → 重投；ack 后崩溃 → 不重投（以 offset 文件为准）。
- **幂等**：由消费方按 `message_id` 去重；PoC 只提供 `message_id`，不实现消费方幂等表。
- **死信**：重试超限写入 `dlq.log`，并返回 `message_id` / `offset` 供排障。

## 6. 基准 <a id="benchmark"></a>

### 6.1 场景

| 场景 | 说明 |
| --- | --- |
| B1 HTTP/1.1 + JSON | 同逻辑 broker，HTTP/1.1 + JSON 负载（基线） |
| B2 HTTP/2 + MessagePack | 本 PoC 目标 |

- 1 publisher / 1 subscriber；消息 1KB；共 10,000 条；warmup 1,000 条。
- 指标：吞吐（msg/s）、P50 / P99 端到端延迟、CPU、内存、日志落盘大小。
- 环境：同一台开发机，固定 Python 版本与依赖；记录 CPU / 内存 / 磁盘。

### 6.2 Go/No-Go 目标（待基准确认）

| 指标 | 目标 |
| --- | --- |
| 吞吐 | B2 ≥ B1 × 1.5 |
| P99 延迟 | B2 ≤ B1 × 0.7 |
| 恢复 | 重启后不丢已 ack、可重投未 ack |
| 稳定性 | 10k 条无崩溃、无死锁 |

> 若目标未达成，记录原因（h2 实现、序列化、fsync、Python 开销），再决定是否调整协议或换实现。

## 9. 风险与开放项 <a id="risk"></a>

| # | 风险 | 处置 |
| --- | --- | --- |
| 1 | `h2` 库直接实现服务端的复杂度 | 先做最小连接 + 单 stream；跑通后再加订阅长流 |
| 2 | Windows 下 asyncio / h2 行为差异 | 本地 Windows 先跑通；必要时在 Linux 开发服务器复测 |
| 3 | fsync 拖慢吞吐 | 基准分别测 `sync_every_n=1` 与批量 |
| 4 | 基准噪声 | 固定环境、warmup、多次取中位数 |
| 5 | PoC 目录与正式域结构冲突 | 8B_02 重构时迁移，PoC 不直接进生产 |
