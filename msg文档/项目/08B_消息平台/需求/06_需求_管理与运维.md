## 1. 域说明 <a id="intro"></a>

本域定义「平台怎么被看见、怎么被处置」。自研消息平台最容易「功能做完、运维没做」，上线后出问题只能重启。本域的目标是让积压、延迟、死信、复制状态都可观测、可操作。

覆盖范围：消息平台管理模块只读视图、写操作、指标与告警、链路追踪、死信处置、重放任务、主题授权界面、租户用量视图。依据见《[架构设计 · 控制面](../../../设计/架构设计/06_架构设计_控制面_元数据与运维.md)》与 bms《[运维与可观测](../../../../bms文档/资料/知识档案/消息与事件驱动/10_事件驱动_运维与可观测.md)》。

## 2. 需求 06-1：消息平台管理模块只读视图 <a id="r06-1"></a>

优先级：2（高）

**背景与动机**：排障时最需要的是「能看见」——积压多少、卡在哪个分区、哪条消息没被 ack。没有只读视图，每次故障都要登录服务器查文件。

**内容**（《架构设计 · 控制面》第 4 节、《运维与可观测》第 5 节）：

1. 主题列表：名称、分区数、消息量、保留期。
2. 消费组列表：组、成员数、积压、最后提交时间。
3. 分区详情：LEO、HW、ISR、积压。
4. 消息查询：按 offset / key / 时间 / `log_id` 检索（只展示头信息与载荷摘要）；支持按延迟状态与到期时间过滤。
5. 延迟消息视图：待投列表（`log_id` / 主题 / 分区 / 档位 / 到期时间 / 剩余时间）、档位分布、堆积提示（**只读**，不做改期与取消）。
6. 权限码 `msg:query`；查询操作支持按租户 / 主题 / 消费组过滤。

**完成标准**：不登录服务器即可查看积压与分区状态；消息可按条件检索；延迟待投与档位分布可查；列表可过滤且响应可接受。

## 3. 需求 06-2：消息平台管理模块写操作 <a id="r06-2"></a>

优先级：3（中）

**背景与动机**：建删主题、改分区数、改保留期、位点重置等操作若只能靠脚本，既容易出错也难以审计。

**内容**（《架构设计 · 控制面》第 4 节、《运维与可观测》第 5 节）：

1. 支持建 / 删主题、改分区数（**只能增**）、改保留期与配额。
2. 支持位点重置（高危，必须二次确认）。
3. 所有写操作需 `msg:manage` 权限并留痕。
4. 删除主题需二次确认并说明影响范围。
5. 写操作不得绕过 `router → log` 直接改日志。

**完成标准**：写操作有权限校验与审计；高危操作有二次确认；分区数不可减少。

## 4. 需求 06-3：指标与告警 <a id="r06-3"></a>

优先级：1（紧急）

**背景与动机**：没有指标就无法判断「是消费慢还是生产快」「是磁盘满还是副本落后」。指标必须先于功能可用。

**内容**（《架构设计 · 控制面》第 5 节、《运维与可观测》第 2~6 节）：

1. 四大黄金信号：延迟、流量、错误、饱和度。
2. 消息特有指标：积压（按分区）、inflight、死信增长、ISR 收缩、fsync 耗时。
3. 指标按 topic 聚合，`partition` / `group` 明细走管理模块，避免标签基数爆炸。
4. 告警分级 P0~P3，必须可行动、有抑制、有恢复通知。
5. 暴露 Prometheus 格式端点。

**完成标准**：积压 / 延迟 / 死信 / 磁盘可查；告警可触发与恢复；指标采集不显著影响吞吐。

**参考文档**：《[架构设计 · 控制面](../../../设计/架构设计/06_架构设计_控制面_元数据与运维.md)》第 5 节；bms《[运维与可观测](../../../../bms文档/资料/知识档案/消息与事件驱动/10_事件驱动_运维与可观测.md)》第 2~6 节。

## 5. 需求 06-4：链路追踪 <a id="r06-4"></a>

优先级：3（中）

**背景与动机**：消息链路是异步断开的，若 trace 不随消息透传，生产与消费会变成两个孤立链路，排障时无法串起来。

**内容**（《架构设计 · 控制面》第 6 节）：

1. 消息 header 透传 `trace_id` / `span_id` / `parent_span_id`。
2. broker 不解包 payload，只在 header 透传。
3. 消费动作创建新 span，parent 指向生产 span。
4. 批量消费时逐条记录 trace，避免串链。
5. 按 trace 采样，保证单条链路完整。

**完成标准**：一条消息的生产与消费可在同一 trace 中查看；批量消费不串链；采样不破坏链路完整性。

> **交付注块（2026-11-09，任务 06-4）**：消息头新增 `span_id` / `parent_span_id` / `trace_flags`（与既有 `trace_id` 同为可空字符串、上限 128、**只判长度不判形态**），三项均为 additive，旧客户端不传即 `null`、broker 不伪造也不生成服务端 span。内部把四个字段收成 `TraceContext` 值对象一物一传（替换原先逐层手传的 `trace_id` 参数），落盘走 `trace` 子结构（无 span 时不写该键、普通消息字节不变、**不升记录格式版本**）；发布 → 存储 → 投递 → 延迟转投 → 重放八条路径逐一确认原样透传。消费响应（JSON / SSE / 帧 `message` 头）**逐条**回显四项、不设批级字段；采样标记只透传（`trace_flags=00` 照常投递，不读含义、不改写、不据此丢弃）。发布路径的日志绑定四项（空值不写 key，避免顶掉自动注入的 `trace_id`），消费侧因批内多 trace 不逐条打日志。管理面消息检索 additive 返回四项，仍拿不到正文。契约快照与前端类型已重导，`x-msg-frame` 增 `tracing` 段写明「broker 只存搬回显」的口径。**验收**：1678 例全绿、16 个变更模块行 + 分支 100%。**遗留**：SDK 侧 span 创建 / OTel 导出归 bms 另立任务（本任务不宣称端到端已通）；死信 / 重放 / 延迟视图展示 span 需加表列，归 06 域后续。Kiwi 2469；详见[06-4 实施记录](../任务/06_管理与运维/06_管理与运维_04_链路追踪/实施/01_实施记录_06-4_链路追踪.md)与[06-4 测试记录](../任务/06_管理与运维/06_管理与运维_04_链路追踪/测试/01_测试记录_06-4_链路追踪.md)。

## 6. 需求 06-5：死信处置 <a id="r06-5"></a>

优先级：2（高）

**背景与动机**：毒消息若无限重试会阻塞整个分区；直接丢弃又会丢业务。死信是「隔离失败、等待人工处置」的出口。

**内容**（《架构设计 · 控制面》第 7 节、《运维与可观测》第 7 节）：

1. 重试超过上限的消息进入死信，记录原因、重试次数、原 offset。
2. 死信状态：待处置 / 重放中 / 已解决 / 已忽略 / 已归档。
3. 支持重放、忽略（必须填原因）、归档三种处置。
4. 死信处置必须留痕。
5. 死信增长必须告警。

**完成标准**：毒消息不进主链路阻塞；死信可查询与处置；处置有记录可追溯。

**参考文档**：《[架构设计 · 控制面](../../../设计/架构设计/06_架构设计_控制面_元数据与运维.md)》第 7 节；bms《[运维与可观测](../../../../bms文档/资料/知识档案/消息与事件驱动/10_事件驱动_运维与可观测.md)》第 7 节。

## 7. 需求 06-6：重放任务 <a id="r06-6"></a>

优先级：2（高）

**背景与动机**：一次性重放百万条会打挂消费端、吃满带宽。重放必须可控——限速、可暂停、可取消、可看进度。

**内容**（《架构设计 · 控制面》第 7 节、《运维与可观测》第 5 节）：

1. 重放以**任务**形式创建，指定条件（offset / 时间 / key）与速率上限。
2. 任务支持暂停、恢复、取消，并展示进度。
3. 重放不改变原 `message_id`，消费端仍需幂等。
4. 重放任务需 `msg:manage` 权限并留痕。
5. 重放期间对目标消费组产生的影响需在任务详情中可见（如积压变化）。

**完成标准**：重放任务可限速；可暂停 / 取消；进度可见；重放不绕过权限与审计。

**参考文档**：《[架构设计 · 控制面](../../../设计/架构设计/06_架构设计_控制面_元数据与运维.md)》第 7 节。

## 8. 需求 06-7：消息平台管理模块主题授权界面 <a id="r06-7"></a>

优先级：2（高）

**背景与动机**：05-3 已交付主题授权的存储、判定与管理端点，但只能调接口维护；排障与日常运维需要看见「谁对哪个主题有哪种动作」，并能在界面上授予、更新、收回。没有界面，主题授权就会退化为脚本操作，既难审计也容易出错。

**内容**（《架构设计 · 多租户与安全》第 7 节、《控制面》第 4 节）：

1. 消息平台管理模块新增「主题授权」页，列表支持按命名空间 / 主题 / 主体 / 动作 / 状态过滤与分页。
2. 支持单条与批量授予 / 更新：主体可选用户或角色，动作取发布 / 订阅 / 描述 / 管理，效果取允许 / 拒绝。
3. 支持收回，收回为软停用，二次确认说明影响范围；已停用规则不可重复收回。
4. 页面挂 `msg:manage`；复用 05-3 的 `GET/PUT/DELETE /api/v1/msg/admin/acls` 与错误码，不新增后端端点、不改判定顺序。
5. 主体候选与名称解析优先走 bms 平台用户 / 角色接口；无对应查询权限时降级手填主体标识，不阻断授权。

## 10. 需求 06-9：前端契约类型自动生成 <a id="r06-9"></a>

优先级：3（中）

**背景与动机**：06-1-1 会重导 `deploy/contracts/msg.json` 并新增四条只读端点，但 msg 前端目前只有 `frontend/modules/msg/src/domain.ts` 里手写的少量类型，契约变更后没有任何机器判据能发现前端类型没跟上。06-1-2、06-5、06-6、06-7、06-8 都消费同一份契约，手写类型会持续漂移，最终变成前端与后端各有一套「事实源」。

**内容**（依《[AI开发规范](../../../../bms文档/规范/AI开发规范.md)》「补充需求的处理方式」节顺延新增）：

1. 新建前端类型包，以 `deploy/contracts/msg.json` 为唯一输入，用 `openapi-typescript` 生成 TypeScript 类型声明并随代码入库。
2. 生成器提供 `--check` 模式，契约变更而生成物未更新时立即失败，并接入提交前门禁，与既有契约快照零漂移步骤并列。
