# 01 需求：消息平台

## 1. 背景与动机 <a id="background"></a>

bms 当前的事件与同步通信由三块拼成：

1. **事件投递**：本地事务性发件箱 + 轮询投递器 + RocketMQ；
2. **跨服务同步调用**：`HttpServiceClient`（httpx + JSON，OpenAPI 契约）；
3. **事务一致性**：短流程跨服务写走 TM + XA。

暴露的问题：

- `HttpServiceClient` 在同步链上性能不佳（JSON 序列化、连接开销、无多路复用）；
- outbox 的表名写死，产品共库时出现同名表重叠；事件账本/重放能力与 broker 绑定；
- 事件与 RPC 两套机制、两套契约、两套运维，长期维护成本高。

因此立项自研**统一消息平台**：一套传输同时承载事件与 RPC，替换 RocketMQ / outbox / `HttpServiceClient`。

## 2. 范围 <a id="scope"></a>

### 2.1 包含

- **传输**：HTTP/2 + 二进制序列化（多路复用、连接复用、背压）。
- **事件总线**：topic / queue、发布订阅、消费组、分区、offset、顺序、ack、重试、死信、重放。
- **RPC**：请求/响应、超时、取消、流式。
- **存储**：追加日志 / WAL、索引、分段、保留期、崩溃恢复。
- **高可用**：单机 → 主从 / 分区复制、故障切换。
- **管理台与运维**：主题 / 消费组 / 积压 / 死信 / 重放 / 配额 / 指标 / 追踪。
- **多租户与安全**：租户隔离、服务身份、鉴权、消息审计。
- **bms 迁移**：适配 `EventPublisher` / `BaseServiceClient` / outbox，保留回滚开关。

### 2.2 不包含

- 业务事件语义与业务消费逻辑（归各业务服务）。
- bms 基座的用户 / 角色 / 菜单 / 权限 / 字典 / 参数。
- 对外商业化计费与运营后台（L3 之后的独立阶段）。

## 3. 验收标准 <a id="accept"></a>

| # | 验收点 | 判据 |
| --- | --- | --- |
| 1 | 传输性能 | 与现有 HTTP/JSON 基准对比，吞吐 / P99 延迟达到设计目标 |
| 2 | 事件可靠 | 业务提交则事件不丢；消费幂等；重复投递效果一次 |
| 3 | 顺序 | 同分区 / 同聚合有序 |
| 4 | 崩溃恢复 | 进程崩溃后从持久化位点恢复，不丢已确认消息 |
| 5 | 死信与重放 | 失败进死信；可按条件重放 |
| 6 | RPC | 请求/响应、超时、取消、错误码可用；可替换一个 `HttpServiceClient` 试点 |
| 7 | 多租户 | 租户隔离、配额生效 |
| 8 | 运维 | 积压 / 延迟 / 死信指标可观测，管理台可操作 |
| 9 | 迁移 | bms 至少一条事件链路 + 一个 RPC 调用切换成功，可回滚 |
| 10 | 文档与覆盖 | 设计 / 实施 / 测试记录齐全；变更模块覆盖率 100% |
