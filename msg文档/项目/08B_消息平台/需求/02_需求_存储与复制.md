## 1. 域说明 <a id="intro"></a>

本域定义消息「怎么落盘、崩了怎么恢复、怎么多副本、切主怎么防错」。消息平台的性能与可靠性七成取决于存储引擎，任何存储层的 bug 都是数据丢失级别，因此本域是平台的地基。

覆盖范围：分区追加日志、索引与分段、崩溃恢复、消费位点、ISR 复制、选举与故障切换、自动选举与无人工切主恢复、存储水位、多实例部署与故障切换验收。依据见《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》与 bms《[存储引擎](../../../../bms文档/资料/知识档案/消息与事件驱动/03_事件驱动_存储引擎.md)》《[复制与高可用](../../../../bms文档/资料/知识档案/消息与事件驱动/04_事件驱动_复制与高可用.md)》。

## 2. 需求 02-1：分区追加日志 <a id="r02-1"></a>

优先级：1（紧急）

**背景与动机**：消息的访问模式是「写只追加、读只按位点顺序读、删只按整段删」。用数据库表存消息会带来写放大、保留期清理困难与吞吐上限；必须用追加日志。

**内容**（《架构设计 · 数据面》第 2 节、《存储引擎》第 1~3 节）：

1. 每个分区一组文件：`.log`（消息追加）、`.index`（稀疏索引）、`.timeindex`（时间索引）。
2. 每条记录带 `length`、`crc`、`header_len`、`header`、`payload`；**头体分离**，broker 只读头做路由。
3. 索引稀疏建立（按字节间隔），读取时二分定位最近索引项再顺序扫描。
4. 按大小 / 时间分段，段名以 base offset 命名，删除以段为单位。
5. broker **不反序列化 payload**，保持零拷贝转发能力。
6. **首期不做 compaction（含键压缩）**：段只按时间 / 容量整段删除，不做段重写（架构 09 D39）；出现「按 key 只留最新值」的账本需求再评估。

**完成标准**：写入顺序追加且 offset 单调；按 offset 可定位读取；删除按段生效且不重写其他段；索引体积显著小于数据体积。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 2~4 节；bms《[存储引擎](../../../../bms文档/资料/知识档案/消息与事件驱动/03_事件驱动_存储引擎.md)》第 2~4 节。

## 3. 需求 02-2：崩溃恢复 <a id="r02-2"></a>

优先级：1（紧急）

**背景与动机**：进程崩溃或断电时，最后一条记录可能只写了一半。若不做校验与截断，恢复后会读到垃圾数据，甚至把损坏数据当正常消息投递。

**内容**（《架构设计 · 数据面》第 5 节、《存储引擎》第 6 节）：

1. 启动时从**恢复点**开始，只扫描日志尾部，不扫全量。
2. 逐条校验 `length` 与 `crc`，遇到不完整或校验失败即**截断到上一条完整记录**。
3. 扫描过程中补建缺失的索引条目。
4. 已提交位点若超过截断后的 LEO，回退位点并告警（属于数据丢失事件，必须可见）。
5. 恢复过程必须有日志记录：扫描范围、截断位置、重建索引条数、位点调整。

**完成标准**：人为制造半条记录后重启，服务可正常启动且只丢最后一条；恢复日志能定位截断位置；位点越界时产生告警。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 5 节；bms《[存储引擎](../../../../bms文档/资料/知识档案/消息与事件驱动/03_事件驱动_存储引擎.md)》第 6 节。

## 4. 需求 02-3：消费位点管理 <a id="r02-3"></a>

优先级：1（紧急）

**背景与动机**：位点是「消费到哪」的唯一依据。位点丢失会导致整组重头消费或跳过消息，位点错乱会导致丢消息，因此位点的持久化与恢复必须可靠。

**内容**（《架构设计 · 数据面》第 8 节、《消费组与再均衡》第 5 节）：

1. 位点按 `(group, topic, partition)` 存储，首期用独立文件（后续可评估入表）。
2. 提交时机：**处理完再提交**，提交值为「已处理完的最后一条 + 1」。
3. 位点文件定期刷盘，并在优雅关闭时强制刷盘。
4. 位点损坏或丢失时，默认回退到最近已持久化位点（宁可重复，不可丢），并告警。
5. 支持位点重置（管理员操作），必须二次确认并留痕。

**完成标准**：重启后从正确位点续读；位点文件损坏时可回退并告警；位点重置有权限校验与审计记录。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 8 节；bms《[消费组与再均衡](../../../../bms文档/资料/知识档案/消息与事件驱动/05_事件驱动_消费组与再均衡.md)》第 5 节。

## 5. 需求 02-4：副本与 ISR 复制 <a id="r02-4"></a>

优先级：2（高）

**背景与动机**：单机存储只能防进程崩溃，防不了磁盘损坏与整机故障。平台要承载生产事件，必须在迁移前具备副本能力，否则单点故障会放大到全平台。

**内容**（《架构设计 · 数据面》第 7 节、《复制与高可用》第 3 节）：

1. 采用 **ISR 式半同步**：leader 写本地 + ISR 副本确认后提交。
2. 副本落后超过阈值即踢出 ISR；恢复后重新加入。
3. `acks=all` 时要求 ISR 数量不低于 `min.insync.replicas`，否则拒绝写。
4. 消费者只能读到已提交（HW 之前）的消息。
5. **记录格式必须预留 epoch / 副本位点字段**（在存储设计阶段就带上，不能等到复制实现）。

**完成标准**：单副本故障时写入不丢已提交消息；ISR 收缩与恢复可观测；副本不足时按配置拒绝写而非静默降级。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 7 节；bms《[复制与高可用](../../../../bms文档/资料/知识档案/消息与事件驱动/04_事件驱动_复制与高可用.md)》第 3 节。

## 6. 需求 02-5：选举、epoch 与故障切换 <a id="r02-5"></a>

优先级：2（高）

**背景与动机**：切换主节点时若没有 epoch 与 fencing，旧 leader 可能继续写入，造成数据分叉；客户端缓存旧地址会持续写错地方。

**内容**（《架构设计 · 数据面》第 7 节、《复制与高可用》第 5~6 节）：

1. 日志带 **epoch / term**，写入时校验，拒绝旧 leader 的过期写入。
2. 首期支持**手动切换**；自动选举在稳定性验证后启用。
3. 切换时必须明确：新 leader 选择依据、旧 leader 隔离方式、未提交数据截断或保留、客户端感知方式。
4. 客户端通过元数据版本 + leader epoch 感知切换并刷新，不得持续写旧地址。
5. 切换过程与结果必须留痕（谁触发、耗时、数据调整情况）。

**完成标准**：旧 leader 的写入被拒绝；切换后客户端能自动刷新并恢复写入；切换过程可追溯。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 7 节；bms《[复制与高可用](../../../../bms文档/资料/知识档案/消息与事件驱动/04_事件驱动_复制与高可用.md)》第 5~6 节。

## 7. 需求 02-6：存储水位与拒绝策略 <a id="r02-6"></a>

优先级：2（高）

**背景与动机**：磁盘满会让 broker 无法写索引甚至崩溃；没有水位策略时，故障会从「写不进去」升级为「整机不可用」。

**内容**（《架构设计 · 部署与运维》第 8 节、《背压与流控》第 4 节）：

1. 设置**高低水位滞回**（如 70% 告警、85% 拒绝写），避免阈值附近反复抖动。
2. 高水位时拒绝新消息并返回明确错误码（`350022`），不允许静默丢弃；与生产限流 `350005`、延迟区满 `350015` **分立**（2026-11-05 定，03-5 启用 `350005` 后原「复用全局背压码」不再成立）。
3. 提供运维手段：缩短保留期、清理过期段、扩容磁盘。
4. 水位指标与告警必须接入（`msg_disk_used_ratio`）。
5. 预留空间（默认 10%~15%），避免磁盘 100% 后无法写索引。

**完成标准**：模拟磁盘写满时服务拒绝写而非崩溃；清理后可自动恢复写入；水位告警可触发。

**参考文档**：《[架构设计 · 部署与运维](../../../设计/架构设计/08_架构设计_部署与运维.md)》第 8 节；bms《[背压与流控](../../../../bms文档/资料/知识档案/消息与事件驱动/06_事件驱动_背压与流控.md)》第 4 节。

## 8. 需求 02-7：延迟消息持久化与到期恢复 <a id="r02-7"></a>

优先级：2（高）

**背景与动机**：延迟投递是「出问题时的兜底」（退避重试、超时关闭、超时提醒）。兜底能力一旦在进程重启或崩溃后失效，平台对「某个时刻一定被投递」的承诺就被静默撕毁，而业务侧无从感知。需求 01-5 只定义语义与接口（固定档位、延迟区端口、到期不可见、失败可见），**落盘与恢复必须在本域承接**——否则平台级验收时「重启不丢」没有负责方。

**内容**（《架构设计 · 数据面》第 2.4~2.6 节、第 5 节）：

1. **落盘位置**：延迟消息写该分区的 `.delay` 段（记录头含 `deliver_at` / `delay_level` / `message_id` / `log_id` / `key`），与分区日志同目录、同 CRC 与长度前缀格式；**不占 offset 空间**。`log_id` 在发布时即分配，转投时沿用（不重新生成），是记录级去重的判据。
2. **启动重建**：扫描 `.delay` 重建时间轮——未到期按**剩余时间**装填；已到期未转投的立即转投（限速，避免重启风暴）。
3. **不丢不重**：先 `append` 并刷盘、再清 `.delay`（偏序保证崩溃不会丢）；「是否已入日志」按 **`log_id`** 判定——恢复期扫 `.log` 尾部建立 `log_id` 集合，`.delay` 中命中者直接清掉、不再 `append`。**不用 `message_id`**：重放会以原 `message_id` 追加新记录，用它判重会误杀。单副本下不丢且不重；多副本由 8B_05 的单写者 / fencing 收敛。
4. **延迟区 TTL 与段轮转**：极端长延迟不无限增长；段损坏按 CRC 隔离（改名 + 告警），不静默丢、不阻塞其他分区。
5. **优雅关闭**：停收新延迟 → `.delay` 刷盘 → 时间轮进度落恢复点。
6. **容量口径沿用**：延迟区软上限（租户 + 全局）与 `350015` 拒绝语义由 01-5 定义，本域只负责落盘后的容量核算。

**完成标准**：

- 进程重启后，未到期延迟消息仍在剩余时间后投递（不提前、不丢）；已到期未转投的在启动后补投完成。
- 转投崩溃窗口内**不丢消息**（先写后清）；重启后同一 `log_id` 在日志中**只出现一条**（恢复期按 `log_id` 去重，单副本）。
- `.delay` 段损坏可隔离并告警（含段路径与损坏条数），其他分区不受影响。
- 优雅关闭后重启无丢失；延迟区容量与拒绝计数可查。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md#model)》第 2.4~2.6 节、第 5 节（崩溃恢复）；[需求 01-5](01_需求_消息模型与投递.md#r01-5)；bms《[存储引擎](../../../../bms文档/资料/知识档案/消息与事件驱动/03_事件驱动_存储引擎.md)》第 6 节。

## 9. 需求 02-8：多实例部署与故障切换验收 <a id="r02-8"></a>

优先级：2（高）

**背景与动机**：8B_05 的退出条件是「单节点故障可恢复、不丢已提交」，而 02-4 / 02-5 只定 ISR 复制与选举机制，没有一条任务负责**多实例拓扑、分区分配、真实故障切换与客户端刷新**的端到端验收。缺这一段，02-4 / 02-5 即使各自用例全绿，也不能证明「生产能按多副本跑、坏一台不掉数据」；平台级生产部署架构的生产迁移又硬依赖 8B_05（D24），因此必须把部署与验收单独落成需求。

**内容**（《架构设计 · 数据面》第 7 节、《部署与运维》第 7 / 11 节、《消息平台规划》§7）：

1. **多实例拓扑**：至少三实例（或按副本数 N）部署，分区按副本分配；`replication_factor` 与 `min.insync.replicas` 可配，单实例模式仍可回退。
2. **分区分配与迁移**：新实例加入 / 下线时的分区分配、副本迁移与客户端可见性；分区数只能增不能减（01-1 约束）；**运行态须随分配收敛**——缩容后被移出的副本停止拉取并卸载该分区（数据保留），leader 侧同步剔除该成员。
3. **故障切换**：leader 故障后的选举、任期 / fencing、ISR 收缩与重入；已提交（HW 之前）消息不丢，未提交部分可回退且可说明。
4. **客户端刷新**：`acks=all` 与 `acks=1` 的行为差异、实例摘除与重连、位点不越过 HW；与 02-5 的客户端刷新口径一致。
5. **可观测与演练**：ISR / HW / leader / 副本延迟可查；单节点故障、网络分区、进程崩溃三类演练各至少一次，结论区分通过 / 降级 / 失败。
6. **边界**：不做跨机房强一致、不做 Raft 多数派（架构 04 §7）；不做备份（副本不是备份）；生产迁移的完整链路归平台级生产部署架构，本需求只证明 8B_05 的退出条件。

**完成标准**：

- N 实例拓扑可部署、可回退单实例，分区分配与副本迁移结果可核对；
- 单节点故障后已提交消息不丢、消费可继续；未提交部分回退范围可说明；
- ISR 收缩 / 重入、leader 切换、客户端刷新均有观测与用例；
- 单节点故障、网络分区、进程崩溃三类演练有记录，结论不默认通过；
- 变更模块行 + 分支覆盖率达标，静态与文档校验通过。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md#replication)》第 7 节；《[架构设计 · 部署与运维](../../../设计/架构设计/08_架构设计_部署与运维.md)》第 7 / 11 节；《[消息平台规划](../../../规划/01_规划_消息平台.md)》§7（D24）；[需求 02-4](02_需求_存储与复制.md#r02-4)、[需求 02-5](02_需求_存储与复制.md#r02-5)。

## 10. 需求 02-9：自动选举与无人工切主恢复 <a id="r02-9"></a>

优先级：2（高）

**背景与动机**：02-5 交付的是**手动**切主——leader 进程不可用后 `msg_partition.leader` 仍指向死节点，写请求持续返回 `350033`，只能人工执行 `ops.failover switch`；02-8 的三类真容器演练已把这条遗留固定下来（实施记录 §5 第 7 条）。生产环境里「坏一台就要等人」等于把可用性绑在值班反应上，与 8B_05「单节点故障可恢复」的退出条件不符。但自动选主误判代价高（02-5 定稿的口径），因此必须在**复用同一套 epoch / fencing / 两阶段停写**的前提下补自动触发，不得另立切主实现。

**内容**（《架构设计 · 数据面》第 7 节、《复制与高可用》第 5~6 节、02-8 实施记录 §5）：

1. **故障判据**：复用控制通道探活（`LeaderControlTransport.snapshot`），连续 N 次失败判「leader 不可用」；**判据不看数据库**（DB 抖动不得触发换主），但发起前必须有可读的元数据权威，读不到即本轮不动作。
2. **候选与选择**：候选须在旧 leader 的**最后已知 ISR** 内且自身视图新鲜；新 leader 由切换服务按「ISR ∩ LEO 最大」选出，自动流程不自带第二套选择算法；`min.insync.replicas` 只决定 `acks=all` 可用性，不作为当选资格。
3. **抢主原子性**：复用 `msg_partition` 的 `epoch` 条件更新（`switch_state='idle' AND epoch=expected`）作为唯一抢占点，epoch 单调递增；并发发起只有一个成功，落败方不覆盖结果。
4. **防脑裂**：沿用租约 + `switch_state='switching'` + demote + 宽限 ≥ 租约；自动路径**永不使用 `force`**，无法验证 ISR 时停在 `blocked` 交人工。
5. **误判与风暴抑制**：尝试上限 + 指数退避 + 成功切换后的冷却（跨节点读 `last_switch_at`）+ 单轮并发上限 + 按副本序错峰；冷却期内新 leader 再次失效不再自动切，改告警。
6. **可观测**：新增自动选举结果计数（`triggered` / `succeeded` / `blocked` / `conflict` / `exhausted`）；切主结果复用既有 `msg_leader_switch_total`；审计沿用 `msg:partition.failover`，`operator` 记 `system:auto-election`。
7. **开关与单实例零变化**：独立开关缺省关闭；复制关闭时不装配、不启动、不产生任何行为差异；配置组合不满足安全性约束时拒绝启动。
8. **验收与演练**：多实例演练的进程崩溃场景改为「杀 leader 后不人工切主，等自动切换在预算内完成」，人工切主只作超预算兜底（结论记降级）。

**完成标准**：

- leader 进程不可用后，集群在预算内自动选出新 leader，客户端按 `350033` / `metadata_version` 改投后可继续写；
- 自动切换过程不出现双主可写；已提交（HW 之前）消息不丢，未提交尾部按 02-5 口径截断或保留且可说明；
- 数据库抖动、控制通道整体不可用、冷却期内二次故障均不触发换主风暴，且原因可查；
- 单实例（复制关闭）行为与既有版本完全一致；
- 演练中「不人工切主也能恢复」有记录、可复跑，降级项不计通过；
- 变更模块行 + 分支覆盖率达标，静态与文档校验通过。

## 11. 需求 02-10：拉取态初始化 <a id="r02-10"></a>

优先级：2（高）

**背景与动机**：02-4 的分区复制运行态是**惰性挂载**的——只有该分区在本节点收到过请求（写、消费、管理面查询、被拉的拉取）才会建立复制态并开始拉取。于是「副本必须被某个写请求碰过一次」成了复制生效的前置条件：空闲分区（从未被写）的副本永远不拉取，leader 侧 `lag_time_max_ms` 到期即把副本踢出 ISR，`msg_isr_size` 长期停在 1。该缺口已在 02-8 实施记录 §5 第 6 条被真机证实，并直接传导到 02-9：自动选举的候选资格依赖「最后已知 ISR」，空闲分区两侧都没有视图，只能记 `blocked(isr_unverified)` 交人工——即「bad 一台就要等人」在空闲分区上仍然成立。02-8 的演练靠「向每个实例各写一轮」预热绕行，属证据侧妥协，不是产品行为。

**内容**（《架构设计 · 数据面》第 7 节、02-8 实施记录 §5、02-9 详细设计 §4.1）：

1. **挂载由分配事实驱动**：进程内挂载循环按 `msg_partition` 的副本分配枚举本节点承载的分区并建立复制运行态，不依赖该分区是否收到过请求；枚举只读库，成员判定复用既有的副本集解析（行内 `replicas` 为空时按同一轮转算法推导），不引入第二套分配算法。
2. **启动首轮 + 周期追赶**：复制启动即跑首轮（不等周期），此后按固定周期复查，承接运行期新建主题、新增分区与迁移新增副本；单轮挂载量有上限，本轮未排空则立即续轮，排空后回到周期节拍。
3. **挂载即建立拉取态**：挂载成功后立即拉取一次（空批亦为心跳），使 leader 侧挂载时的乐观 ISR 初值被真实拉取证实，避免「踢出后重入」的秒级抖动；follower 侧持续刷新最后已知视图。
4. **空闲分区节拍**：连续空拉达阈值后降频到空闲间隔，有新记录立即回落；空闲间隔必须显著小于 ISR 时间阈值（否则会因降频被踢出）。
5. **拉取并发**：follower 拉取由逐分区串行改为有界并发，保证分区规模上升后单轮耗时仍小于轮次间隔。
6. **非成员守卫**：本节点不在副本集内的分区不挂载、不拉取、不参与 ISR 推导。
7. **可观测与失败处置**：暴露「已挂载分区数」；挂载轮次 / 失败 / 跳过均有结构化日志；枚举失败与单分区挂载失败按周期重试、逐分区隔离、不导致启动失败。
8. **单实例零变化与演练去绕行**：复制关闭时不装配、不启动、不产生 DB 查询；多实例演练删除「向每个实例各写一轮」的预热，改为直接等 ISR 收敛，判据集不变。

**完成标准**：

- 从未被写过的空闲分区在无写请求情况下 ISR 收敛到副本集大小，副本侧具备新鲜的最后已知视图；
- 02-9 自动选举对空闲分区不再只能 `blocked(isr_unverified)`；
- 运行期新建主题 / 新增分区在周期内被各副本挂载，不需重启、不需写请求；
- 单实例（复制关闭）行为与既有版本逐项一致；
- `replica_crash` 演练去掉预热后仍可复跑通过，判据集不变、既有归档记录无需替换；
- 变更模块行 + 分支覆盖率达标，静态与文档校验通过。
