## 1. 域说明 <a id="intro"></a>

本域定义消息平台上的**同步调用**能力：请求/响应、超时、取消、流式与错误语义，目标是替换现有 `HttpServiceClient` + FastAPI 的同步链路。与事件总线共用 HTTP/2 连接，但可靠性模型完全不同——RPC 要「立即知道结果」，消息要「可靠送达」。

覆盖范围：一元调用、deadline 传播、取消、流式、错误分类与重试、与 bms 端口适配、服务发现与负载均衡。依据见《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》与 bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》。

## 2. 需求 04-1：RPC 一元调用 <a id="r04-1"></a>

优先级：2（高）

**背景与动机**：服务间查询、校验等同步场景需要「发请求、等结果、拿错误码」。现有 HTTP/1.1 + FastAPI 链路开销大，且无法与事件共用连接。

**内容**（《架构设计 · 接入面》第 3 节、《RPC 模型》第 2~3 节）：

1. 提供 `/rpc/{service}/{method}` 一元调用端点，与事件共用 HTTP/2 连接。
2. 请求与响应通过 HTTP/2 `stream_id` 关联，不另造关联 ID 协议。
3. 请求携带 `trace_id` 与调用方标识，便于链路追踪与鉴权。
4. 服务端按 `service + method` 路由到处理器，未注册方法返回明确错误码。
5. 与事件流量共用连接时，按路径分配配额，避免大消息挤占 RPC。

**完成标准**：可完成一次跨服务调用并拿到结果；未注册方法返回明确错误；RPC 与事件并发时互不阻塞。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 3 节；bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》第 2~3 节。

## 3. 需求 04-2：超时传播与取消 <a id="r04-2"></a>

优先级：2（高）

**背景与动机**：只设客户端超时是最常见的错误——客户端返回了，服务端还在跑，继续占资源、继续调下游。取消不传播则会让无效请求一路打到最底层。

**内容**（《架构设计 · 接入面》第 3 节、《RPC 模型》第 4~5 节）：

1. 请求头携带**剩余预算（deadline）**，每跳扣除已消耗时间。
2. 服务端必须在预算耗尽时停止处理并返回超时错误。
3. 客户端取消通过 `RST_STREAM` 传递，服务端中断处理并释放资源。
4. 取消是尽力而为，不保证副作用回滚——因此不能替代幂等。
5. 超时视为「结果未知」，不得等同于「失败」直接重试。

**完成标准**：多层调用时下游不会在上游超时后继续长跑；取消后资源被释放；超时与失败在错误码上可区分。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 3 节；bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》第 4~5 节。

## 4. 需求 04-3：流式调用 <a id="r04-3"></a>

优先级：3（中）

**背景与动机**：订阅、分页拉取、进度推送等场景需要「一次请求、多次响应」。消息平台的 `subscribe` 本身就是服务端流，RPC 复用同一能力可减少一套机制。

**内容**（《架构设计 · 接入面》第 3 节、《RPC 模型》第 6 节）：

1. 首期支持 **unary + server streaming** 两种形态；client streaming 与双向流后置。
2. 流式响应必须有背压（窗口 + 应用层 inflight）。
3. 流内错误用流内错误帧表达，不能再用 HTTP 状态码。
4. 半开流必须有心跳或空闲超时，避免永久挂起。
5. 流结束用 `flags` 标记，客户端可识别正常结束与异常中断。

**完成标准**：服务端流可连续推送且背压生效；流内错误可被客户端识别；半开流在超时后释放。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 3 节；bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》第 6 节。

## 5. 需求 04-4：错误语义与幂等重试 <a id="r04-4"></a>

优先级：2（高）

**背景与动机**：客户端若无法判断「这个错误能不能重试」，只能全量重试或全量放弃——前者会放大故障，后者会丢成功机会。

**内容**（《架构设计 · 接入面》第 5 节、《RPC 模型》第 7~9 节）：

1. 每个错误必须带 **`retryable` 标记**，客户端据此决定重试或放弃。
2. 错误分类：参数错误 / 业务拒绝（不重试）、瞬时故障（可重试）、超时未知（谨慎重试）、服务端 bug（不自动重试）。
3. 重试必须指数退避 + 抖动，禁止无退避的立即重试。
4. 非幂等操作必须带幂等键，否则不得自动重试。
5. 熔断打开时直接失败，不进入重试。

**完成标准**：不同错误类型返回正确的 `retryable`；重试有退避与抖动；非幂等操作重试被阻止。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 5 节；bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》第 7~9 节。

## 6. 需求 04-5：与 bms 端口适配 <a id="r04-5"></a>

优先级：2（高）

**背景与动机**：迁移的前提是「业务代码不改」。若要求业务直接调 msg 的新 API，迁移成本与回滚风险都不可控。

**内容**（《架构设计 · 接入面》第 9 节、《规划》第 8 节）：

1. 实现 bms `EventPublisher` 的 msg 版本：`publish()` 转 `/msg/publish`。
2. 实现 `BaseServiceClient` 的 msg 版本：`call()` 转 `/rpc/{service}/{method}`。
3. 适配层必须可配置切换（msg / 原实现），切换不需要改业务代码。
4. 适配层需覆盖错误码映射、超时映射、trace 透传。
5. 适配层与业务解耦，独立测试。

**完成标准**：业务代码不改即可切换实现；配置切回原实现后行为恢复；错误码与超时映射正确。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 9 节；《[消息平台规划](../../../规划/01_规划_消息平台.md)》第 8 节。

## 7. 需求 04-6：服务发现与负载均衡 <a id="r04-6"></a>

优先级：2（高）

**背景与动机**：单实例时「一个地址」够用；一旦有多个 RPC 实例或 broker 副本（8B_03 / 8B_05），客户端就必须知道「有哪些实例、选哪个、失败了换谁」。没有这层，要么把地址写死，要么把负载均衡甩给网关——前者改一次部署要改代码，后者让内网调用多一跳。

**内容**（《架构设计 · 接入面》第 8.1 节、《RPC 模型》第 10 节）：

1. 客户端持有**实例列表**（DNS / 服务目录解析），**不写死在代码里**；首期单实例也走同一抽象，避免多实例时改客户端契约。
2. 选实例默认**轮询**（确定性、易断言），可选「最少在途」；策略可配置。
3. 实例级失败重试：换实例重试，**不重放已提交批次**；连续失败摘除，探活通过后恢复。
4. 与事件总线共用同一套寻址（同一个 broker 集群 / 同一份实例列表）。
5. **不引入外部注册中心**（Consul / etcd）：首期 DNS + 静态列表够用，实例规模与变更频率上来后再评估。

**完成标准**：停掉一个实例后，客户端在有限次数内切到健康实例且不产生重复提交；地址变更只改配置、不改客户端代码。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md#discovery)》第 8.1 节；bms《[RPC 模型](../../../../bms文档/资料/知识档案/消息与事件驱动/09_事件驱动_RPC模型.md)》第 10 节。
