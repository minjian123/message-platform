## 1. 域说明 <a id="intro"></a>

本域定义消息平台的租户边界与安全防线。bms 是多租户平台，消息平台一旦接入产品就必然承载跨租户流量；隔离缺失会导致数据越权，配额缺失会导致单租户拖垮全平台。

覆盖范围：租户标识与三级命名空间、租户隔离与解析、配额、认证、授权、审计留痕、租户生命周期。依据见《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》与平台《架构设计 · 多租户路由》。

## 2. 需求 05-1：租户标识与三级命名空间 <a id="r05-1"></a>

优先级：2（高）

**背景与动机**：只有「租户 + 主题」两级时，同一租户下多条业务线无法分别管理配额与权限；租户标识若用可变编码，改名就会导致数据目录断链。必须先定死标识与层级。

**内容**（《架构设计 · 多租户与安全》第 2 节）：

1. 采用 `tenant_id / namespace / topic` 三级结构；`tenant_id` 为雪花内部身份，**不可变**，目录与元数据列一律使用它。
2. `namespace` **对齐 bms `module_key`**，且必须取自已登记且启用的模块；未登记值拒绝创建。
3. 物理落点：`data/{tenant_id}/{namespace}/{topic}/{partition}`。
4. 主题名建议 `{对象}.{动作}`（如 `operation.created`），与 bms 事件契约命名一致。
5. 租户编码 `code` 只用于日志与展示，不参与存储路径。

**完成标准**：可按三级结构创建与查询主题；未登记 module_key 被拒绝；租户编码变更后目录与数据不受影响。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 2 节；平台《架构设计 · 多租户路由》。

## 3. 需求 05-2：租户隔离与解析 <a id="r05-2"></a>

优先级：1（紧急）

**背景与动机**：数据越权是最严重的安全事故；同时消息平台的 HTTP/2 数据面不走 ASGI 中间件，若不统一解析口径，会出现「管理面看到的租户」与「数据面看到的租户」不一致。

**内容**（《架构设计 · 多租户与安全》第 3~4 节）：

1. 隔离采用「逻辑隔离 + 目录隔离」：元数据按 `tenant_id` 列区分，消息本体按 `tenant_id` 分目录。
2. 管理面 / RPC 直接复用基座中间件注入的租户上下文。
3. 数据面（`h2` 直连）在帧入口**复用基座同一套解析函数**，不信任客户端自报的租户头。
4. **每次请求校验租户状态**：停用即拒绝收发；校验结果按短 TTL 缓存。
5. 跨租户访问一律拒绝并留痕；租户不存在时不泄露存在性。

**完成标准**：跨租户访问被拒绝；停用租户的收发被拒绝；管理面与数据面对同一请求解析出同一租户。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 3~4 节；平台《架构设计 · 多租户路由》「租户解析链」节。

## 4. 需求 05-3：配额管理 <a id="r05-3"></a>

优先级：2（高）

**背景与动机**：没有配额，一个大租户可以在几分钟内打满磁盘或带宽。消息维度（主题数、消息存储、吞吐）不属于 bms 通用配额，且 `sys_tenant_quota` 归属 bms tenant 服务，msg 不能跨服务直写。

**内容**（《架构设计 · 多租户与安全》第 6 节）：

1. 配额由 **msg 自维护**（`msg_quota`），维度：主题数、消费组数、生产速率、消息存储、未确认数、连接数。
2. **不写入 bms `sys_tenant_quota`**（隔离纪律：不访问其他服务数据库）。
3. bms 租户管理页经**产品数据源**（`deploy/registry/msg.toml` 的 `[[data_sources]]`）只读加载 msg 用量接口，不做双写。
4. 执行点前置：接收请求时判断；软硬两档（软限告警、硬限拒绝）。
5. 配额可查询、可调整，调整留痕；用量在 msg 管理台与 bms 只读板块均可见。

**完成标准**：超限时按软硬限正确响应；bms 租户管理页能看到 msg 用量；配额调整立即生效并留痕。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 6 节；《[数据库设计总览](../../../设计/数据库设计/01_数据库设计_总览.md)》第 2.3 节。

## 5. 需求 05-4：认证 <a id="r05-4"></a>

优先级：2（高）

**背景与动机**：消息平台不能另造一套身份体系，否则会与 bms 的服务认证、用户会话产生双轨。

**内容**（《架构设计 · 多租户与安全》第 4、8 节）：

1. 复用 bms 服务 JWT（`[service_token]`）校验服务身份；不另造令牌。
2. 生产环境启用 TLS（h2 over TLS）；开发环境可用 h2c。
3. 校验三件事：签名与有效期、身份归属（租户 / 命名空间）、身份权限。
4. 认证失败返回明确错误码并记录来源。
5. 密钥轮换采用「双密钥过渡」，不得直接替换。

**完成标准**：无令牌或过期令牌被拒绝；认证失败有审计记录；密钥轮换期间在途请求不受影响。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 4、8 节。

## 6. 需求 05-5：授权 <a id="r05-5"></a>

优先级：2（高）

**背景与动机**：认证只回答「你是谁」，授权回答「你能做什么」。没有资源级授权，任何已登录服务都能操作任意主题。

**内容**（《架构设计 · 多租户与安全》第 7 节）：

1. 采用 **RBAC 权限码 + 主题级 ACL** 双层模型。
2. 权限码：`msg:query`（只读）/ `msg:manage`（管理操作），与 bms 权限体系对齐。
3. 操作类型：`publish` / `subscribe` / `describe` / `manage`。
4. 校验顺序：RBAC → ACL → 租户 / 命名空间归属。
5. 三个易漏点必须覆盖：跨租户订阅、管理接口只校验登录、重放任意主题。

**完成标准**：无权限操作被拒绝；跨租户订阅被拒绝；重放接口有资源级校验。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 7 节。

## 7. 需求 05-6：审计留痕 <a id="r05-6"></a>

优先级：2（高）

**背景与动机**：消息平台的管理操作直接影响数据，必须可追溯到人；同时不应自建一套审计体系。

**内容**（《架构设计 · 多租户与安全》第 9 节）：

1. 配置变更、数据操作、权限变更、访问异常（含停用租户访问）四类必须留痕。
2. 留痕内容：谁、何时、对什么（`tenant_id` / namespace / topic / group）、做了什么、结果、来源 IP / `trace_id`。
3. 审计写入 bms 审计链（`audit-chain`），不自建。
4. 普通读写不逐条留痕，只做指标统计。
5. 审计记录不可被消息平台自身删除。

**完成标准**：管理操作可在 bms 审计链查到；越权与停用访问有记录；普通读写不产生审计洪泛。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 9 节；平台《架构设计 · 审计哈希链》。

## 8. 需求 05-7：租户生命周期 <a id="r05-7"></a>

优先级：2（高）

**背景与动机**：bms 的租户开通是「平台超管触发 + 建库 + 种子」，但消息平台没有租户库，无法复用建库流程；若每次开租户都要人工配置，必然遗漏。同时停用租户不能继续收发，也不能丢数据。

**内容**（《架构设计 · 多租户与安全》第 5 节）：

1. **懒初始化**：首次**发布**到未开通的 `(tenant_id, namespace)` 时自动创建命名空间与默认配额。
2. **查询不创建**：未开通时查询返回「不存在」，读路径无写副作用。
3. 并发首次发布靠唯一约束兜底，冲突时重查而非报错。
4. **停用**：拒绝生产与消费，管理查询仍可查看；**数据完整保留**，不自动清理、不归档。
5. **启用**：立即恢复收发，无需数据迁移。
6. **平台租户**按普通租户处理，不引入「全局 topic」；跨租户广播由各租户各自消费一份。

**完成标准**：首次发布自动创建命名空间；查询未开通返回不存在且不建数据；停用后收发被拒但数据保留；重新启用后恢复；平台租户与普通租户行为一致。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 5 节；平台《概要设计 · 租户管理》「租户开通 / 停用」节。
