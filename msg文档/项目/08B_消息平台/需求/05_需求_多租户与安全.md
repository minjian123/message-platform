## 1. 域说明 <a id="intro"></a>

本域定义消息平台的租户边界与安全防线。bms 是多租户平台，消息平台一旦接入产品就必然承载跨租户流量；隔离缺失会导致数据越权，配额缺失会导致单租户拖垮全平台。

覆盖范围：三级命名空间、租户隔离、配额、认证、授权、审计留痕。依据见《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》与 bms《[多租户与安全](../../../../bms文档/资料/知识档案/消息与事件驱动/11_事件驱动_多租户与安全.md)》。

## 2. 需求 05-1：三级命名空间 <a id="r05-1"></a>

优先级：2（高）

**背景与动机**：只有「租户 + 主题」两级时，同一租户下多条业务线无法分别管理配额与权限；命名空间是租户内的业务线边界，也是权限与配额的挂载点。

**内容**（《架构设计 · 多租户与安全》第 2 节、《多租户与安全》第 2 节）：

1. 采用 `tenant / namespace / topic` 三级结构。
2. 物理落点按租户与命名空间分目录：`data/{tenant}/{namespace}/{topic}/{partition}`。
3. 命名空间承担配额与权限的挂载点，主题继承命名空间约束。
4. 租户与 bms 租户体系对齐，从服务令牌解析，不接受客户端自报。
5. 支持命名空间的创建、查询与停用。

**完成标准**：可按三级结构创建与查询主题；不同命名空间可独立配置配额与权限；目录结构与命名空间一致。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 2 节；bms《[多租户与安全](../../../../bms文档/资料/知识档案/消息与事件驱动/11_事件驱动_多租户与安全.md)》第 2 节。

## 3. 需求 05-2：租户隔离 <a id="r05-2"></a>

优先级：1（紧急）

**背景与动机**：数据越权是最严重的安全事故。消息平台必须保证「A 租户的消费者无法读到 B 租户的消息」，且这一保证不能依赖客户端自觉。

**内容**（《架构设计 · 多租户与安全》第 3 节）：

1. 所有数据面与管控面操作都必须校验租户归属。
2. 租户 ID **从服务令牌解析**，不接受请求头自报。
3. 跨租户访问一律拒绝并留痕（含越权尝试记录）。
4. 隔离采用「逻辑隔离 + 目录隔离」：共享进程，但按租户 / 命名空间分目录。
5. 隔离强度不足时（如大租户抢占资源），可升级为独立进程或独立集群。

**完成标准**：构造跨租户访问请求时被拒绝；越权尝试可审计；单租户数据仅在其目录下可见。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 3 节；bms《[多租户与安全](../../../../bms文档/资料/知识档案/消息与事件驱动/11_事件驱动_多租户与安全.md)》第 3 节。

## 4. 需求 05-3：配额管理 <a id="r05-3"></a>

优先级：2（高）

**背景与动机**：没有配额，一个大租户可以在几分钟内打满磁盘或带宽，导致全体不可用。配额是「公平使用」的硬约束。

**内容**（《架构设计 · 多租户与安全》第 4 节、《多租户与安全》第 3 节）：

1. 配额维度：主题数、消费组数、生产速率、存储量、未确认消息数、连接数。
2. 执行点**前置**：在接收请求时判断，不是写入后统计。
3. 软硬两档：软限告警、硬限拒绝并返回明确错误码。
4. 配额可查询、可调整，调整必须留痕。
5. 配额用量必须在管理台可见，避免用户不知道为什么被拒。

**完成标准**：超限时按软硬限正确响应；配额调整后立即生效；用量可在管理台查看。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 4 节；bms《[多租户与安全](../../../../bms文档/资料/知识档案/消息与事件驱动/11_事件驱动_多租户与安全.md)》第 3 节。

## 5. 需求 05-4：认证 <a id="r05-4"></a>

优先级：2（高）

**背景与动机**：消息平台不能另造一套身份体系，否则会与 bms 的服务认证、用户会话产生双轨。复用基座令牌是最低成本的正确做法。

**内容**（《架构设计 · 多租户与安全》第 5 节）：

1. 复用 bms 服务 JWT（`[service_token]`）校验服务身份。
2. 生产环境启用 TLS（h2 over TLS）；开发环境可用 h2c。
3. 校验三件事：签名与有效期、身份归属（租户 / 命名空间）、身份权限。
4. 认证失败返回明确错误码并记录来源。
5. 密钥轮换采用「双密钥过渡」，不得直接替换。

**完成标准**：无令牌或过期令牌被拒绝；认证失败有审计记录；密钥轮换期间在途请求不受影响。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 5、8 节。

## 6. 需求 05-5：授权 <a id="r05-5"></a>

优先级：2（高）

**背景与动机**：认证只回答「你是谁」，授权回答「你能做什么」。没有资源级授权，任何已登录服务都能操作任意主题，等于没有隔离。

**内容**（《架构设计 · 多租户与安全》第 6 节、《多租户与安全》第 5 节）：

1. 采用 **RBAC 权限码 + 主题级 ACL** 双层模型。
2. 权限码：`msg:query`（只读）/ `msg:manage`（管理操作），与 bms 权限体系对齐。
3. 操作类型：`publish` / `subscribe` / `describe` / `manage`。
4. 先校验功能权限，再校验资源权限。
5. 三个易漏点必须覆盖：跨租户订阅、管理接口只校验登录、重放任意主题。

**完成标准**：无权限操作被拒绝；跨租户订阅被拒绝；重放接口有资源级校验。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 6 节；bms《[多租户与安全](../../../../bms文档/资料/知识档案/消息与事件驱动/11_事件驱动_多租户与安全.md)》第 5 节。

## 7. 需求 05-6：审计留痕 <a id="r05-6"></a>

优先级：2（高）

**背景与动机**：消息平台的管理操作（建删主题、改配额、重放）直接影响数据，必须可追溯到人；同时不应自建一套审计体系，避免与 bms 审计链割裂。

**内容**（《架构设计 · 多租户与安全》第 9 节）：

1. 配置变更、数据操作、权限变更、访问异常四类必须留痕。
2. 留痕内容：谁、何时、对什么、做了什么、结果、来源 IP / `trace_id`。
3. 审计写入 bms 审计链（`audit-chain`），不自建。
4. 普通读写不逐条留痕，只做指标统计。
5. 审计记录不可被消息平台自身删除。

**完成标准**：管理操作可在 bms 审计链查到；越权尝试有记录；普通读写不产生审计洪泛。

**参考文档**：《[架构设计 · 多租户与安全](../../../设计/架构设计/07_架构设计_多租户与安全.md)》第 9 节；平台《架构设计 · 审计哈希链》。
