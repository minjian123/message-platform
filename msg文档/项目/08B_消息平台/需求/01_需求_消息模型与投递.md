## 1. 域说明 <a id="intro"></a>

本域定义消息平台「对上层承诺什么」：消息怎么组织、投递做到什么程度、顺序保到什么级别、消费怎么分工。它是存储、复制、消费组设计的语义前提——**语义定不下来，后面的存储与传输都无法设计**。

覆盖范围：主题与分区模型、投递语义、顺序性、消费组、延迟消息、保留与重放、应用固定成本治理、可靠性与事务（outbox 适配 / 事务消息后置）。依据见《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》与 bms《[消息模型与语义](../../../../bms文档/资料/知识档案/消息与事件驱动/02_事件驱动_消息模型与语义.md)》。

## 2. 需求 01-1：主题与分区模型 <a id="r01-1"></a>

优先级：1（紧急）

**背景与动机**：消息平台需要一套统一的组织单位，让生产者知道往哪发、消费者知道从哪读、平台知道按什么并行与保留。没有明确的 topic / partition / offset 模型，分区扩容、位点恢复、顺序保证都无从谈起。

**内容**（《架构设计 · 数据面》第 2 节）：

1. 以 **topic** 为逻辑消息类别、**partition** 为物理分片、**offset** 为分区内单调递增序号，消息定位使用 `(topic, partition, offset)` 三元组。
2. 分区数在创建时确定，**只能增不能减**；减少会破坏 key → partition 映射。
3. 分区键由生产者提供，按 `hash(key) % partition_count` 选分区；未提供时按轮询或随机分配。
4. **两类 ID**：`message_id` 由 broker 生成、全局唯一，标识一条消息（用于幂等与排障，与 offset 不等价）；`log_id` 标识一条**物理日志记录**，每次物理写入唯一、永不复用（延迟消息发布时即分配、转投沿用，重放分配新的），用于记录级去重、复制比对、精确定位与**审计引用**。`log_id` 属内部头字段：不进消费端契约，但**发布响应下发**（上游发布即引用）。

**完成标准**：可创建含指定分区数的主题；发布消息返回 `{offset, partition}`；按三元组可正确定位消息；分区键路由可复现。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 2 节；bms《[消息模型与语义](../../../../bms文档/资料/知识档案/消息与事件驱动/02_事件驱动_消息模型与语义.md)》第 2 节。

## 3. 需求 01-2：投递语义 <a id="r01-2"></a>

优先级：1（紧急）

**背景与动机**：bms 现有事件基线是「至少一次 + 消费端幂等」，迁移到自研平台后语义必须保持一致，否则审计与业务事件的可靠性口径会漂移。

**内容**（《架构设计 · 数据面》第 8 节、《消息模型与语义》第 4 节）：

1. 默认语义为**至少一次**：先处理、后提交位点；未 ack 超时重投。
2. 消费端按业务唯一键幂等去重，实现「效果一次」；平台不承诺协议级恰好一次。
3. 提供 `acks` 语义级别（首期至少支持「确认后才算成功」与「不等确认」两档），供 best-effort 场景显式选择。
4. 重复投递必须可识别（携带 `message_id` 与投递次数），便于消费端排障。
5. **单条消息大小上限**：超限须明确拒绝（`350006` 消息过大），不得静默截断或落半条记录；**上限值待定**（规划 §10 #10），由 8B_01 帧契约给出（建议 1MB 级），值定后由 01-2 契约层补校验。

**完成标准**：消费端崩溃后消息可重投；重复消息可被幂等键识别；`acks=0` 与默认档行为可区分且有文档说明。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 8 节；bms《[消息模型与语义](../../../../bms文档/资料/知识档案/消息与事件驱动/02_事件驱动_消息模型与语义.md)》第 4 节。

## 4. 需求 01-3：顺序性 <a id="r01-3"></a>

优先级：2（高）

**背景与动机**：审计链、订单状态迁移等场景要求「同一聚合根的事件按发生顺序被处理」；若平台不提供分区内有序，业务只能靠状态机兜底，复杂度高且易错。

**内容**（《架构设计 · 数据面》第 2 节、《消息模型与语义》第 5 节）：

1. 保证**分区内有序**：同分区按 offset 顺序投递。
2. 同聚合键必落同分区，从而保证**同键有序**；跨分区不承诺全局顺序。
3. 重试不得破坏顺序：同 key 失败重试时阻塞该 key，或回到原分区尾部，不得与主链路并行消费。
4. 再均衡期间允许短暂乱序，但必须保证位点不跳、消息不丢。

**完成标准**：同 key 消息按发布顺序被消费；失败重试后顺序仍成立；再均衡后无消息跳过。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 2 节；bms《[消息模型与语义](../../../../bms文档/资料/知识档案/消息与事件驱动/02_事件驱动_消息模型与语义.md)》第 5 节。

## 5. 需求 01-4：消费组 <a id="r01-4"></a>

优先级：1（紧急）

**背景与动机**：同一事件需要被审计、通知、检索等多个下游各自消费，彼此不能互相抢占。消费组是「组内分摊、组间广播」的唯一实现方式，也是位点隔离的边界。

**内容**（《架构设计 · 接入面》第 3 节、《消费组与再均衡》第 3 节）：

1. 消费组模型：**组内分区不重复分配，组间各自独立位点**。
2. 组内消费者数超过分区数时，多出的消费者空闲（不报错）。
3. 位点按 `(group, topic, partition)` 存储，与消费者实例无关。
4. 支持消费者加入 / 离开时的重新分配；首期可先实现全量再均衡，增量再均衡后置。
5. 心跳与业务处理分离，避免处理慢导致被误判死亡。

**完成标准**：两个组可独立消费同一主题且位点互不影响；消费者增减后分区重新分配；心跳异常不会误踢正常消费者。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 3 节；bms《[消费组与再均衡](../../../../bms文档/资料/知识档案/消息与事件驱动/05_事件驱动_消费组与再均衡.md)》第 3 节。

## 6. 需求 01-5：延迟与定时消息 <a id="r01-5"></a>

优先级：3（中）

**背景与动机**：延迟消息是「出问题时的兜底」——消费失败后的退避重试、订单超时关闭、审批超时提醒，都靠它在「某个时刻一定被投递」。因此它**不能自己成为新的故障点**：接口要稳定（固定档位、不做任意精度）、投递不能扰乱既有顺序与位点口径、失败必须可见可重试、延迟区满了要明确拒绝而不是静默丢弃。

**内容**（《架构设计 · 数据面》§2.4~§2.6、《消息模型与语义》第 6 节）：

1. **固定档位**：`delay_level` 取 1s / 5s / 10s / 30s / 1m / 5m / 10m / 30m / 60m，不支持任意时间精度；档位非法属契约层错误（`10001`）。
2. **延迟区暂存 + 到期转投**：发布时按 key **锁定分区**，写入该分区延迟区（不占 offset、不参与停等、不计入积压），同时分配 `message_id` 与 `log_id`；到期由后台时间轮 `append` 到同分区日志（沿用该 `log_id`），**此刻才分配 offset**，其后与普通消息完全一致。
3. **到期前不可消费**：到期前对任何消费组不可见；到期后复用既有投递语义（至少一次、分区内停等、死信上限、保留期、重放）。
4. **保留期**：从到期 `append` 起算（延迟期间不被保留期清掉）；延迟区自身另设 TTL 兜底，防极端长延迟积压。
5. **健壮性**：到期转投失败**不删延迟记录**（退避重试 + 告警）；转投**先写日志并刷盘、再清延迟记录**（崩溃不丢），恢复期按 `log_id` 扫尾部比对（不重；`message_id` 在重放时会合法重复，不能用）；时钟回拨不得提前投递、前跳须限速批量到期；延迟区满按软上限拒绝并返回 `350015`（不与全局背压 `350005` 混用）。
6. **只读可见性**：提供延迟中消息的只读查询（待投列表 + 计数 + 剩余时间），供排障与管理模块；首期不做改期 / 取消。
7. **定时消息（指定绝对时间）后置**：首期不实现，能力出现后再评估。

**完成标准**：

- 延迟消息在设定时间前不可被任何消费者读取；到期后可被正常消费，且顺序 / 死信 / 保留口径与普通消息一致。
- 延迟消息不占 offset：发布延迟消息不改变 LEO、不推进位点、不计入积压。
- 到期转投失败时延迟记录仍保留（可见、可重试）；延迟区超软上限返回 `350015`，不静默丢。
- 时钟回拨场景下不出现提前投递；延迟中消息的待投列表与剩余时间可查。
- **（归 8B_02 承接）** 未到期延迟消息在进程重启后按剩余时间投递、不提前不丢失，且同一 `message_id` 不重复入日志（单副本；判据见需求 02-7）。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md#model)》第 2.4~2.6 节、第 5 节；[需求 02-7](02_需求_存储与复制.md#r02-7)；bms《[消息模型与语义](../../../../bms文档/资料/知识档案/消息与事件驱动/02_事件驱动_消息模型与语义.md)》第 6 节。

## 7. 需求 01-6：消息保留与重放 <a id="r01-6"></a>

优先级：2（高）

**背景与动机**：新增消费方需要补历史事件，消费逻辑修复后需要重放失败事件，排障时需要复现某条消息。没有保留与重放能力，这些场景只能人工改库。

**内容**（《架构设计 · 数据面》第 6 节、《运维与可观测》第 7 节）：

1. 按时间与容量双维度保留，到期按段删除。
2. 支持按 offset / 时间 / key 条件重放。
3. 重放必须**任务化**：可限速、可暂停、可查看进度、可取消。
4. 重放不改变原消息的 `message_id`，消费端仍需幂等；但重放**产生新的物理记录**，故分配**新的 `log_id`**（记录身份与消息身份分离，见需求 01-1 内容 4）。
5. 重放操作必须留痕（谁、对什么、范围、结果、新 `log_id`）。

**完成标准**：可按条件重放且限速生效；重放任务可暂停与取消；重放记录可在审计链查到，且审计条目可凭 `log_id` 定位到重放产生的日志记录。

**参考文档**：《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 6 节；bms《[运维与可观测](../../../../bms文档/资料/知识档案/消息与事件驱动/10_事件驱动_运维与可观测.md)》第 7 节。

## 8. 需求 01-7：应用固定成本治理 <a id="r01-7"></a>

优先级：2（高）

**背景与动机**：数据面每条请求都要付一次与载荷无关的「固定成本」——主题元数据解析、保留期清理的**全量扫描**、一次数据库会话，实测约 17ms/请求。它带来两个后果：

1. **延迟被固定成本主导**：publish 档端到端 280ms 里，服务端应用成本与传输无关地占去一大块，传输层与序列化的优化收益被压平——8B_01 基准由此得出「协议差异无法裁定」的结论（见[规划 §9.3](../../../规划/01_规划_消息平台.md#review-8b01)）。不治理这一层，任何传输 / 序列化优化都无法被度量。
2. **清理逐请求全量扫描是稳定性隐患**：请求量上来会持续压数据库，从性能问题变成稳定性问题，也与 8B_02 存储落地后的段级清理口径冲突（同一件事做两遍、且其中一遍是全量）。

**内容**（依据 [03-1 详细设计 · 基准设计](../任务/03_传输与协议/03_传输与协议_01_HTTP2传输/设计/01_详细设计_01_HTTP2传输.md#layered) §8.3 的分层测得结论）：

1. **主题元数据缓存**：主题解析结果（分区数、保留配置、主题状态、租户归属）进程内缓存；主题增删改经**同一处失效**，不得出现「改了配置仍按旧值投递」。
2. **保留清理时间节流**：把「每条请求一次全量扫描」改为**同一（主题, 分区）每个窗口最多一次**（清理本就按分区执行；按主题分键要么改变扫描范围、要么让单请求耗时随分区数上升）；触发点仍为请求驱动（后台定时器归 8B_02），窗口取模块常量口径（基座 `Settings` 为 `extra="forbid"`，产品无法新增配置段——同 01-2 / 01-5 的约束）。
3. **会话不跨请求复用**（边界声明）：每请求一次会话的现状**保留**——长会话会把连接池拖死，代价大于收益；本条只为防止把会话复用顺手做进来。
4. **不得改变语义**：缓存与节流不得改变保留判定结果、位点推进、错误码与审计留痕口径；缓存命中与否，`/msg/publish` / `/msg/consume` / `/msg/ack` 的响应结构逐字段一致。
5. **可观测**：主题解析耗时、清理耗时须可测量（结构化日志即可，指标归 06 域），用于验证治理效果。

**完成标准**：同一实例 `POST /msg/publish` 与 `GET /msg/connection` 的 **p50 差值 ≤ 5ms**（相对判据，不作容量结论；并发取 1——03-1 已实证 16 并发下装置跑满 `p50 ≈ 并发数 × 单请求服务时间`，16 并发同参数复跑只作参考）；保留清理在同一窗口内对同一**（主题, 分区）**最多执行一次（用例断言扫描次数）；既有数据面用例全绿、变更模块行 + 分支覆盖率 100%。

**参考文档**：《[消息平台规划](../../../规划/01_规划_消息平台.md#review-8b01)》§9.3；[03-1 详细设计 · 基准设计](../任务/03_传输与协议/03_传输与协议_01_HTTP2传输/设计/01_详细设计_01_HTTP2传输.md#layered) §8.3；《[架构设计 · 数据面](../../../设计/架构设计/04_架构设计_数据面_存储与复制.md)》第 6 节。

## 9. 需求 01-8：可靠性与事务（outbox 适配 / 事务消息后置） <a id="r01-8"></a>

优先级：1（紧急）

**背景与动机**：8B_04 的退出条件是「审计事件不丢、重复消费效果一次」，而当前只交付了「至少一次 + 消费端幂等」的语义与实现（01-2 / 04-4），**业务侧 outbox relay 仍走原链路**——适配层只换了 `EventPublisher` / `BaseServiceClient`，没有换 `BaseOutboxStore` / relay。只要 outbox 仍是原实现，8B_08 迁移就无法把「业务提交 ⇒ 事件可投递」这条链完整切到 msg；事务消息又明确后置，缺少口径会在迁移期被误当成「已支持」。因此需要一条独立需求，把 outbox 适配、审计事件不丢与事务消息边界一次定清。

**内容**（《架构设计 · 接入面》第 9 节、《架构设计 · 决策与风险》D17、《消息平台规划》§3 / §11）：

1. **outbox 适配**：`BaseOutboxStore` / relay 提供 msg 版本或 msg 侧 connector 两种形态之一，业务只依赖端口，**不改业务代码**；适配层可配置切换回原实现。
2. **审计事件不丢**：审计链（05-4 已交付的四类留痕与记录级定位）经 outbox 适配后仍满足「业务提交 ⇒ 事件可投递」；投递失败可重试、可观测，不得静默丢弃。
3. **效果一次**：消费端幂等键与去重口径沿用 04-4；outbox 重投、迁移期在途与未确认事件的处置不得产生重复副作用。
4. **事务消息后置**：首期**不实现**事务消息，只保留端口 / 事件类型 / 失败分支的占位口径；CDC 同样只保留「outbox connector」形态的口子，不做通用 CDC 平台（规划 §11）。
5. **迁移期 fallback**：RocketMQ / outbox 原实现保留，切换与回滚只改配置；与 07-4 的开关契约、07-8 的生产迁移衔接。
6. **边界**：不做跨服务写事务（仍走 TM + XA）；不替代 8B_08 的分域迁移；不在本需求内实现事务消息与 CDC。

**完成标准**：

- outbox relay 可在配置层切到 msg 实现并切回原实现，业务代码零改动；
- 审计事件在切换后不丢，失败可重试且有可定位记录；重复消费效果一次（幂等键用例通过）；
- 事务消息与 CDC 的「后置」边界在契约与文档中写明，不出现「已支持」的误导性描述；
- 迁移期原链路保留，切换 / 回滚配置可复现；
- 变更模块行 + 分支覆盖率达标，静态与文档校验通过。
