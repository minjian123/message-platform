## 1. 域说明 <a id="intro"></a>

本域定义客户端与 broker 之间「用什么协议、怎么连、说多快」。协议一旦上线就要长期兼容，传输决定每条连接的并发上限与延迟，因此本域是平台对外最稳定的契约面。

覆盖范围：HTTP/2 传输、二进制帧与版本演进、序列化、连接管理、背压与流控。依据见《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》与 bms《[协议与传输](../../../../bms文档/资料/知识档案/消息与事件驱动/07_事件驱动_协议与传输.md)》《[序列化与 Schema](../../../../bms文档/资料/知识档案/消息与事件驱动/08_事件驱动_序列化与Schema.md)》。

## 2. 需求 03-1：HTTP/2 传输 <a id="r03-1"></a>

优先级：1（紧急）

**背景与动机**：现有同步链路基于 HTTP/1.1，单连接存在队头阻塞，且无法承载「订阅长驻流」。HTTP/2 的多路复用与流控窗口能同时满足事件发布、订阅与 RPC 三类流量。

**内容**（《架构设计 · 接入面》第 2 节、《协议与传输》第 5 节）：

1. 采用 **HTTP/2**，开发与 PoC 阶段用 **h2c（prior knowledge）**，生产可切 TLS。
2. 支持单连接多 stream 并发；服务端支持 server streaming（订阅长驻流）。
3. 依赖 HTTP/2 原生流控窗口作为传输层背压，不另造一套。
4. 与现有网关兼容：对外仍经平台网关，路径 `/api/msg/v1/msg/...`。
5. 必须能测量「相对 HTTP/1.1 + JSON 基线」的吞吐与延迟差异。

**完成标准**：单连接可并发多请求；订阅长驻流可用；相对基线的吞吐与延迟数据可产出（阈值在 PoC 阶段确定）。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 2 节；bms《[协议与传输](../../../../bms文档/资料/知识档案/消息与事件驱动/07_事件驱动_协议与传输.md)》第 5 节。

## 3. 需求 03-2：二进制帧协议与版本演进 <a id="r03-2"></a>

优先级：1（紧急）

**背景与动机**：协议是客户端与 broker 的长期合同。没有版本与兼容规则，任何字段变更都会断老客户端；没有头体分离，broker 就必须解包才能路由，零拷贝失效。

**内容**（《架构设计 · 接入面》第 4 节、《协议与传输》第 2~3 节）：

1. 帧结构：`magic` + `ver` + `type` + `flags` + `header length` + `header` + `payload`。
2. **头体分离**：header 用 MessagePack，payload 为原始字节，broker 只读 header。
3. 三条演进铁律：**只增可选字段、未知字段 / 未知帧类型必须忽略、版本必须可见**。
4. 主版本不兼容即断连；次版本只增不删。
5. 帧与消息大小必须有上限，超限返回明确错误码（`350006`）。

**完成标准**：新增可选字段后老客户端仍可用；未知帧类型被忽略而非报错；超大帧被拒绝且错误码正确。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 4 节；bms《[协议与传输](../../../../bms文档/资料/知识档案/消息与事件驱动/07_事件驱动_协议与传输.md)》第 2~3 节。

## 4. 需求 03-3：序列化与内容类型 <a id="r03-3"></a>

优先级：2（高）

**背景与动机**：序列化决定线上字节数与两端兼容性。消息会被长期保留、被多个消费方读取，格式一旦定错，回滚成本极高。

**内容**（《架构设计 · 接入面》第 4 节、《序列化与 Schema》第 2~3 节）：

1. 默认序列化为 **MessagePack**；header 强制 MessagePack，payload 由生产者决定。
2. 协议头带 `content_type`，为将来按 topic 切换 Protobuf 留口。
3. 消息 schema 沿用 bms 事件契约「字段只增不删、不改名、不改语义」。
4. 消费端必须做字段校验，校验失败进死信，不得静默忽略。
5. 压缩按批进行，由生产者压缩、消费者解压，broker 不理解压（保零拷贝）。

**完成标准**：字段新增后老消费者可读；字段缺失或类型错误时进死信；压缩后 broker 仍可零拷贝转发。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 4 节；bms《[序列化与 Schema](../../../../bms文档/资料/知识档案/消息与事件驱动/08_事件驱动_序列化与Schema.md)》第 2~3 节。

## 5. 需求 03-4：连接管理 <a id="r03-4"></a>

优先级：2（高）

**背景与动机**：半开连接会长期占用资源却不自知；滚动重启若无优雅关闭，会把在途请求全部打断。连接管理是「长期稳定运行」的基础。

**内容**（《架构设计 · 接入面》第 6 节、《协议与传输》第 6 节）：

1. 应用层心跳（PING / heartbeat），**不得用 TCP keepalive 替代**。
2. 心跳与业务处理分离，避免处理慢导致连接被误判死亡。
3. 支持 `GOAWAY` 优雅关闭：停止接新流、等待在途完成。
4. 客户端支持指数退避 + 抖动的断线重连。
5. 限制单连接最大并发流与空闲回收时间。

**完成标准**：网络中断后连接能在超时内被识别并释放；滚动重启不丢在途请求；重连不会形成脉冲。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 6 节；bms《[协议与传输](../../../../bms文档/资料/知识档案/消息与事件驱动/07_事件驱动_协议与传输.md)》第 6 节。

## 6. 需求 03-5：背压与流控 <a id="r03-5"></a>

优先级：2（高）

**背景与动机**：生产快、消费慢是消息系统的常态。没有背压，积压会先把内存或磁盘打满，再让整个 broker 雪崩。

**内容**（《架构设计 · 接入面》第 7 节、《背压与流控》第 2~7 节）：

1. 消费采用**长轮询**：请求挂起直到有消息或超时，天然背压且避免空转。
2. 单消费者设 `inflight` 条数与字节双阈值，超限暂停推送。
3. 长轮询必须有 `maxWait`，不得永久挂起。
4. 生产侧按租户 / 主题限速，超限返回 `350005`。
5. 背压不得只靠一层：传输层窗口 + 应用层 inflight + 磁盘水位同时存在。

**完成标准**：消费停止时积压上涨但服务不崩；`inflight` 超限后暂停推送；生产超限返回明确错误码。

**参考文档**：《[架构设计 · 接入面](../../../设计/架构设计/05_架构设计_接入面_协议与客户端.md)》第 7 节；bms《[背压与流控](../../../../bms文档/资料/知识档案/消息与事件驱动/06_事件驱动_背压与流控.md)》第 2~7 节。
