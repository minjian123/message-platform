## 2. 租户标识与三级命名空间 <a id="namespace"></a>

```text
{tenant_id} / {namespace} / {topic} / {partition}
```

| 层级 | 取值 | 说明 |
| --- | --- | --- |
| **tenant_id** | 雪花 ID（十进制字符串） | **内部身份**，不可变；bms 明确规定「库键 code 段可冻结，但内部身份一律 `tenant_id`」 |
| **namespace** | **对齐 bms `module_key`** | 一个平台模块一个命名空间（如 `audit` / `notify` / `file`） |
| **topic** | 业务自定义 | 建议 `{对象}.{动作}`，如 `operation.created` |
| **partition** | `0` 起整数 | 并行与顺序单位 |

### 2.1 为什么 tenant 用 ID 而不是编码

| 标识 | 可变性 | 是否适合做存储边界 |
| --- | --- | --- |
| `tenant_id`（雪花） | **不可变** | ✅ 目录与元数据列都用它 |
| `code`（租户编码） | 可变更（bms 允许改编码，库名不变） | ❌ 一改目录就断链 |
| `db_basis`（库名基） | 创建时冻结 | 可读性好，但只用于库名派生，不是内部身份 |

**结论**：**目录与元数据列一律用 `tenant_id`**。租户编码只出现在日志与展示层，用于人读映射。

### 2.2 为什么 namespace 对齐 module_key

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 自由定义 | 灵活 | 两套命名体系，权限与配额无法与模块对齐 |
| 对齐产品键（`bms` / `mdm`） | 稳定 | 同一产品内多条业务线无法分开配额 |
| **对齐 `module_key`** | 与平台模块、权限码、菜单天然对齐；审计事件正好落 `audit` 命名空间 | 产品内部事件需占一个 module_key |

**取值约束**：namespace 必须是服务目录中已登记且启用的 `module_key`；未登记值拒绝创建（fail-closed），避免出现「消息平台自造模块」。

### 2.3 物理落点

```text
data/{tenant_id}/{namespace}/{topic}/{partition}/*.log
```

按租户 / 命名空间分目录，使「停用租户限流、算用量、限磁盘」都是目录级操作。

## 3. 隔离模型 <a id="isolation"></a>

### 3.1 与 bms 隔离口径的对应关系

bms 的隔离是「**每服务 × 每租户一独立库**」；msg 没有业务表，因此对应关系是：

| bms | msg | 说明 |
| --- | --- | --- |
| 平台服务库 `bms_{service}`（跨租户） | msg 平台库（`msg_topic` / `msg_quota` 等） | 元数据按 `tenant_id` 列区分 |
| 服务租户库 `bms_{service}_{db_basis}` | `data/{tenant_id}/` 目录 | **文件层面对应的「每租户独立存储区」** |
| 归档库 `bms_archive` | 归档目录（后置） | 消息归档走独立目录，不混入热数据 |

**这不是「降级为逻辑隔离」**，而是把「库」换成了「目录」：租户之间仍是物理分离的存储区，只是介质从数据库变成文件系统。

### 3.2 隔离层次

| 层 | 做法 | 强度 |
| --- | --- | --- |
| 逻辑隔离 | 命名空间 + 元数据 `tenant_id` 校验 | 中（防越权，但共享进程） |
| 目录隔离 | `data/{tenant_id}/...` | 中高（删除、配额、限盘独立） |
| 进程隔离 | 独立 broker（后置） | 高（故障不扩散） |
| 物理隔离 | 独立集群 / 独立机器（后置） | 最高 |

**首期选择：逻辑隔离 + 目录隔离**。理由：单人运维下为每租户起独立进程不现实；目录隔离已能满足「停用、配额、统计」三类需求。

**升级信号**：某租户吞吐或存储占比超过阈值、或有强合规隔离要求时，再按租户拆进程 / 集群。

## 4. 租户解析与状态校验 <a id="resolve"></a>

### 4.1 解析来源：复用基座解析链，不另造

| 面 | 接入方式 |
| --- | --- |
| **管理面 / RPC**（ASGI） | 直接用基座中间件注入的租户上下文（以已校验令牌的租户位为准，不采信客户端自报头） |
| **数据面**（HTTP/2 `h2` 直连，不走 ASGI） | 在帧处理入口**复用基座的解析函数**（同一套来源次序与校验），不依赖中间件 |

**关键约束**：两种入口必须得出**同一个租户**，因此数据面不允许「信任客户端自报的 header」，必须走同一套令牌校验与解析逻辑。

### 4.2 状态校验：复用基座租户源，不另建缓存

| 租户状态 | 行为 |
| --- | --- |
| 启用 | 正常收发 |
| 停用 | **拒绝生产与消费**，返回明确错误码 |
| 不存在 | 拒绝，不泄露租户是否存在（与 bms 口径一致） |

**实现方式**：直接使用基座 `RemoteTenantSource`——它已带**全局版本戳**（租户开通 / 停用 / 改名后由租户服务 INCR 版本键，**即时生效**），并按服务侧缓存租户快照。

**关键结论**：msg **不再自建短 TTL 缓存**。原设计「每请求 + 30s TTL」是重复实现，且会引入「基座已判定停用、msg 仍按旧缓存放行」的不一致窗口。

| 入口 | 校验方式 |
| --- | --- |
| 管理面 / RPC | 中间件解析时已校验，业务层直接取上下文 |
| 数据面 | 调用同一 `RemoteTenantSource`（版本键即时比对） |
| 异步任务 / 消费 | 基座租户可用性守卫回落默认实现（07D 任务 03 附录 A）：命名空间判定下移到 `scope_rule` 规则链第四步，循环入口 `per_round(...)` / 批处理 `batch(...)` 经同一契约；msg 不再自建 `MsgTenantGuard` |

**降级口径**：租户源不可达时，按基座既有策略处理（`ServiceUnavailableError`），不静默放行。

### 4.3 服务间调用的租户传递

bms 的 `ServiceRequest` 支持 `tenant_id` claim 传递，目标服务经边缘信任解析租户。msg 作为被调方，从同一 claim 获取租户，不要求调用方额外传参。

## 5. 租户生命周期 <a id="lifecycle"></a>

### 5.1 开通：懒初始化，且只在发布时创建

| 动作 | 行为 |
| --- | --- |
| **首次发布**到某 `(tenant_id, namespace)` | 自动创建命名空间与默认配额，随后正常写入 |
| **查询**未开通的命名空间 | 返回「不存在」，**不产生写副作用** |
| 平台超管预建 | 管理模块可显式创建（可选） |

**为什么只在发布时创建**：读请求产生写副作用，会让扫描、误操作、探活等行为创建大量空命名空间；写操作创建则符合「元数据只由真实使用产生」的原则。

**并发竞争**：首次发布可能并发，靠 `(tenant_id, namespace, topic)` 唯一约束兜底，冲突时重查而非报错。

### 5.2 停用 / 删除：拒绝收发，按保留期处理

| 项 | 结论 |
| --- | --- |
| 停用（`tenant.suspended`） | **生产 / 消费一律拒绝**；已建立连接与长驻流取消；数据完整保留，不清理、不归档 |
| 删除（`tenant.deleted`） | **停写**；连接 / 长驻流取消、延迟区立即清理；消息数据 / 位点 / 元数据按主题 `retention_ms` 保留，保留期内只读，到期物理删除 |
| 管理查询 | 停用 / 删除保留期内仍可只读查看（便于运营核对用量与清理进度）；到期物理删除后不可见 |
| 恢复（`tenant.activated`） | 停用后立即恢复；删除后在保留期内到达则取消待清理、恢复受理；已到期并物理删除的主题不可恢复 |

**为什么可以自动清理**：bms 已登记 `tenant.deleted` 事件（07D `01-4`），语义是「产品按保留期归档或清理资源」；清理以**主题自身保留期**为边界，保留期内只读，不会把「停用可恢复」的数据立即销毁。bms 平台侧的 `tenant.deleted` 触发点尚未落地（归 04_03），msg 侧先按契约消费，端到端真实事件依赖平台后续任务。

### 5.3 平台租户

平台租户（`kind = platform`）**按普通租户处理**：

- 有自己的 `tenant_id`，同样分目录、同样走解析与校验。
- `tenant.created` 等系统事件放在平台租户的命名空间下（namespace 对齐 `module_key`）。
- **不引入「全局 topic」**：跨租户广播由各租户各自消费一份，换取「无特例、无额外权限模型」。

## 6. 配额 <a id="quota"></a>

### 6.1 归属：msg 自维护，bms 只读回显

| 项 | 结论 |
| --- | --- |
| 配额存储 | **msg 自己的 `msg_quota` 表**（平台库，按 `tenant_id` / `namespace`） |
| 为什么不进 `sys_tenant_quota` | 该表归属 bms tenant 服务（`bms_tenant` 库），msg 按隔离纪律不能跨服务直写；且消息维度（主题数 / 消息存储 / 吞吐）不是基座通用维度 |
| bms 如何看到 | msg 在 `deploy/registry/msg.toml` 登记**产品数据源**，bms 租户管理页按 `data_source_key` 装载只读板块 |
| 单一事实源 | 配额值只在 `msg_quota`，bms 页面是只读投影，**不做双写** |

### 6.2 配额维度

| 配额 | 粒度 | 超限动作 |
| --- | --- | --- |
| 主题数 | 租户 / 命名空间 | 拒绝建主题（`350025`） |
| 消费组数 | 租户 | 拒绝建组（`350026`） |
| 生产速率（条/秒） | 租户 / 命名空间 | 限流（`350005`） |
| 消息存储量 | 租户 | 拒绝写（`350022`，`data.reason=tenant_quota`） |
| 未确认消息数 | 租户聚合（组级归 8B_02） | 返空批 + `paused=true` |
| 连接数 | 租户 | 拒绝新连接（`350020`） |

### 6.3 执行与展示

| 项 | 要求 |
| --- | --- |
| 执行点 | **前置**：接收请求时判断，不做事后统计 |
| 软硬两档 | 软限告警 / 管理模块标红；硬限拒绝并返回明确错误码；软限缺省为硬限 80% |
| 缺省与懒初始化 | 未配置按内置缺省生效；首次发布懒初始化六条租户级缺省行（`origin=default`） |
| 可观测 | 用量在 msg 管理模块可见；bms 租户管理页经只读投影回显（三条按单位拆分的 `kind=quota` 声明） |
| 调整 | `GET/PUT /api/v1/msg/admin/quotas` 批量调整，即时失效缓存并写审计 `msg:quota.update` |

## 7. 授权 <a id="authz"></a>

| 模型 | 粒度 | 用途 |
| --- | --- | --- |
| RBAC（权限码） | 功能级 | `msg:query` / `msg:manage` / `msg:publish` / `msg:consume` / `msg:rpc`（真实 RBAC，权限码由 `msg-permissions` 种子登记） |
| topic ACL | 资源级 | 某用户 / 角色可 publish / subscribe / describe / manage 某 topic |

**操作类型**：`publish` / `subscribe` / `describe` / `manage`（`manage` 不隐含其他动作）。

**优先级**：先校验 RBAC，再校验 topic ACL，最后校验租户 / 命名空间归属；ACL 不得前置，且跨租户 / 跨模块不因 ACL 放行。

**落地（05-3）**：

- `msg_topic_acl` 规则 + `msg_topic_acl_scope` 版本戳（msg 平台库，`tenant_id` 列隔离）；无匹配规则默认允许，显式 deny 优先；收回置 `status=disabled`。
- 基座 `resource_acl` 端口（`msg.topic` 实现）负责同步判定；msg 异步守卫按版本戳装载规则快照，变更即时生效；读取失败 10007 / 503 fail-closed。
- 判定入口：数据面 publish / consume / ack / nack / join / subscribe；管理面 topics / groups / delayed / replay；帧闸门与长驻流同口径；heartbeat / leave 只走 RBAC。
- ACL 管理端点 `GET/PUT/DELETE /api/v1/msg/admin/acls`（`msg:manage` + 目标主题 `manage`）；授予 / 更新 / 收回走 `msg:acl.grant|update|revoke` 强审计。
- 拒绝码 `350027`（基座 `82013` 经 `maps_from` 映射），403 且不泄露主题存在性。

**三个易漏的越权点**：

1. 消费者订阅了其他租户 / 其他命名空间的 topic。
2. 管理接口只校验「已登录」，不校验「租户归属」。
3. 重放接口能对任意 topic 操作。

## 8. 加密与密钥轮换 <a id="crypto"></a>

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 传输 | TLS（h2 over TLS） | 生产必须；内网可先 h2c |
| 静态 | 磁盘加密 | 防物理窃取 |
| 字段级 | payload 加密 | 业务负责，broker 只存密文 |

**与零拷贝的关系**：字段级加密不影响零拷贝；但如果 broker 要做内容审计就必须解包，零拷贝失效。**架构选择：不做内容审计，只做操作审计**。

| 对象 | 轮换方式 |
| --- | --- |
| TLS 证书 | 双证书过渡（新旧并存） |
| 服务 JWT 密钥 | `active_kid` + 多密钥并存，旧密钥保留到令牌过期 |

**铁律：先加新、再切用、后删旧**。直接替换会让在途连接与未过期令牌全部失效。

## 9. 审计 <a id="audit"></a>

| 类别 | 是否留痕 | 去向 |
| --- | --- | --- |
| 配置变更（建删 topic、改配额） | 必须 | bms 审计链 |
| 数据操作（重放、删消息、位点重置） | 必须 | bms 审计链 |
| 权限变更（授权 / 回收） | 必须 | bms 审计链 |
| 访问异常（越权尝试、认证失败、停用租户访问） | 必须 | bms 审计链 + 告警 |
| 普通读写 | 不逐条留痕 | 指标统计 |

**留痕内容**：谁（principal）、何时、对什么（`tenant_id` / namespace / topic / group）、做了什么、结果、来源 IP / `trace_id`，
涉及具体日志记录时另带 **`record_ref`**（记录类型 + 主键；消息类操作 `type = msg.message`、`id = log_id`）。

**为什么带 `record_ref`**：审计链是哈希链、写后不可改，条目一旦记下记录主键就等于钉住**一条物理记录**，事后一次寻址；
反之只能按 `topic + 时间窗 + key` 反查——时间戳会同毫秒多条、`key` 不唯一、延迟消息在到期前**还没有 offset**，反查既慢又不确定。
定位对象按操作区分：重放定位**任务**（`msg.replay` + 任务主键，消息级靠载荷首末 `log_id`）、位点重置定位**位点**
（`msg.offset` + `topic:partition`）、延迟处置 / 删消息定位**消息记录**（`msg.message` + `log_id`）。

**这不产生审计洪泛**：「普通读写不逐条留痕」不变，`record_ref` 只出现在**涉及具体记录**的那几类操作上；发布/消费本身不写审计条目。

## 10. 与 bms 租户体系对齐 <a id="align"></a>

> 继承项以 bms《[架构设计 · 产品租户与安全接入](../../../bms文档/设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》为准；本表只列 msg 的接入方式，不重复定义基座能力。

| bms 机制 | msg 接入方式（继承 / 扩展） |
| --- | --- |
| 租户内部身份 | 用 `tenant_id`（雪花），目录与元数据列一致 |
| 租户解析链 | 管理面 / RPC 用中间件，数据面复用同一套解析函数 |
| 租户状态 | 每次请求 / 每轮消费校验（复用基座租户源快照缓存与全局版本戳，msg 不自建缓存），停用拒绝收发 |
| 模块注册 | namespace 必须取自已启用 `module_key` |
| 租户开通 | 懒初始化（仅发布时创建），不依赖事件 |
| 租户停用 | 拒绝收发、保留数据，不做自动清理 |
| 配额 | msg 自维护；`kind=form` 与三条按单位拆分的 `kind=quota` 声明并存，bms 经只读投影回显（07D 任务 03 附录 C）；租户页改由 msg 前端只读插件直连，不再经 bms 反向后端调用 |
| 权限码 | `msg:query` / `msg:manage` / `msg:publish` / `msg:consume` / `msg:rpc`；真实 RBAC（远程权限数据源）+ `msg-permissions` 种子（05-3） |
| 审计链 | 管理操作写基座审计链；记录级操作带 `record_ref` 扩展位并按强审计写入（07D 任务 03 附录 D）；ACL 变更走 `emit_acl_change` 强审计（05-3） |

**不做的事**：msg 不复制 bms 租户表、不自行判定租户有效性（以基座解析结果为准）、不写 `sys_tenant_quota`。
