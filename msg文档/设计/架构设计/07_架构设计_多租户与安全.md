## 2. 三级命名空间 <a id="namespace"></a>

```text
{tenant} / {namespace} / {topic} / {partition}
```

| 层级 | 作用 | 例 |
| --- | --- | --- |
| **tenant** | 隔离边界，与 bms 租户对齐 | `tenant_a` |
| **namespace** | 租户内业务线 / 应用 | `audit`、`order`、`notify` |
| **topic** | 消息类别 | `order.created` |
| **partition** | 并行与顺序单位 | `0`、`1`… |

**为什么需要namespace**：只有「租户 + topic」两级时，同一租户下多个业务线的配额与权限无法分开管理。三级是 Pulsar 的成熟做法，代价是路径变长、元数据多一层。

**物理落点**：

```text
data/{tenant}/{namespace}/{topic}/{partition}/*.log
```

按租户 / 命名空间分目录，使「删租户、算用量、限磁盘」都是目录级操作。

## 3. 隔离模型 <a id="isolation"></a>

| 层 | 做法 | 强度 |
| --- | --- | --- |
| 逻辑隔离 | 命名空间 + 元数据校验 | 中（防越权，但共享进程与磁盘） |
| 目录隔离 | `data/{tenant}/...` | 中（删除与配额独立） |
| 进程隔离 | 独立 broker（后置） | 高（故障不扩散） |
| 物理隔离 | 独立集群 / 独立机器（后置） | 最高 |

**首期选择：逻辑隔离 + 目录隔离**。理由：单人运维下，为每个租户起独立进程/集群不现实；目录隔离已能满足「删除、配额、统计」三类需求。

**升级信号**：某租户的吞吐或存储占比超过阈值、或有强合规隔离要求时，再按租户拆进程/集群。

## 4. 配额 <a id="quota"></a>

| 配额 | 粒度 | 超限动作 |
| --- | --- | --- |
| topic 数 | 租户 / 命名空间 | 拒绝建 topic（`35005`） |
| 消费组数 | 租户 | 拒绝建组 |
| 生产速率（msg/s 或 B/s） | 租户 / topic | 限流 |
| 存储量 | 租户 | 缩短保留期 / 拒绝写 |
| 未确认消息数 | 消费组 | 暂停投递 |
| 连接数 | 租户 | 拒绝新连接 |

**执行点必须前置**：在「接收请求时」判断，而不是「写入后统计」——后者资源已经被占用。

**软硬两档**：

| 档 | 行为 |
| --- | --- |
| 软限（如 80%） | 告警、管理台标红 |
| 硬限（如 100%） | 拒绝并返回明确错误 |

**配额可观测**：每个租户的用量必须能在管理台看到，否则配额是黑盒，用户不知道为什么被拒。

## 5. 认证 <a id="authn"></a>

| 方式 | 用途 | 说明 |
| --- | --- | --- |
| **服务 JWT** | 内部服务间 | 复用 bms `[service_token]`，不另造 |
| TLS（mTLS 可选） | 生产传输 | h2 over TLS |
| API Key | 外部集成（弱） | 首期不做 |

**必须校验三件事**：

1. **真实性**：签名、签发者、有效期。
2. **归属**：这个服务属于哪个租户 / 命名空间。
3. **权限**：能对哪些 topic 做哪些操作。

**最关键的一条**：**租户 ID 必须从令牌解析，不接受客户端自报**。否则任何客户端都能冒充其他租户。

## 6. 授权 <a id="authz"></a>

| 模型 | 粒度 | 用途 |
| --- | --- | --- |
| RBAC（权限码） | 功能级 | `msg:query` / `msg:manage` |
| topic ACL | 资源级 | 某服务可 publish / subscribe 某 topic |

**操作类型**：`publish` / `subscribe` / `describe` / `manage`。

**优先级**：先校验 RBAC（有没有这个功能权限），再校验 ACL（有没有这个主题的权限）。

**三个易漏的越权点**：

1. 消费者订阅了其他租户 / 其他命名空间的 topic。
2. 管理接口只校验「已登录」，不校验「租户归属」。
3. 重放接口能对任意 topic 操作。

## 7. 加密 <a id="crypto"></a>

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 传输 | TLS（h2 over TLS） | 生产必须；内网可先 h2c |
| 静态 | 磁盘加密 | 防物理窃取 |
| 字段级 | payload 加密 | 业务负责，broker 只存密文 |

**与零拷贝的关系**：字段级加密不影响零拷贝（broker 只存密文、不解包）；但如果 broker 要做内容审计，就必须解包，零拷贝失效。**架构选择：不做内容审计，只做操作审计**。

## 8. 密钥轮换 <a id="rotation"></a>

| 对象 | 轮换方式 |
| --- | --- |
| TLS 证书 | 双证书过渡（新旧并存） |
| 服务 JWT 密钥 | `active_kid` + 多密钥并存，旧密钥保留到令牌过期 |
| API Key（若启用） | 双 Key 过渡 |

**铁律：先加新、再切用、后删旧**。直接替换会让在途连接与未过期令牌全部失效。

## 9. 审计 <a id="audit"></a>

| 类别 | 是否留痕 | 去向 |
| --- | --- | --- |
| 配置变更（建删 topic、改配额） | 必须 | bms 审计链 |
| 数据操作（重放、删消息、位点重置） | 必须 | bms 审计链 |
| 权限变更（授权 / 回收） | 必须 | bms 审计链 |
| 访问异常（越权尝试、认证失败） | 必须 | bms 审计链 + 告警 |
| 普通读写 | 不逐条留痕 | 指标统计 |

**留痕内容**：谁（principal）、何时、对什么（tenant / namespace / topic / group）、做了什么、结果、来源 IP / trace_id。

## 10. 与 bms 租户体系对齐 <a id="align"></a>

| bms 机制 | msg 对接方式 |
| --- | --- |
| 租户上下文 | 从服务 JWT 解析，注入请求上下文 |
| 租户路由 | msg 不查业务库，只按 `tenant` 分目录与元数据 |
| 权限码 | 沿用 `业务码:动作` 规则，登记 `msg:query` / `msg:manage` |
| 审计链 | 管理操作写 `audit-chain` 事件 |
| 租户开通 | 首次发布时自动建命名空间（或管理台预建） |

**不做的事**：msg 不复制 bms 的租户表，不自行判定租户有效性（以令牌为准）。
