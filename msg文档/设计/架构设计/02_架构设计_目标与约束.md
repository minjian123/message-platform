## 1. 文档目的 <a id="purpose"></a>

把「消息平台要做成什么样」拆成可验证的目标，并明确「不能突破的约束」。**目标是验收依据，约束是设计边界**——两者共同决定后面所有架构取舍。

## 2. 功能目标 <a id="functional"></a>

### 2.1 事件总线

| 能力 | 目标 | 判据 |
| --- | --- | --- |
| 发布 | 生产者可向指定 topic 发布消息，返回 offset | 发布成功可查、失败返回明确错误码 |
| 订阅 | 消费者按消费组订阅，支持从指定位点开始 | 换消费者后能从已提交位点续读 |
| 消费组 | 组内分摊、组间广播 | 两组独立消费互不影响；组内无重复分配 |
| 顺序 | 同分区 / 同聚合键有序 | 同 key 消息按发布顺序被消费 |
| 确认 | ack 推进位点，未 ack 超时重投 | 未 ack 消息在超时后重新投递 |
| 重试 | 失败按退避重试，超限进死信 | 重试次数与退避可配置 |
| 死信 | 死信可查询、可重放、可忽略 | 死信处置有记录、可追溯 |
| 重放 | 按位点 / 时间 / key 重放 | 重放任务可限速、可暂停 |

### 2.2 同步 RPC

| 能力 | 目标 | 判据 |
| --- | --- | --- |
| 请求响应 | 一元调用，返回结果或错误 | 错误分类明确（可重试 / 不可重试） |
| 超时 | deadline 跨跳传播 | 下游不会在上游已超时后继续长跑 |
| 取消 | 上游取消可传导到下游 | 取消后资源释放 |
| 流式 | 至少支持服务端流 | 订阅类长驻流可用 |

### 2.3 管理台与运维

| 能力 | 目标 | 判据 |
| --- | --- | --- |
| 只读视图 | 主题 / 消费组 / 分区 / 积压 / 死信 | 排障不需要登录服务器 |
| 写操作 | 建删主题、改配额、重放 | 有权限校验与操作留痕 |
| 可观测 | 指标 / 日志 / 追踪 | 能定位到具体分区与消费组 |

### 2.4 多租户

| 能力 | 目标 | 判据 |
| --- | --- | --- |
| 隔离 | 租户间消息不可互读 | 越权访问被拒绝并留痕 |
| 配额 | 按租户限制 topic 数、吞吐、存储 | 超限被拒绝或有明确降级 |
| 审计 | 管理操作可追溯 | 写入 bms 审计链 |

## 3. 非功能目标 <a id="nonfunctional"></a>

### 3.1 性能

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 传输开销 | 同逻辑下优于 HTTP/1.1 + JSON 基线 | 比值在 8B_01 用实测确定，不在架构层写死 |
| 延迟 | 端到端 P99 可控 | 以「不显著劣于现有 RocketMQ 链路」为底线 |
| 吞吐 | 单机可支撑平台事件量 | 具体阈值由 8B_12 容量测试给出 |
| 资源效率 | 顺序写 + 零拷贝转发 | 保零拷贝是硬约束（见 04 篇） |

> **架构层只定方向，不定数字**：具体阈值、基准脚本、达标线在 8B_01 与 8B_12 的测试记录里。

### 3.2 可靠性

| 属性 | 目标 |
| --- | --- |
| 投递语义 | **至少一次 + 消费端幂等**（默认）；效果一次由业务幂等键保证 |
| 持久性 | 已 ack 的消息在重启后不丢 |
| 恢复 | 崩溃后从持久化位点恢复，截断不完整尾部 |
| 复制 | 已提交（多数派 / ISR 确认）的消息在单节点故障后不丢 |
| 重放 | 死信与历史消息可按条件重放，且重放不破坏幂等 |

### 3.3 可用性

| 属性 | 目标 |
| --- | --- |
| 单机可用 | 进程崩溃可在重启后自恢复 |
| 集群可用 | 单节点故障不影响写入（8B_05 后） |
| 降级 | 磁盘高水位时拒绝写而非整机崩溃 |
| 回滚 | 迁移期可按域切回原链路 |

### 3.4 可运维性

| 属性 | 目标 |
| --- | --- |
| 可观测 | 积压、延迟、死信、ISR 可查 |
| 可操作 | 重放、死信处置、配额调整可在管理台完成 |
| 可诊断 | 每条消息可按 `message_id` / offset 定位 |
| 低组件数 | 单服务多域，避免多进程运维 |

### 3.5 安全

| 属性 | 目标 |
| --- | --- |
| 身份 | 复用 bms 服务 JWT；生产启用 TLS |
| 授权 | 按租户 + topic 的 ACL，权限码 `msg:query` / `msg:manage` |
| 隔离 | 租户 ID 从令牌解析，不接受客户端自报 |
| 留痕 | 管理操作写 bms 审计链 |

### 3.6 可扩展性

| 属性 | 目标 |
| --- | --- |
| 协议演进 | 只增字段、未知忽略、版本可见 |
| 存储演进 | 格式预留复制字段（term / 副本位点），避免 8B_05 推倒重来 |
| 部署演进 | 单服务先行，可按面拆分为多服务 |
| 接入演进 | 先 Python 客户端，跨语言时按 topic 切 Protobuf |

## 4. 约束 <a id="constraints"></a>

| # | 约束 | 对设计的影响 |
| --- | --- | --- |
| 1 | **单人兼职维护**，无专职运维 | 组件越少越好；管理台与指标必须先于功能 |
| 2 | **后端单一 Python** | 接受 GIL 与解释器开销；热点用异步批处理，必要时 C 扩展 |
| 3 | **三库兼容**（MySQL / PG / 达梦） | 元数据存储不得依赖特定方言特性；CDC 路线基本排除 |
| 4 | **本地开发 SQLite** | 开发态要能跑单机 broker，不依赖外部中间件 |
| 5 | **Windows 开发机 + Linux 部署** | 文件 IO、fsync、网络行为需双端验证 |
| 6 | **01_01 已上线、06_01 已依赖** | 迁移必须保留回滚，不能一次性删除 outbox |
| 7 | **审计合规** | 操作 / 登录 / 字段审计不能丢事件 |
| 8 | **bms 产品接入机制** | 按 `deploy/registry/msg.toml` 声明接入，不改基座业务 |
| 9 | **对外契约仍走 OpenAPI** | 性能优化只发生在内部链路与框架栈，不改变对外契约 |
| 10 | **跨服务写仍走 TM + XA** | 消息不承担分布式事务 |

## 5. 质量属性权衡 <a id="tradeoff"></a>

消息平台的三个核心属性互相牵制，架构必须显式选择：

| 权衡 | 倾向 | 理由 | 代价 |
| --- | --- | --- | --- |
| 一致性 vs 吞吐 | **偏向吞吐** | 平台事件量以业务联动为主，不需要线性一致 | 极端故障可能丢最后几条未提交消息 |
| 可用性 vs 一致性 | **偏向可用性**（单机期） | 单机先行阶段无复制，先保证能跑 | 单节点故障即不可用，8B_05 后改善 |
| 顺序 vs 并行 | **分区内顺序** | 满足聚合有序，保留并行 | 跨分区无全局顺序 |
| 功能 vs 运维成本 | **偏向低运维** | 单人维护 | 放弃跨机房、Schema Registry 等能力 |
| 自研 vs 成熟度 | **自研 + 可刹车** | 与平台深度集成 | 需承担自研 bug 风险，用适配层兜底 |
